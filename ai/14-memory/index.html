一、AI 为什么记不住你：记忆是补出来的

会话即忘不是 bug，是大模型的工作机制——所有"记忆"都是工程手段

会话即忘：金鱼记忆的技术真相

很多人有过这种体验：跟 AI 聊了一个小时，把自己的偏好、背景、项目情况说得清清楚楚，第二天新开一个对话，它完全不认识你——"我昨天不是告诉过你了吗？"是的，你告诉过，但那次会话结束的瞬间，一切都清零了。这不是 AI"敷衍"你，而是大模型的基本工作机制决定的：模型本身是无状态的——每次请求，它只能"看见"这一次随请求送进去的文字，对之前的会话没有任何内在记忆。你在聊天软件里感受到的"连续对话"，其实是应用每次都把本轮之前的聊天记录一并塞进请求里造成的效果。

理解了这一点，就理解了"记忆"类功能的真相：AI 产品的所有记忆能力，都是外部工程补出来的。聊天软件把历史对话带上，是"短期记忆"的工程化；产品宣传的"它记得你的偏好"，通常是把你的关键信息存进它家的数据库，下次对话时悄悄塞回请求里；你上传的文件"它读过了"，也只是在那次会话里被放进了上下文。没有任何一种是真的"长进模型脑子里"——模型权重在为你服务的过程中并没有被修改。这个认知很重要：它决定了你的资料放在哪里、谁能看到、删了之后是不是真的删了（第六节隐私讨论的基础）。

上下文窗口：AI 的"工作台面"

每次请求能送进模型的文字总量有上限，这个上限叫上下文窗口（context window），按 token 计（第1章讲过 token 是模型处理文字的计量单位，中文大致一两个字对应一个 token）。可以把它想象成一张工作台面：台面再大也是有限的，你的指令、历史对话、上传的文件、系统的提示词，全都要摊在这张台面上让模型"一眼看到"；台面放满了，最早放上去的东西就会被挤下去（多数聊天产品会自动丢弃最久远的对话内容）。

近几年各家模型的窗口从几千 token 一路扩到数十万甚至百万级，"把所有资料全塞进去"看似快要可行，但三个物理限制依然存在：①成本——按 token 计费的服务里，窗口塞得越满，每一次提问越贵，把一百页手册全文带上问一句话，等于每次提问都为一百页付钱（第5章的成本账）；②速度——输入越长，响应越慢；③效果——研究与实践都发现，超长上下文里模型对中间部分信息的利用率会下降（学术界称为"迷失在中间"现象，Liu et al., 2023 的研究是常被引用的出处）。工作台面大了是好事，但把整个仓库搬上台面，既贵又乱，找东西反而更慢——这就引出了下一节的思路：别把仓库搬上台面，只把需要的那几页拿上来。

记忆的分类：短期、长期与"外置大脑"

借用人类记忆的框架，AI 系统的记忆可以分成两大类，工程手段完全不同。短期记忆=上下文窗口里的东西：本次会话的历史对话、刚上传的文件、系统提示词——模型"睁眼就能看见"，但会话结束或窗口挤满就消失（Anthropic 官方文档把上下文窗口称为模型的"工作记忆"，working memory）。长期记忆=存在窗口之外、需要时再取回的信息：你的偏好档案、历史会话摘要、整个资料库——平时躺在数据库里，用的时候通过检索（本章主角 RAG）或产品自动注入的方式，把相关部分"搬回"工作台面。

这个分类给普通用户三个实用推论：①"教 AI 记住"的正确姿势是写下来——想让偏好长期生效，与其每次口头叮嘱，不如写进产品的记忆/自定义指令功能，或者干脆维护一份"个人说明书"文档，每次重要任务开头贴给它（土办法，但百分百可控）；②长期记忆必然经过检索，检索就可能失准——产品"忘记"你说过的话，多数不是没存，是这次没检索到，重要信息别把身家性命押在自动记忆上；③记忆是隐私面——长期记忆里存着你的偏好与历史，它存在谁家服务器、能否查看和删除，属于第六节"条款关"的必查项。本章余下部分聚焦长期记忆最重要、最可控的形态：你自己的知识库。

二、RAG 是什么：先检索，再回答

开卷考试的思路：不背下整个图书馆，答题时现场翻到那一页

一句话与一个比喻：RAG 的本质

RAG（Retrieval-Augmented Generation，检索增强生成）一句话：让模型回答之前，先从你的资料库里检索出最相关的几段原文，把它们连同问题一起交给模型，让它"照着资料回答"。比喻是开卷考试：闭卷考试全靠背（对应模型只凭训练时记住的参数知识答题——记不全、会记错、更不知道你家的事）；开卷考试允许带资料，答题前先翻到相关页（对应 RAG 的检索步骤），再组织语言作答。考试难的不是背得多，而是翻得快、翻得准——这正是 RAG 系统的核心挑战。

这个思路解决了裸模型的三个死穴：①知识截止——模型训练完成后世界还在变，它不知道上个月的新政策、昨天的新价格，但你的资料库可以随时更新；②不知道你的私有信息——你公司的规章制度、你家的菜谱、你的项目文档，从来不在训练数据里，但可以被索引进你的知识库；③幻觉难核对——凭参数记忆答题，你无从知道它依据什么；照资料答题，回答可以附带出处，你顺着出处就能核对原文（第六节）。日常你在各种产品里看到的"上传文件后提问""和文档对话""企业知识库问答"，底层几乎都是 RAG。

原论文的核心思想：给生成模型配一个外部记忆

RAG 这个术语来自 2020 年的论文《Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks》（Lewis et al., 2020）。它的核心思想用大众语言说：把"记住知识"和"运用知识"拆开——生成模型负责语言能力（把话说明白），一个可替换的外部检索器负责知识存储（从文档库里找相关内容），两者配合完成知识密集型任务。论文在开放域问答等任务上验证：相比纯靠模型参数记忆，配了外部检索的系统回答更具体、更准确，而且换掉检索库就能换知识——不用重新训练模型。

"换库不换脑"是这篇论文留给实践者最值钱的遗产，直接解释了为什么 RAG 成了企业知识库的事实标准：公司制度改了，更新文档库即可，不用动模型；想接入新产品线，加一个资料源即可；昨天的会议纪要，今天就能被问答——而"把知识训进模型"（微调）每改一次都要花训练成本（第四节对比）。论文里的检索器基于文本的向量表示（下一节的主角），生成器是当时的大模型；五年多过去，模型换了十几代，"检索器+生成器"的架构骨架没有变——理解了一个 2020 年的思想，就理解了今天几乎所有知识库产品的工作原理。

四步流水线：从一堆文件到能问答

无论产品界面长什么样，RAG 系统内部都是同一条四步流水线：

①收集与预处理：把资料（文档、网页、笔记、聊天记录）汇到一起，转成纯文本，去掉页眉页脚水印等噪音；
②切分（chunking）：把长文档切成小段落（常见几百字一段，段落间留少量重叠避免切断语义）——因为检索的粒度是"段"，太长找不准，太短丢上下文；
③索引（embedding + 入库）：把每一段用嵌入模型转成一串数字坐标（向量），连同原文存进向量数据库——这一步是"建图书馆的索引卡片"，只做一次，之后资料更新只需增量补做；
④检索与生成（问答时）：你的问题也被转成坐标→系统找出坐标最接近的若干段落→把"问题+这几段原文"一起交给大模型→模型照着资料作答（通常附出处）。——依据 RAG 原论文架构与主流向量数据库官方文档整理的通用流程（示例框）

记住这条流水线，你就获得了一项实用技能：知识库答得不好时，能定位是哪一步出了问题。答非所问、找错资料→多半是③索引质量或④检索数量的问题；回答缺上下文、断章取义→②切分粒度问题；资料明明在库里却说"没有相关信息"→①预处理没做好（比如关键内容锁在扫描图片里没转成文字）；资料是旧的说法→①的更新机制没跟上。第五节展开每一步的实操要点。

三、向量检索：把意思变成坐标

"报销流程"和"怎么报账"一个字都不同，坐标却紧挨着——这就是语义检索

嵌入（embedding）：每段文字一个坐标

向量检索的核心部件叫嵌入模型（embedding model）：输入一段文字，输出一串数字（比如几百到几千个），这串数字就是这段文字在高维空间里的"坐标"。关键性质是：意思相近的文字，坐标相近；意思无关的文字，坐标相距远。"公司报销流程是什么"和"出差垫付的钱怎么报账"没有任何共同的关键词，但嵌入模型会把它们放到几乎相邻的位置；而"报销流程"和"今天天气不错"的坐标则隔着十万八千里。

对比一下传统搜索就明白它的价值：老式关键词检索靠"字面匹配"，搜"报账"找不到写着"报销"的文档，是图书馆按书名笔画排卡片——你得知道确切的字才找得到；向量检索按"意思"排卡片，你随便怎么问，只要意思对得上就能找到——甚至可以用大白话问专业文档（"请假扣不扣钱"问的是考勤制度原文），语义对了，坐标就对了。这就是为什么 RAG 系统能听懂人话——你不需要学会资料库的用词习惯，资料库来适应你的问法。OpenAI 等服务商提供嵌入 API（按 token 计费，价格远低于对话模型），也有大量开源嵌入模型可以本地跑（数据不出门，第六节隐私场景常用）。

检索的质量上限：切分与上下文的工程细节

"意思相近就能找到"听起来完美，实践中却有一个大坑：切块之后，段落丢了上下文。举例（示例）：一份制度文档里有一段写着"符合条件的员工可申请补贴，标准为每月八百元"——单独看这段，"符合条件"是什么条件？在上一段里。切分把它孤立出来后，用户问"申请补贴需要什么条件"，这段的坐标和问题未必接近，可能被漏检；就算被检索到，模型拿到的也是个残缺信息。这类问题在长文档、多章节资料里非常普遍。

工程界的对策不断演进，Anthropic 2024 年提出的"上下文检索"（Contextual Retrieval）是代表性思路：入库前让大模型给每个切块补写一两句"这段在全文中的位置与背景"（比如给上例那段加上"本段出自《员工补贴制度》第三章，前文定义了申请条件为入职满一年"），再连同补充说明一起做嵌入，官方报告称能显著降低检索失败率。大众用户不需要自己实现这些——但这解释了一个选品要点：好的知识库产品会在"切分与索引"环节下功夫（智能分段、保留章节结构、给切块补上下文），而粗糙的产品只是把文件剁碎了事。评估产品时可以问一句："它对长文档的分章节处理是怎么做的？"——答不上来的，效果多半也答不上来。

四、三条路线：RAG、微调、长上下文怎么选

让 AI"懂你的资料"有三条路，绝大多数人只需要第一条

对照表：一张表想清楚三条路线

把私有知识交给 AI 有三条技术路线：RAG（资料放外部库，用时检索）、微调（用你的资料继续训练模型，把知识"焊进"参数）、长上下文（每次提问把资料整包塞进窗口）。三者不是互斥关系，但对大众用户，适用优先级非常清晰：

维度RAG（检索增强）微调（fine-tuning）长上下文直塞
知识更新改文档库即可，当天生效要重新训练，成本高周期长每次提问重新塞，无所谓更新
单次成本低（只检索相关几段）训练贵，推理便宜每次都贵（整包 token 计费）
可核对性强（回答可附原文出处）弱（知识混在参数里，无出处）中（资料都在上下文里）
适合场景知识库问答、文档助手、客服（绝大多数场景）固定风格/格式的专项任务（改变"说话方式"而非"知识"）单份长文档的深度分析、一次性任务
资料量级几十页到百万页都行需要成规模的训练样本受窗口限制，几份文档以内

一条经验法则："知识"问题用 RAG，"行为"问题才考虑微调，"一次性小资料"直接塞上下文。想让 AI 熟悉公司制度、产品手册、个人笔记——这是知识问题，RAG 几乎是唯一合理选择；想让 AI 稳定输出某种特殊格式或风格——这是行为问题，微调或精细提示词更对症；手头就一份三十页的合同要通读分析——直接上传塞进长上下文最省事。行业常见误区是拿微调当知识库用：花大价钱训练完，制度一改全部作废，还查无对证——这正是 RAG"换库不换脑"优势的反面教材。还有一个隐藏的第四选项值得知道：三条路线可以叠着用。成熟系统的常见配方是"RAG 为主、长上下文为辅"——检索出最相关的十几段放进窗口（窗口够大，可以多带几段保上下文），单份重点文档则整篇直塞；对风格有硬要求的场景再考虑用少量样本微调"说话方式"，知识依然走检索。理解了各路线的原理，你就能看懂产品文档里的技术选型，判断它是不是为你这类场景认真设计过的。

五、动手搭建：个人与团队知识库的四步框架

工具会换，框架不变：收集→切分→索引→问答，每一步的质量决定最终效果

工具地图：从"零门槛"到"全自建"

市面上的知识库方案按动手程度分三档（工具中立，均可按需替换）：①零门槛档——聊天产品的"上传文件对话"功能、笔记软件的 AI 问答（如笔记类产品的"和笔记对话"）、网盘的文档问答：资料拖进去就能问，适合个人、小资料量、低敏感场景；②中间档——知识库 SaaS 与办公套件的 AI 助手：支持持续同步资料源、多人共享、权限管理，适合团队；工作流工具（第11章的 n8n 等）也有现成的向量存储与 RAG 节点，可以把"新文档自动入库"接进自动化流程；③全自建档——开源向量数据库（Qdrant、Chroma 等）+ 开源嵌入模型 + 自选大模型 API 自己组装：数据完全自控，适合有技术成员、资料高敏感的团队（第12章讲过自托管的意义）。

选型三问：资料有多敏感（决定云端 SaaS 还是自托管，第六节）、谁来维护（没有专人维护的团队库会烂掉，见下下卡）、问答量多大（个人偶尔问，零门槛档足够；客服场景每天千次问答，才值得上中间档或自建）。绝大多数个人用户从零门槛档开始就是对的——先体验价值，再升级装备，和第11章"先用模板再谈定制"是同一个道理。三档之间也不必一步到位：零门槛档用熟了、资料量涨了、团队要共享了，再平移到中间档；只有当"数据必须留在自己手里"成为硬约束（行业监管、公司政策、资料本身高敏）时，全自建的投入才真正必要——它的成本不只是服务器，还有持续维护它的人。

资料质量决定效果：垃圾进，垃圾出

RAG 系统有一句铁律：检索只能找到库里有的东西，生成只能基于检索到的内容——资料库的质量就是回答质量的上限，这条定律没有任何技术能绕过。实践中最常见的四种"资料病"：①过时——库里的制度是两年前的版本，AI 言之凿凿地给出已废止的流程（比不知道更危险）；②矛盾——三份文档对同一件事说法不一，检索到哪份算哪份，回答随机漂移；③噪音——把没清理的原始文件整堆倒入：会议记录里的闲聊、文档里的修订痕迹、重复的三个版本，都在稀释检索精度；④断层——关键信息只存在于某人脑子里或聊天记录里，从没沉淀成文档，库里自然检索不到。

对应的四条治理动作（比选什么工具重要十倍）：入库前清理——去重、去噪、留最新版；入库时标注——给文档带上生效日期与适用范围，让系统能"喜新厌旧"；入库后测试——准备十个你知道答案的真实问题（第13章的"已知答案考核法"在知识库场景同样适用），跑一遍看命中率，不达标回头查四步流水线哪环出了问题（第二节的定位技能）；定期巡检——每季度清一次过期文档，重要更新当天入库。团队场景还要加一条：指定资料维护责任人——没有主人的知识库，半年后就是数字垃圾场。反过来，维护得好的库会形成正向循环：回答越准，用的人越多；用的人越多，暴露的资料缺口越清晰；缺口补上，回答更准——这正是下一卡"让知识库长在流程上"要解决的问题：把维护从"靠自觉"变成"靠机制"。

让知识库长在自动化流程上

知识库最理想的形态不是"一个你去问问题的网站"，而是自动生长的活系统——这与第11、12章的工作流和集成知识直接接轨（示例构想）：①自动入库：用工作流监听资料源（共享文件夹新增文件、会议纪要生成、邮件归档标签），新文档自动走"预处理→切分→索引"流水线入库，不靠人记得去上传；②自动引用：Agent 处理任务时（第13章），把知识库挂成它的检索工具——回答客户问题前先查产品手册、写周报前先查项目记录，让"照资料说话"成为流程默认动作；③自动保鲜：定时任务扫描库内文档的生效日期，过期自动标记或下架，并给维护人发提醒。

这样搭出来的系统，价值随时间复利：资料越全→回答越准→越多人用→用中发现的缺口又反过来驱动资料补充。反过来，"一次性倒入资料然后再没人管"的库，价值随时间衰减：资料越旧→错答越多→没人再信→彻底荒废。知识库的成败不在搭建那天，而在搭建之后的维护机制——这与第12章"上线才是开始"的运维观完全同构。

两个落地场景：个人第二大脑与团队问答台

场景一：个人第二大脑（示例）。你积累了几年笔记、几百篇收藏文章、一堆读书笔记和会议纪要，散落在三四个软件里，"我记得我写过/存过，但找不到"。知识库化之后的日常变化：写周报时问"上个月我在 X 项目上做了哪些决定"，它翻出你当时的会议纪要并附出处；读到新观点时问"这和我笔记里的哪些想法有关联"，它检索出三条旧笔记——你的旧资料从"存了就忘"变成"随问随在"。搭建路径：从零门槛档起步（笔记软件自带的 AI 问答），把三年的存量笔记导入，用十个已知答案的问题测试命中率，不合格就清理资料（去重、删过时）再来一轮。全程一个周末，零代码。要点是别贪多：第一年先只导一个软件里的笔记，把命中率调满意了再扩资料源——库小而准，远胜库大而浑。

场景二：团队问答台（示例）。三十人的团队，新人入职要花两周到处问"报销找谁、部署流程在哪、客户 A 的历史情况是什么"，老员工每天被打断十次回答重复问题。把制度文档、流程手册、项目档案（脱敏后）接入团队知识库，配两条规则：回答必须附出处、查无依据必须明说。效果的双重性要预先讲清楚：省下的时间是真实的（重复问题自助解决），维护的责任也是真实的——制度更新没人同步入库，问答台就从"帮手"变成"谣言放大器"，比没有更糟。所以团队库上线前先落实第五节说的责任人机制与自动保鲜流程，没有主人就不要上线。两个场景共同的底线：涉他人个人信息与公司机密资料，先过第六节的三道关。

六、幻觉缓解与隐私红线

RAG 让回答有据可查，但"有据"不等于"无误"；投喂资料前，先过隐私这一关

引用溯源：人工核对的抓手

RAG 对幻觉的作用要说到准确：它能显著降低幻觉，但不能根除。降低的逻辑很直白——模型照着检索到的原文回答，比凭参数记忆瞎编的依据扎实得多；但三种漏网情况依然存在：①检索错了——找到的段落本身不相关或过时，模型"忠实地"基于错误依据作答；②过度发挥——资料只说了一半，模型用参数记忆把另一半"脑补"完整，真伪混在一句话里；③综合失真——多段资料各说一点，模型拼接概括时引入偏差。所以负责任的知识库产品都提供引用溯源：回答旁边标注"依据：《员工手册》第 3.2 节"，点开能看原文。

引用溯源把"核对 AI"从不可能变成了举手之劳——这正是第13章"双通道验证"在知识库场景的落地。给你三条使用纪律：①重要结论必点出处——涉及钱、合规、对外承诺的回答，花三十秒点开引用的原文核对，别只看 AI 的转述；②警惕"没有出处的流畅回答"——资料库里查无依据时，好的系统会明说"库里没有找到"，如果它仍然对答如流，那是参数记忆在冒充知识库，可信度要大打折扣；③发现错答就修库——错答是免费的系统体检报告：顺着它定位是资料过时、切分不当还是检索失误（第二节流水线），修一处，全库受益。顺带说透一个常见困惑：为什么有时"AI 明明引用了原文，结论却还是错的"？因为引用只保证"这段话在库里存在"，不保证"这段话适用于你的问题"——制度文档常有适用范围与例外条款，检索到的可能是通用段落而漏掉了针对你情形的特殊规定。核对出处时多看引用的前后文（好的系统支持点开看整节而非孤立段落），是比"看有没有引用"更深一层的核对功夫。

隐私红线：投喂之前过三道关

建知识库的动作本质是把资料交给你选择的系统处理与存储——第12章"数据经过谁的手"的拷问在这里加倍适用，因为知识库往往是长期、批量、全量的数据托付。三道关：①分级关——给资料分敏感度：公开资料（产品手册、政策法规）随便放；内部资料（流程文档、会议记录）放可控的服务（团队版协议、可自托管）；高敏资料（个人身份信息、财务数据、未公开商业机密、他人隐私）默认不进任何云端服务，确有需要走全自建本地方案，且先做合法性判断。②脱敏关——必须入库的敏感文档，先脱敏再投喂：真实姓名换成角色（"客户A"）、证件号银行卡号打码、具体金额区间断化；《个人信息保护法》的最小必要原则在这里的操作化就是：问答用不到的个人信息，就不要让它进库。③条款关——入库前读服务方的数据处理条款：我的资料会被用于训练模型吗（要选"不用于训练"的选项或企业协议）？存储在哪、保留多久、删除后是否真删？能一键导出走人吗？

本地与云端的取舍给个大众口径：个人低敏资料，主流云端产品的便利大于风险；团队协作与内部资料，选有正式数据处理协议的服务或自托管开源方案；高敏与涉他人隐私的资料，本地化是唯一稳妥选项——开源嵌入模型+开源向量数据库+本地部署的组合已经足够成熟，成本主要是硬件与一点技术投入。最后提醒一个隐蔽泄露面：知识库的问答记录本身也是数据——你在库里问过什么，暴露了你在关注什么（薪酬？并购？裁员名单？），团队场景的问答日志同样要按敏感信息对待。

谣言粉碎：关于记忆与知识库的四个误解

误解一："接了知识库，AI 就无所不知我的资料了。"——错。检索有粒度与精度限制（第三节）：切分不当会漏检、问法太偏会找错、资料没转成文字（扫描件、图片表格）等于不存在。知识库的上限是"你放进去了什么+放进去的质量"，不是"AI 有多聪明"。

误解二："上下文窗口都一百万了，还要 RAG 干什么？"——窗口大小解决"装得下"，解决不了"每次都为整包付钱"（成本）、"中间信息利用率下降"（效果，Liu et al., 2023）和"资料持续更新"（窗口内容每次请求都要重新塞）。单份短文档一次性分析直接塞窗口；长期、大量、频繁更新的资料库，检索仍是正解——两者是互补而非替代。

误解三："RAG 有出处，就不会 hallucinate（幻觉）了。"——有出处只说明"它引用了某段资料"，不保证"引用对了、概括准了"：检索错、过度发挥、综合失真三种漏网情况都在（第六节）。出处是给你核对用的抓手，不是免检标志——重要结论永远点开原文看。

误解四："微调能让模型记住公司知识，比 RAG 更彻底。"——方向就错了：微调擅长改变模型的"行为方式"（风格、格式、专项任务），而非注入可持续更新的事实知识；OpenAI 官方文档明确提示微调不是注入最新知识的手段。制度一改就要重训、答错还查无对证——知识库场景，RAG 的"换库不换脑"全面占优（第四节）。

  • 短期记忆与长期记忆分别对应什么工程手段？"教 AI 记住"的三个实用推论是？
  • 个人第二大脑与团队问答台两个场景里，各自的关键成功条件是什么？为什么"没有主人就不要上线"？
📌 本章要点速览（一张工具表带走）：模型无状态、会话即忘，所有"记忆"都是外部工程补的；上下文窗口=有限工作台面，长上下文有成本、速度、"迷失在中间"（Liu et al., 2023）三重限制；RAG=开卷考试：先检索相关原文再照着作答（Lewis et al., 2020），解决知识截止、私有信息、幻觉难核对三个死穴，核心优势"换库不换脑"；四步流水线=收集预处理→切分（chunking，留重叠）→索引（嵌入成向量入库）→检索生成，答不好按步定位：找错资料查索引、断章取义查切分、说没有查预处理、答案旧查更新；嵌入=文字变坐标，意思相近坐标相近，语义检索听得懂人话；切块丢上下文的坑用"入库前补写背景"缓解（Anthropic Contextual Retrieval）；三路线口诀=知识问题用 RAG、行为问题才微调、一次性小资料直塞长上下文；工具三档=零门槛（上传即问）/中间档（团队 SaaS+工作流节点）/全自建（开源向量库+本地嵌入），选型三问=多敏感、谁维护、问答量；资料质量决定上限：四种资料病（过时/矛盾/噪音/断层）对应四条治理（清理/标注/测试/巡检），团队库必须有责任人；知识库要长在自动化上：自动入库、自动引用（挂成 Agent 工具）、自动保鲜；RAG 降低幻觉不根除（检索错/过度发挥/综合失真），引用溯源是核对抓手：重要结论必点出处、警惕无出处的流畅、错答就修库；隐私三道关=分级（高敏不上云）、脱敏（PIPL 最小必要：用不到的个人信息不进库）、条款（是否用于训练/存多久/能否删净），问答记录本身也是敏感数据。
