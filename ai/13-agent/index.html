一、Agent 是什么：从一问一答到自主循环

聊天机器人回答你的问题，Agent 完成你的任务——差别在于"循环"

一个场景看懂区别：订一场活动

假设你想组织一场三十人的团队活动（示例）。你对普通聊天机器人说"帮我策划团建"，它会给你一篇像模像样的策划文案——但仅此而已，文案里的场地是它编的，价格可能过时，你还要自己一项项去查、去订。而你对一个 Agent 说同样的话，理想流程是：它先拆解任务（查场地→比价格→看档期→发投票→订场地→发通知），然后逐步执行：调用搜索工具查场地、看到结果后决定下一步查什么、发现预算超了就换方案重查、最后把候选清单发给你确认——每一步都基于上一步的真实结果做决定。

这就是本质区别：聊天机器人是"一问一答"，Agent 是"接了任务自己转起来"。它可以自己拆解步骤、调用工具、观察结果、再决定下一步，直到任务完成或发现问题需要求助。Anthropic 在《Building effective agents》里给了一个清晰的区分：工作流（workflows）是按预定义代码路径编排的 LLM 与工具，而 Agent 是LLM 动态决定自己的流程与工具使用的系统——路线图写在模型脑子里，而不是写死在流程配置里。第11章的工作流工具是"你画好路线图，机器照着开"；Agent 是"你说目的地，机器自己找路"。

核心循环：感知→规划→行动→观察

几乎所有 Agent 系统，剥开外壳都是同一个循环：

①感知：接收任务与当前环境信息（你的指令、上一步的工具结果、相关文件内容）；
②规划：模型思考"现在该做什么"——拆解任务、选择工具、决定参数（这一步常以"思考文本"形式显式输出）；
③行动：发出工具调用请求（搜索、读文件、调 API、执行操作），由外部程序真正执行；
④观察：把执行结果送回模型——成功就带着新信息进入下一轮循环，失败就调整方案重试或换路；
⑤循环：重复②③④，直到模型判断任务完成、或达到步数/成本上限、或遇到需要人类决策的节点。——依据 ReAct（Yao et al., 2022）与 Anthropic《Building effective agents》的循环范式整理（示例框）

注意两个关键点。第一，"规划"不是一次性完成的——好的 Agent 走一步看一步，根据观察到的真实结果动态调整计划，这正是它比预定义工作流灵活的地方，也是它容易跑偏的地方（第五节）。第二，循环必须有刹车：最大步数、最大花费、超时、人工介入点，缺一个都可能变成"永动机式烧钱"。任何正经的 Agent 产品都会暴露这些刹车设置——用之前先找到它们。

Agent 不是新物种：它是"被放大的大模型"

理解了循环，还要破除一层神秘感：Agent 的"大脑"就是第1章讲过的大语言模型，没有任何魔法。它的所有能力上限与缺陷，都继承自底层模型——模型会幻觉，Agent 就会基于幻觉的"观察"做决策；模型的上下文窗口有限，Agent 跑长任务就会"忘前忘后"（第14章的记忆机制正是为此而生）；模型不理解你的真实意图时，Agent 会勤勤恳恳地把错误的任务执行得很彻底。

Agent 相对于裸模型的增量，来自三样"外挂"：工具（让它能查实时信息、能操作软件，突破"只会生成文字"的局限）、循环（让它能多步推进，突破"一问一答"的局限）、记忆（让它能跨步骤跨会话保持信息，突破上下文窗口的局限——第14章细讲）。Anthropic 把最基础的组合称为"增强的 LLM"（augmented LLM）：模型+检索+工具+记忆，这是所有 Agent 系统的积木原点。记住这个视角，你就不会被营销话术带节奏：评估任何 Agent 产品，先问它的模型是什么、工具接了什么、刹车怎么设、错了谁兜底。

二、工具调用：AI 是怎么"动手"的

模型从不亲自执行任何操作——它只是"下单"，执行和兜底都在模型之外

function calling 原理：一次"下单-上菜"的接力

"AI 能操作电脑了"听起来很玄，机制其实朴素。以 OpenAI 的 function calling 与 Anthropic 的 tool use 为例（两家官方文档口径一致），一次工具调用是四步接力：①开发者在请求里附上一份"工具菜单"——每个工具的名称、用途说明、参数格式（比如 get_weather：输入城市名，返回天气）；②模型读到你的问题后，如果判断需要用工具，就输出一段结构化的调用请求（"调用 get_weather，参数：杭州"）——注意，模型只输出这段文本，它自己并不执行任何操作；③外部程序（你的应用、工作流工具、Agent 框架）解析这段请求，真正去执行——调 API、查数据库、跑代码；④执行结果被送回模型，模型基于结果生成回答，或决定下一次调用。

看清这个机制，你就握住了理解 Agent 安全性的钥匙：模型的"手"是外部程序装的，权限也是外部程序给的。模型说"我要删除这个文件"，只有当外部程序被授予了删除权限并且照单执行时，删除才会发生。所以 Agent 的安全边界不取决于模型多聪明，而取决于你给它接了什么工具、开了什么权限、设了什么确认环节——这正是第12章密钥纪律与最小权限原则在 Agent 时代的延续。

ReAct：让模型"边想边做"的奠基论文

工具调用的"怎么想"这一半，来自 2022 年的 ReAct 论文（Yao et al.,《ReAct: Synergizing Reasoning and Acting in Language Models》）。它提出的问题很实际：让模型纯推理（一步步想但不接触外部世界），容易越想越偏、编造事实；让模型纯行动（直接输出操作不解释），又缺乏规划、错了不知为何错。ReAct 的做法是把两者交替进行：模型每做一步行动前，先生成一段"思考"（Thought：我现在知道了什么、下一步该查什么），再输出"行动"（Action：调用什么工具），拿到"观察"（Observation：工具返回的结果）后继续下一轮思考。

论文在知识问答与网页操作任务上验证了这种"思考-行动-观察"交替的有效性：推理帮助模型制定和调整行动计划，行动帮助模型获取外部信息、避免幻觉式空想。今天你看到 Agent 产品界面里滚动的"思考过程/Thought"面板，血统基本都可以追溯到这篇论文。对普通用户的实用价值：选 Agent 产品时，优先选把思考与工具调用过程透明展示出来的——你能看见它每一步为什么这么做，出了错能定位到哪一步的观察或判断歪了；黑箱式"咣当一下给你结果"的 Agent，出错时你连复盘的抓手都没有。

工具生态：从各家私有接口到标准化协议

早期每家模型服务商的工具调用格式互不相同，开发者给 A 家写的工具要重写一遍才能给 B 家用。行业很快走向标准化：一方面各家 API 的 function calling 格式趋同（都是"工具名+参数 JSON 模式"的描述方式），另一方面出现了跨模型、跨应用的工具接入协议——把"有哪些工具可用、怎么调用、返回什么"定义成通用规范，让任何支持该协议的应用即插即用地接入任何工具服务。你可以把它理解为"工具界的 USB 接口"：以前每个设备配一种专属插头，现在大家都用同一种。

对大众用户的意义：Agent 的能力边界由工具生态决定。同一个模型，接上搜索工具就能查实时信息，接上日历工具就能排日程，接上代码执行工具就能算数画图，接上你公司系统的接口就能干业务活。评估一个 Agent 产品时，"它的模型多强"只是半个问题，另一半是"它能接什么工具、接工具的门槛高不高、第三方工具可不可信"——来路不明的第三方工具可能把你的数据转手送走（第12章第三节的教训在工具生态同样成立），给 Agent 装工具前，跟给自己手机装 App 一样要看清来源与权限。还有一层成本视角别忽略：工具调用不是免费的——每次调用都消耗 token（工具菜单本身占上下文，调用请求与返回结果也占），一条循环几十步的 Agent 任务，token 账单可能是单次聊天的几十倍。这就是为什么第5章的成本意识在 Agent 场景要加倍：给工具菜单"瘦身"（只挂当前任务用得上的工具）、控制循环步数上限、贵任务先用便宜模型跑通流程再换强模型提质量，都是实践中验证过的省钱手法。

三、五种编排模式：Anthropic 官方菜谱的大众版

从简单到复杂：链式、分流、并行、主管-下属、评估-改进，最后才是自主 Agent

链式与分流：最常用的两种"简单聪明"

Anthropic 在《Building effective agents》中总结的五种工作流模式，前两种最朴素也最常用。链式（Prompt chaining）：把任务拆成固定的几步，一步的输出是下一步的输入——"先写大纲→再按大纲写正文→最后校对格式"。适合能清晰拆成固定子任务的工作，好处是每一步都可以单独检查和调优，中间还能插入程序化校验（比如大纲不合格就不往下走）。

分流（Routing）：先给输入分类，再分发给不同的专门处理路径——客服场景里，先判断这是退款问题、技术问题还是投诉，然后各走各的专门提示词与工具。它的价值在于"关注点分离"：不用写一个包打天下的万能提示词（第3章讲过万能提示词往往哪头都不精），而是每类任务配一套量身定做的处理。这两种模式在第11章的工作流工具里都能直接搭出来——它们不是 Agent，是预定义工作流，但对大多数结构化任务，这就是最优解。

并行与主管-下属：人多力量大的两种组织法

并行化（Parallelization）：把任务拆成互不依赖的块同时处理，最后汇总——审一份合同，"查法律风险""查商务条款""查错别字"三路同时跑，比串行快数倍；或者同一任务跑多个独立视角再投票/合并，用冗余换可靠性。前提是子任务之间真的不互相依赖。

主管-下属（Orchestrator-workers）：一个"主管"模型在运行时动态拆解任务，把子任务派给若干"下属"模型执行，最后综合结果。它与并行化的关键区别是子任务不是预先定好的，而是主管临场决定的——比如"修改这个功能涉及哪些文件"要主管看了代码库才知道，再把不同文件分给不同下属去改。这已经半只脚踏进 Agent 领域：主管有动态决策权，但每个下属的动作范围仍然被主管框定。复杂内容生产（多章节报告）、涉及多文件的修改类任务，是这个模式的典型战场。

评估-改进与自主 Agent：循环的两副面孔

评估-改进（Evaluator-optimizer）：一个模型生成，另一个模型（或同一个模型换个角色）按明确标准评估打分、给出修改意见，生成方照意见改，循环若干轮直到达标——"写作+审稿"的内部化。适用前提是你能写出清楚的评估标准（翻译要信达雅、代码要过测试、文案要符合品牌规范），且多轮打磨确实能提升质量。这个模式在第3章"让 AI 自我检查"技巧的规模化版本。

自主 Agent（Autonomous agents）：五种模式的终点——模型在开放环境里自己规划、自己调工具、自己循环，直到完成任务或触到刹车。与前四种的根本区别：前四种的流程图是你画的，自主 Agent 的流程图是它自己临场走的。Anthropic 对它的评价很清醒：Agent 适合步骤数无法预先确定、需要模型自己决策的开放性任务，代价是成本更高、错误会随步数累积、需要沙箱与人工兜底等防护措施。模式对照一张表：

模式流程谁定典型场景成本/风险
链式你（固定步骤）大纲→正文→校对低
分流你（固定分支）客服问题分类处理低
并行化你（固定拆分）多角度审查、批量处理中
主管-下属主管临场拆多文件修改、多章节报告中高
评估-改进你（固定循环）翻译润色、按标准改稿中
自主 Agent模型自己走开放性研究、探索式任务高（需刹车+兜底）

官方忠告：从最简单的方案开始

《Building effective agents》开篇就给所有跃跃欲试的搭建者浇了一盆清醒的冷水，值得原文级转述：很多框架把 Agent 系统做得层层抽象，隐藏了底层提示词与响应，让调试更难，也诱使开发者过早采用复杂结构；建议先直接、透明地用模型 API，从最简单的方案开始——很多场景根本不需要 Agent，单次调用+检索+上下文示例就够了；只有当简单方案确实遇到瓶颈时，才考虑更复杂的模式，而且每加一层复杂度都要换来可衡量的收益。

选型口诀（大众版）：
一次问答能解决 → 直接用聊天（配好提示词）；
缺你的资料 → 加检索（第14章知识库）；
步骤固定 → 链式/分流工作流（第11章工具）；
步骤不固定但边界清楚 → 主管-下属或评估-改进；
真正开放、需要临场决策 → 才轮到自主 Agent，且必须配刹车与人工兜底。——依据 Anthropic《Building effective agents》"find the simplest solution possible"原则整理（示例框）

这个忠告背后是工程现实：复杂度每加一层，调试难度、成本、失控面都跟着涨。而"能用简单工作流不要上 Agent"恰恰是 2023 年 AutoGPT 式狂热退潮后行业沉淀下来的共识——当年无数人试图用全自主 Agent 做一切，最后发现大部分任务用一条确定性流水线做得又快又稳。

四、单 Agent 与多 Agent：一个人干还是组队干

多 Agent 不是"更强"的同义词——协调开销是真实的成本

多 Agent 的诱惑与代价

既然一个 Agent 能干活，那组一支"Agent 团队"——一个当产品经理、一个当工程师、一个当测试员——是不是更强？这是近年产品与研究的热门方向，逻辑上有真实收益：角色分工让每个 Agent 的提示词更聚焦（第3章：专注单一角色的提示词质量更高）、可并行（独立子任务同时推进）、可互相检查（一个干活一个审核，评估-改进模式的组织化）。研究团队公开的多 Agent 系统演示过让多个 Agent 分头调研再汇总产出报告的玩法，效果亮眼。

但代价同样真实，核心是协调开销：Agent 之间靠自然语言传递信息，每一次转述都可能丢失细节、引入歧义——人类团队开会对齐要花的时间，Agent 团队一样要花，而且花的是 token（真金白银，第5章）；任务分配本身需要决策（谁干什么、干到什么程度算完），这个决策错了全队跟着歪；两个 Agent 对同一事实各执一词时，还得有仲裁机制。经验规律：子任务之间依赖越少、接口越清晰，多 Agent 越划算；任务本身揉成一团、需要频繁来回对齐的，单 Agent 带一套好工具往往又快又省。"主管-下属"模式（第三节）正是折中方案：动态分工，但信息都经主管汇总，减少横向扯皮。

Agent 简史：从狂热到工程化，普通用户能学到什么

回顾这几年 Agent 的公众形象变迁，本身就是一堂预期管理课。第一波（2023 年）是"全自主狂热"：AutoGPT 等开源项目在网络上爆红，演示视频里 AI"自己给自己派任务"，一夜之间"AGI 已来"的说法满天飞。但大量跟进者很快发现：真实使用中这些系统频繁原地打转、反复做无效尝试、token 烧得飞快，任务完成率远低于演示印象——AutoGPT 官方文档后来也坦率地把这类项目定位为实验性平台，强调需要谨慎配置与人工监督。狂热的教训：演示视频是精心挑选的最好情况，不是日常使用的平均情况。

第二波（2024 年起）是"工程化回潮"：行业话语从"全自主 AGI"转向 Anthropic 式的冷静框架——承认 Agent 有用，但强调简单优先、模式化编排、沙箱测试、人工兜底；学术界同步建起 WebArena、SWE-bench 等严肃基准，用可复现的考试代替感觉良好的演示；产品形态也从"放养式全自动"收敛为"有边界的自主"：编码助手在明确仓库里修明确问题、研究助手在限定资料库里做调研、浏览器 Agent 在受控环境里完成结构化操作。对普通用户的启示很直接：看 Agent 产品别听它"能自主做什么"，要看它"在哪里被约束"——权限怎么裁、刹车怎么设、过程给不给看、错了怎么回滚。约束设计得越认真的产品，反而越值得托付。

五、可靠性现实：评测分数与真实世界的距离

看懂基准测试的口径，才不会被"成功率 80%"之类的宣传误导

评测基准怎么说：分数背后的口径

Agent 能力如何量化？学术界的做法是建标准化测试环境：WebArena（Zhou et al., 2023）搭了一套仿真的网站群（购物、论坛、办公系统），让 Agent 在里去完成真实风格的任务并统计成功率；SWE-bench（Jimenez et al., 2023）收集真实开源仓库的历史问题单，测 Agent 能否写出修复代码并通过项目原有测试。这些基准的价值在于可比性——所有系统在同样题目上考，分数才有意义。

但读分数要懂口径，三条提醒：①测试环境≠真实世界——基准里的任务边界清晰、工具集固定、环境可重置，而你的真实任务往往信息不全、系统时有抽风、做错了不能一键撤销；②分数会过时——新一代模型发布后旧基准分数普遍上移，2023 年"最强系统"的成功率放今天可能平平，看评测一定注明时间（本章口径截至 2026 年 10 月）；③单步成功率与全链路成功率是两码事——这是下一卡的主题，也是 Agent 可靠性最反直觉的一点。

错误累积：长任务的乘法效应

做个小学算术就明白 Agent 为什么"演示很惊艳、长任务拉胯"。假设一个 Agent 每一步的决策正确率高达 95%——已经相当优秀——那么一条需要 10 步的任务，全程不出错的概率是 0.95 的 10 次方，约 60%；20 步的任务，只剩约 36%；50 步的任务，不足 8%。这就是错误累积：单步可靠性再高，也扛不住长链路的乘法。更糟的是 Agent 的错误不是独立事件——第三步基于第二步的错误观察做了决定，后面步步都在错误的地基上施工，越走越远。

Anthropic 在官方文章里对此直言不讳：Agent 的灵活性以更高的成本和错误累积为代价，建议在开始规模化之前先在沙箱环境里充分测试。工程界的应对思路你也可以拿来评估产品：把长任务切短（每完成一个里程碑就停下来让人确认，等于把 0.95 的 50 次方拆成十段 0.95 的 5 次方）、关键步骤加检查点（做之前先复述"我打算干什么"等你点头）、可回滚设计（改文件先备份、发消息先进草稿箱）、失败报警（连续失败就停下来叫人，而不是硬着头皮继续）。一个 Agent 产品有没有这些设计，比它宣传的模型多强更能决定你的真实体验。

幻觉进入循环：比单次回答错误更麻烦的事

第1章讲过大模型的幻觉问题：它会一本正经地编造不存在的事实。在单次问答里，幻觉的代价是你收到一条错误信息，核对后识破即可。但在 Agent 的循环里，幻觉会被"行动"放大：模型幻觉出一个不存在的文件路径→尝试读取失败→它可能基于"失败"这个观察推理出更歪的结论（"文件被删了？那我重建一个"）→在幻觉的地基上继续施工。工具返回的真实观察本可以纠偏（这是 ReAct 论文强调行动价值的另一面：真实世界的反馈能戳破空想），但纠偏的前提是模型正确解读观察结果——而解读本身又是一次模型推理，仍可能出错。

对使用者的三条防护建议：①让 Agent 的关键结论"有据可查"——要求它在产出里附上信息来源（查了哪个网页、读了哪个文件），你抽查其中两三条，比通读全文效率高得多；②对"它说它做了"保持警觉——Agent 报告"已完成发送""已删除旧版本"时，去真实系统里核对一眼，报告与事实不符是循环系统最常见的静默故障；③高危决策要求双通道验证——涉及钱、数据、对外承诺的结论，让 Agent 给出证据链，人沿证据链独立复核（第14章的引用溯源机制就是为这个场景设计的）。一句话总结：幻觉在聊天框里是错误答案，在行动循环里是错误行为的起点——这正是 Agent 场景比聊天场景更需要人工兜底的根本原因。

人工兜底：给自主性划定安全区

基于错误累积的现实，负责任的使用方式不是"不用 Agent"，而是按后果的严重程度给操作分级，后果越重，人工介入越深。一个可直接套用的三级分级（示例模板）：

🟢绿灯区（可全自动）：只读操作与可逆操作——查资料、做摘要、生成草稿存进文档。错了没有实际损失，放手让 Agent 跑；
🟡黄灯区（先审后发）：对外可见但可补救——发邮件、发群消息、发布内容、修改共享文档。Agent 准备好一切，人过目后再发出去（对外发布 AI 生成内容记得按《标识办法》履行标识义务）；
🔴红灯区（禁止自动执行）：不可逆或涉钱涉权——支付、删除数据、签署文件、修改权限、批量操作生产系统。Agent 最多准备材料和建议，执行按钮必须握在人手里。——依据"关键操作人工确认"通用安全原则整理的分级模板（示例），与第4章安全框架一脉相承

配置 Agent 产品时的落地动作：检查它有没有"执行前确认"开关并打开、给它的账号权限按红灯清单反向裁剪（不能支付的账号就干脆别绑支付方式，第12章最小权限原则）、给每次运行设成本上限。自主性是滑块不是开关——从绿灯区开始用，积累信任后再逐步放宽，永远不要一上来就把全权限交给一个你还没摸清脾气的系统。

六、预期管理：2026 年，Agent 能干什么不能干什么

不神话不贬低：按任务性质对号入座

现实图景：标准化任务可用，开放性任务需人盯

综合官方文档口径与公开评测（截至 2026 年 10 月），Agent 的现实能力版图大致是：已经靠谱的地带——边界清晰、工具成熟、结果可验证的任务：在明确代码库里修明确的 bug（SWE-bench 类任务上头部系统成绩逐年大幅提升）、按模板整理与转换数据、在给定网站上完成结构化操作（WebArena 类环境）、多源资料的调研初稿（人来定稿）。仍需人盯的地带——目标模糊、环境多变、错误代价高的开放任务：跨多系统的复杂业务流、需要理解组织潜规则的协调工作、任何触碰红灯区操作的场景。

给普通用户的三条决策建议：①用"验证成本"筛任务——结果一眼能核对的（数据转换、格式整理）放心交给 Agent，结果需要专业判断才能核对的（法律意见、医疗建议、投资决策）只让它做资料准备；②用"回滚成本"定权限——错了能撤销的给自动权，撤不回的一律人审；③把它当"聪明但没经验的实习生"——这个比喻精准匹配现状：能干活、学得快、偶尔自作聪明、必须给清楚的边界和抽查机制。实习生培养得好能成为得力助手，Agent 也一样：从窄任务开始、配好刹车、看过程而不只看结果。最后留一个动态视角：本章的能力版图是 2026 年 10 月的快照，边界会随着模型与工具的进步持续移动——去年还"需人盯"的任务类别，今年可能已经进了"靠谱地带"。所以比记住版图更重要的是掌握重新画版图的方法：每隔一段时间，用第⑧问的"已知答案小任务"重新考核一次你手头的 Agent 工具，它的进步与短板都会自己显形；你的托付程度跟着考核结果走，而不是跟着新闻标题走。

选 Agent 产品：普通用户的八问清单

市面上"Agent"字样的产品越来越多，营销话术大同小异。把本章知识压缩成八个问题，试用任何 Agent 产品前照着问一遍（示例模板）：

①过程透明吗——能看到它的思考步骤和每次工具调用记录，还是只给最终结果？
②刹车在哪——最大步数、花费上限、超时设置，能不能调？
③权限怎么给——接入我的账号时走官方授权还是索要密码？能不能只给只读权限？
④红灯区有没有拦——支付、删除、对外发送这类操作，它会自动执行还是停下来等我确认？
⑤错了怎么办——改文件有没有备份、发消息有没有草稿态、操作能不能回滚？
⑥数据去哪了——我的文件与对话内容存哪家服务器、留多久、给不给下游？（第12章的第三方转接问题）
⑦失败会报警吗——任务卡住或连续失败，它会通知我还是静默重试烧钱？
⑧用什么任务试——我有没有一个真实、低风险、结果好核对的小任务可以让它先跑？（用试用期考核它，别用演示视频的印象）——依据本章可靠性原则与第4章安全框架整理的评估清单（示例）

八问里最容易被忽略的是第⑧问。多数人对新工具的做法是"看评测、看演示、直接上大任务"，正确顺序恰恰相反：先给它一个你做过的、知道正确答案的小任务——比如让它整理一份你手工整理过的数据、调研一个你熟悉的领域。对照你已知的答案看它的过程记录，十分钟内你就能摸清它的可靠边界，比读十篇评测文章都管用。这个"用已知答案考核"的方法，与第5章讲的成本意识合在一起，构成普通用户驾驭 Agent 的两条腿：知道它会怎么错，知道错一次多少钱。这两条腿也解释了本章反复出现的选型逻辑：Agent 的价值不在"自主"这个卖点本身，而在"有约束的自主"能不能在你的具体任务上稳定兑现——约束越透明、考核越容易的产品，越值得长期托付。

谣言粉碎：关于 Agent 的四个误解

误解一："Agent 就是更聪明的聊天机器人。"——不是程度差异，是结构差异：聊天机器人一问一答即结束，Agent 有"感知-规划-行动-观察"的自主循环和真实工具调用（第一、二节）。反过来说也成立：没有循环、没有工具执行的"Agent 模式"按钮，只是营销话术。

误解二："Agent 越强，越应该什么都交给它。"——错误累积的乘法效应决定了长链路任务的可靠性天花板（第五节）：单步 95% 正确率的系统，50 步全程正确率不足 8%。越自主的系统越需要刹车、检查点与人工兜底，这不是不信任，是数学。

误解三："多 Agent 一定比单 Agent 强。"——多 Agent 的收益（分工、并行、互查）要扣掉协调开销（信息转述损耗、token 成本、仲裁机制）；子任务高度耦合时，组队反而更慢更贵更歪（第四节）。

误解四："评测分数高的 Agent 产品，我的任务它也一定行。"——基准是标准化考场，你的任务是真实世界：环境不同、工具不同、容错要求不同（第五节）。正确姿势是用你自己的真实小任务先试跑，看过程记录，再决定托付程度——别人的考卷分数，代替不了你的试用期。
