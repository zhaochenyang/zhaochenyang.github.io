一、编排是什么：给自动化当项目经理

一个工具解决一个动作，编排解决一整件事——中间差的是计划、分派、监督与异常处理

从"单点自动化"到"流程自动化"的鸿沟

假设你已经会让 AI 做单件事：把一段录音转成文字（第10章）、让浏览器自动填一张表单（第8章）、用一个工作流工具把新邮件转发到群里（第11章）。每个动作单独看都成立，但真实世界的任务几乎从来不是单个动作。"每周一早上，把上周的项目进展整理成周报发给团队"——这一句话背后是：从三个系统里拉数据、清洗格式、识别重点、写成文、检查数字、按模板排版、发送、存档，至少八个步骤，涉及四类工具，其中两步可能失败。

单点工具与完整任务之间的这段距离，就是编排（orchestration）要填的。编排这个词借自乐团：几十位乐手各擅一件乐器，但没有人负责"整体"，演出就是一场灾难；指挥不演奏任何乐器，却决定谁在什么时候进、以什么音量进、出错了怎么救回来。自动化系统里的编排层就是这位指挥——它自己不干活，它负责拆任务、排顺序、分派给合适的工具、盯进度、处理异常。你在本章要学会的，正是"当指挥"这门手艺，而不是再多学一件乐器。

编排的五项职责：计划、分派、监督、兜底、留痕

把"指挥"拆开看，编排层承担五项职责，本章后续各节正是逐项展开。①计划（分解）：把"整理周报"这种人类语言的任务，翻译成机器可执行、可验证的步骤序列——这是第二节。②分派（调度）：决定每一步交给谁（哪个工具、哪个模型、哪段脚本），以及哪些步骤可以同时跑——这是第三节。③监督（检查点）：在关键节点停下来核对结果，必要时等人确认——这是第四节。④兜底（异常处理）：某一步失败了怎么办？重试几次？降级成什么方案？彻底失败怎么回滚？——这是第五、六节。⑤留痕（可观察性）：整个流程做了什么、每步的输入输出是什么，事后能查——这是第七节。

为什么这五项缺一不可？因为自动化系统有一个和人类员工完全不同的特性：它不会"心里没底"。人类做错了事往往自己先慌，会停下来求助；自动化流程则会以同样的自信、同样的速度，把第一步的错误原封不动地放大到第八步——数据拉错了，摘要就摘错了；摘要错了，周报就写错了；周报发出去，全团队都看到了错数。编排层的每一项职责，本质上都是在给"不知疲倦但也不知情"的执行者加装人类的判断力。

工作流与 Agent：编排的两种"指挥风格"

Anthropic 在《Building effective agents》里给出了一个被业界广泛引用的区分：工作流（workflows）是"预先写好的路线图"——步骤和顺序由人提前定义，LLM 只是在每个节点上干活；Agent（智能体）是"给了目的地的自由行"——LLM 自己决定下一步做什么、用什么工具、什么时候算完成。对应到编排上，就是两种指挥风格：确定性编排（流程图固定，每步可预期，适合规则明确的重复任务）与自主性编排（把大目标交给 Agent，它自己拆步骤，适合路径无法预先穷举的开放任务）。

该选哪种？官方与学界的共识出奇一致：从最简单可行的方案开始。Anthropic 明确建议：如果预定义的工作流能解决问题，就不要上自主 Agent——因为 Agent 的灵活性是拿成本、延迟和"错误累积"换来的：每一步由模型临场决定，意味着每一步都可能决定错，而错误会沿着链条传递放大。本章第八节的周报案例就是典型：它 90% 的步骤是固定的（拉数据→清洗→套模板），只有一步需要判断（识别本周重点），正确的设计是"固定工作流为主干，把那一步交给 LLM"，而不是"让 Agent 全权负责周报"。记住这个优先级：能写死的写死，能规则化的规则化，剩下的才交给模型的判断力。

确定性编排（工作流）自主性编排（Agent）
步骤由谁定人预先定义模型运行时决定
可预期性高：每步输入输出可验证低：路径可能每次不同
成本与延迟低（只在该用模型处调用）高（每步决策都消耗推理）
适合任务高频、规则明确的重复劳动开放探索、路径无法穷举
翻车模式遇到未预料的分支会卡住（好排查）错误沿链条累积放大（难排查）

二、任务分解：粒度决定成功率

拆得太粗，机器接不住；拆得太细，管理成本爆炸——好的分解有可操作的标准

分解的终点是"原子操作"：一步一动作一验证

任务分解的标准路径是三层：大任务 → 子任务 → 原子操作。"整理周报"是任务；"收集各项目上周进展"是子任务；"调用项目管理工具的接口，拉取 10 月 1 日至 7 日状态变更的条目"是原子操作。原子操作的判定标准有三条，缺一不可：①单一动作——一步只做一件事（"拉取并清洗数据"就该拆成两步，因为清洗失败和拉取失败的处置方式完全不同）；②输入输出明确——上一步交出什么格式，这一步产出什么格式，白纸黑字说得清；③可独立验证——这一步做对了没有，不依赖后面步骤就能检查（拉到 32 条记录、时间范围对、字段齐全，即为成功）。

为什么强调"可独立验证"？因为它直接决定了排错成本。一条八步的链条如果只在终点验证（"周报看起来对不对"），一旦不对，你要在八个嫌疑人里找凶手；如果每步都有验证点，错误在哪一步发生当场就知道。这正是 Anthropic 提出的 Orchestrator-workers（主管-下属）模式的精髓：主管负责把任务拆成边界清晰的子任务分派下去，每个 worker 交付的结果都经过验收再进入下一环节——拆分的清晰度，就是验收的可能性。

任务分解四问（对任何想自动化的任务逐条过）：
① 这件事的输入是什么、从哪来、什么格式？（说不清 → 先别自动化）
② 这件事的完成标准是什么？用什么证据能判断"做对了"？
③ 中间哪几步是固定规则（写死），哪几步需要理解与判断（交给模型）？
④ 哪一步失败了代价最大？（代价最大的步骤前后，就是检查点该在的位置） 原则：分解的粒度以下一步能"独立验证对错"为准；验证不了的步骤，等于埋雷。

粒度失衡的两种翻车：太粗与太细

拆得太粗的典型症状是"步骤里藏着判断"。比如把"处理客户反馈"当成一步交给 AI：这一步里其实混着分类（是投诉还是建议）、情感判断（客户有多生气）、优先级排序（哪条要先回）、起草回复四种性质完全不同的操作。粗粒度步骤的问题不是"AI 做不了"，而是做错了你不知道错在哪一环——回复语气不对，是分类错了、情感误判了，还是起草模板选错了？无法定位就无法修复，只能整步重来碰运气。

拆得太细则是另一种病：把"打开表格→定位到 B2→输入数字→按回车"这种界面级动作逐个编排。每多一步，就多一次失败机会、多一份维护成本——目标软件改个版，二十个细步骤可能全要重写。工程上的经验法则是：分解到"每步有独立验证点、每步失败有独立处置方式"就停，再细没有收益。另外，凡是目标软件提供官方 API 或官方批量功能的（第12章），永远优先走接口而不是模拟界面点击——接口的一步，稳定胜过界面操作的十步。

给每一步写"验收标准"：自动化版的 Definition of Done

软件工程里有个概念叫 Definition of Done（完成的定义）：一个任务什么叫"做完了"，事先写清楚，不许含糊。编排自动化任务时，这个习惯价值千金。每一步的验收标准应该是机器可判定的：不是"数据看起来正常"，而是"记录数 ≥1 且每条都有日期与金额字段且金额为非负数"；不是"摘要质量不错"，而是"摘要长度在 100-300 字之间、包含全部三个指定要点关键词、不含内部代号"。机器可判定的标准才能自动执行，人工判断的标准只能靠人守着。

对 LLM 参与的步骤（摘要、分类、起草），验收标准还要多加一层：幻觉防线。具体做法包括——让模型输出时附上依据（"这条结论来自原文第几段"）、用第二个独立检查步骤核对关键事实（数字、人名、日期是否与原始数据一致）、设置"不确定就上交"的出口（提示词里明确"若原文信息不足，输出 NEED_HUMAN 而不是编造"）。这些手段的原理与局限在第1章（幻觉）和第14章（RAG 让回答有据可查）已经讲过，编排层的任务是把它们组装成流程里的固定环节，而不是指望某一次的运气。

三、串行与并行：哪些步骤排队，哪些同时跑

并行省时间，但有三笔隐藏账单——限流、冲突与排错复杂度

依赖决定顺序：先画"谁等谁"，再谈快慢

判断两个步骤该串行还是并行，只需要问一个问题：后一步的输入是否依赖前一步的输出？依赖则必须排队（先拉数据才能清洗，先清洗才能汇总），不依赖则可以同时跑。以周报流程为例："拉取 A 项目进展"“拉取 B 项目进展”“拉取考勤数据"三步互相不依赖，可以并行；"汇总三个来源"必须等三步全部完成，是汇合点。把工作流画成图，你会看到它不是一条线，而是一张有分叉有汇合的网——这正是 Anthropic 总结的 Parallelization（并行化）模式：把可独立的子任务同时分派，最后聚合结果。

并行的收益直观：三步各需 1 分钟，串行 3 分钟，并行约 1 分钟。对涉及网络请求的步骤（调接口、抓页面、问模型），并行常常是数量级的提速。但新手常忽略的是汇合点的等待逻辑：三个并行分支，两个成功一个失败，怎么办？全部作废重来，还是带着两个成功的结果降级继续？这个决定必须提前设计（见第五节的降级策略），否则流程会卡死在汇合点，或者更糟——悄悄跳过了失败的分支，交出一份缺了三分之一的"完整"周报。

并行的三笔隐藏账单：限流、冲突、排错复杂度

第一笔：限流。任何正规服务都对"单位时间请求数"设了上限（第12章讲过的速率限制），大模型 API、网站接口概莫能外。串行时每分钟 5 次请求安然无恙，改成 10 路并行瞬间变成每分钟 50 次，可能直接触发 HTTP 429（请求过多）错误——并行度不是越高越好，要对照目标服务的官方限额设计，必要时在编排层做"节流"（比如最多同时跑 3 路）。第二笔：冲突。多个并行步骤写同一份资源（同一个表格、同一个文件、同一条数据库记录）时会互相覆盖——A 分支刚写入，B 分支基于旧数据又写一次，A 的成果就没了。设计上要么让并行分支各写各的（最后汇合时合并），要么给共享资源的写入单独排队。

第三笔：排错复杂度。串行流程的日志是一条线，错误发生的位置一目了然；并行流程的日志是多条交错的时间线，"第 4 步失败"可能有三四个不同的"第 4 步"。缓解办法是给每个并行分支打上标签（分支名+序号），日志里永远带标签。三笔账单算下来，实践建议是：默认串行，只对"耗时明显、互相独立、不写共享资源"的步骤开并行，并且并行度从小开始（2-3 路）试探。省下的时间要大于多付的复杂度，这笔交易才划算。

四、人在回路：检查点怎么设

自动化不是"无人化"——把人安排在最值钱的位置上，而不是最累的位置上

human-in-the-loop：不是自动化的失败，而是自动化的设计

很多人在设计自动化时有个执念："全自动才高级，还要人参与算什么自动化？"这是对本章最重要概念的误解。人在回路（human-in-the-loop，HITL）指的是在自动化流程的关键节点，刻意保留"由人确认后才继续"的环节——它不是自动化程度不够的遮羞布，而是工程上经过反复验证的可靠性设计。理由在第1章已经铺垫过：AI 会以正常的语气犯不正常的错误（幻觉），自动化会以惊人的速度重复执行这个错误；而人的审查虽然慢，却能在错误扩散前拦住它。NIST 的 AI 风险管理框架把"人类监督"列为 AI 系统治理的核心原则之一；对普通人来说，操作版本更简单：错误代价越高的环节，越要有人在场。

一个实用的心智模型是把流程里的操作分成两档：可逆操作（生成草稿、保存到暂存区、打标签——错了能改能删）和不可逆操作（发送邮件、对外发布、支付转账、删除数据、修改线上配置——覆水难收）。可逆操作放心交给自动化；不可逆操作前面必须设人工确认点。这条线画好了，你就能同时拥有自动化的速度和人类的安全感：机器把 95% 的准备工作做完，你只负责最后 5% 的"按确认键"。

必须人工确认的操作清单（收藏级）

以下操作，无论自动化跑得多顺、你对它多有信心，都请在编排里显式设置人工确认点。这不是保守，是对"错误代价不对称"的理性应对——确认一次花十秒，出错一次可能花十天。

📋 人工确认清单：这些动作前必须有人按键

  • 资金类：支付、转账、下单购买、修改价格、批量退款——金额再小的自动支付也要设总额上限+人工审批线
  • 对外发送类：发邮件给客户/领导/全员、发社媒、发消息给外部联系人——AI 起草可以，"发送"按钮必须人按
  • 删除与覆盖类：删除文件/记录/邮件、清空数据、覆盖线上内容——先备份，再人工确认，两步都不能省
  • 发布与上线类：网站内容更新、应用发布、配置变更——自动化负责构建与检查，发布动作人来触发
  • 法律与承诺类：合同文书生成后的签署、代表公司做出的任何承诺、涉及个人信息的对外披露
  • 权限与账号类：授权第三方应用访问账号、创建 API 密钥、修改共享权限——这类操作还应遵守最小权限原则（第12章）
  • 批量放大类：任何"一次动作影响一百个对象"的操作（群发、批量改价、批量删改）——批量会把小错误放大成事故
  • 模型"自报不确定"时：流程中任何步骤输出 NEED_HUMAN / 置信度低 / 验收标准未通过——这是设计好的求助出口，不是异常

确认环节的体验设计也影响可靠性：如果每次确认都要你打开电脑登录三个系统，你很快会开始"无脑点同意"——确认点就名存实亡了。好的做法是把待确认内容推到你顺手的地方（一条消息卡片，附"通过/驳回/查看详情"），并且给确认请求设时效（24 小时未确认则流程挂起并再次提醒，而不是默认通过）。永远不要设计"超时未确认就自动放行"——那等于把人工兜底改回了全自动，还多了一层自欺。

确认点放哪：三个选位原则

检查点不是越多越好——每加一个确认点，流程就多一次等待，多到你烦了就会全部橡皮图章化。选位有三个原则。①不可逆操作之前（上节清单），这是底线，不可谈判。②错误放大点之前：流程里有些位置是"放大器"——比如"把 100 条数据的清洗结果写入正式表格"，写入前数据还有救，写入后就污染了下游一切；在放大器前设卡，一次确认保护一百条。③模型判断的第一次使用处：一条流程里如果有多步依赖同一个 AI 判断（比如分类结果决定后续所有分支），在分类完成后立刻设一个抽检点（不必全检，抽 10% 或抽关键类），比在每条分支末端各设一卡高效得多。

反过来，两种位置不该设确认点：纯可逆的中间步骤（生成草稿存到暂存区，确认它毫无意义，因为后面还要改）；以及你已连续确认了三十次、从未驳回过的步骤——这是明确的信号：要么这个确认点多余（可降级为"仅通知不等待"），要么你已经在无脑点同意（那它形同虚设，还制造虚假安全感）。定期回顾确认点的驳回率，是编排维护的重要动作：确认点的价值 = 它拦住的错误数，不是它的数量。

五、检查点与回滚：让长任务断点续跑

失败不可怕，"失败了要从头再来"才可怕——进度是要存档的

进度存档：游戏教会我们的编排原理

打过游戏的人都懂存档的价值：Boss 战打到第三阶段死了，有存档就从第三阶段重来，没存档就从第一关重打。长链条自动化面临完全相同的问题：一个跑 40 分钟的流程在第 7 步失败（网络抖动、接口超时、模型输出格式错），如果没有进度存档，你只能从第 1 步重跑——不仅浪费时间，还可能造成重复执行（前 6 步里如果有"已发送通知"这类动作，重跑就会发两遍）。检查点（checkpoint）就是自动化的存档点：每完成一个关键步骤，把"已完成到哪一步+每步的结果"持久保存；失败后从最近的检查点恢复，跳过已完成步骤，只重跑失败的部分。

设计检查点的工程要点有三条。①存什么：步骤编号、该步的输入摘要与输出结果（或输出存放位置的指针）、时间戳——足够让流程"从这一步之后"继续即可。②存在哪：本地文件、数据库或工作流工具自带的执行历史（主流工具如 n8n 会保留每次执行的完整记录，LangGraph 类框架把持久化检查点作为内置能力），原则是与执行过程分离——流程崩了，存档不能跟着崩。③多久存一次：每个"贵"步骤（耗时长、调用付费接口、有副作用）之后必存；纯粹的中间计算可以几步一存。存档本身有开销，但对长流程来说，这点开销换"断点续跑"，稳赚。

回滚：做错了怎么体面地退回去

检查点解决"从哪继续"，回滚解决"怎么撤销"。回滚设计的核心是一个问题：这一步的副作用能不能消除？能消除的（写入暂存文件、打标签、生成草稿），回滚就是删除或恢复原值，成本低；不能消除的（邮件已发出、数据已删除且无备份、转账已完成），回滚在物理上不可能，只能"补救"（发更正邮件、从备份恢复、走人工流程冲正）——这正是第四节把不可逆操作全部划入人工确认的原因：回滚能力决定自动化边界，回滚不了的步骤就不该全自动。

给普通用户的三条实操守则。①先备份后动手：任何批量修改文件/表格/数据的自动化，执行前自动复制一份原件到备份目录（带时间戳命名），这是第9章讲过的铁律，在编排层要固化为流程的第一步。②用"暂存区"模式：让自动化把结果先写到暂存位置（新文件、草稿箱、待发布队列），人工确认后再由最后一步"搬"到正式位置——相当于给所有副作用加了一道可撤销的缓冲。③写下回滚剧本：对每个有副作用的步骤，事先用一句话写清"如果这步错了，怎么撤销"；写不出这句话的步骤，说明你还没想清楚它该不该自动化。

六、超时、重试、熔断：编排层的三根保险丝

自动化不会累，也不会停——不设保险丝，它会拿着你的钱和账号跑到天荒地老

重试：对付"偶发失败"，但要有礼貌有上限

网络抖动、接口偶尔超时、模型偶发输出格式错误——自动化流程里相当一部分失败是偶发的，重跑一次就过。所以"失败自动重试"是编排层的标配。但重试有两个必须守的规矩。第一，有上限：无限重试偶发失败会变成永久卡死，常规设置是重试 2-3 次，仍失败就走"失败处置"（通知人/降级/终止）。第二，有间隔且递增：失败后立刻重试，大概率撞上同一个故障（对方服务正忙），密集重试还会加重对方负担、更容易触发限流；工程惯例是"退避"——第一次等 5 秒，第二次等 20 秒，第三次等 1 分钟，给故障恢复留时间。主流工作流工具都内置了重试次数与间隔的配置项，这是搭流程时第一批该设置的参数，而不是出事后才想起的补丁。

还有一条容易忽略的：只对"幂等"的步骤自动重试。幂等的意思是"执行一次和执行多次，结果相同"——查询数据、生成文件是幂等的，重试无害；"发送一封邮件""扣一次款""新增一条记录"不是幂等的，自动重试等于发两封、扣两次、加两条。对非幂等步骤，要么先查询"上次到底成没成功"再决定重试，要么干脆不自动重试、交给人处理。分不清某步是否幂等时，按非幂等对待。

超时与死循环检测：给"不知疲倦"装上刹车

AI Agent 类自动化有一种特有的翻车模式：死循环——模型反复尝试同一个失败的动作（页面打不开就一遍遍刷新、格式不对就一遍遍重写），或者两个步骤互相触发形成"永动机"（A 的产出触发 B，B 的产出又触发 A）。每一次循环都在消耗真金白银的 API 费用和真实存在的账号行为记录：烧钱是轻的，高频异常操作触发平台风控、导致账号受限才是重的。防御靠三根保险丝：①单步超时——任何一步执行超过预定时长（比如 5 分钟）即判失败，进入重试或失败处置；②步数/预算上限——给整个流程设"最多执行 N 步"“最多消耗 M 元"的硬顶，触顶即强制停止并通知人；③重复检测——连续 3 次执行相同动作且结果相同，判定疑似死循环，熔断停机。

这三根保险丝的共同哲学是：自动化的失败应该是"响亮的"，而不是"安静的"。宁可流程频繁地、明显地停下来找你，也不要它悄无声息地空转一夜，第二天给你一份天价账单和一个被风控的账号。与保险丝配套的是通知机制——熔断触发时必须第一时间推送给你（消息/邮件），写明"停在哪一步、为什么停、已完成到哪"，让你接手时不用从头排查。具体翻车案例与排查手册见第19章。

降级策略：主路断了走辅路，辅路断了要能说"今天不行"

成熟的编排不只有"成功"和"失败"两种结局，还有第三种：降级完成。设计流程时对关键步骤预先想好"如果它不可用，退而求其次的方案是什么"：AI 摘要服务超时？降级为"只转发原文+标注'今日摘要失败'"；某个数据源接口挂了？降级为"用昨天的数据+显著标注数据日期"；智能分类置信度低？降级为"全部进入'待人工分拣'队列"。降级的原则是保住核心功能，砍掉增强功能，并且把降级状态明确告知使用者——一份标注了"数据截至昨日"的周报，远好过一份迟迟不来、来了也不知道数据新不新的周报。

降级链的终点必须有一个诚实的兜底：全流程失败时，自动通知人"今天这事机器干不了，请你手动处理"，并附上已完成部分的存档。最糟糕的设计是失败后静默跳过——流程"成功"结束了，产物却缺斤短两，而你毫不知情。检验标准很简单：任何一天早上你没收到周报，你应该在 5 分钟内收到一条"周报流程失败，原因 X，请手动处理"的通知，而不是在开会时才发现根本没有周报。自动化的可靠性，一半来自它做对的事，另一半来自它把做错的事及时告诉你。

七、日志与可观察性：不知道它在干什么的自动化是危险的

留痕不是官僚主义，是排错、审计与信任的地基

每次执行都该回答的五个问题

"可观察性"这个词听着工程味很重，落到个人自动化上就是：流程跑完之后，你能不能回答这五个问题——①它什么时候跑的、跑了多久？②每一步的输入和输出分别是什么？③哪一步用了 AI、模型说了什么、置信度如何？④哪里出过错、重试了几次、最后是成功/降级/失败？⑤哪些动作产生了外部副作用（发了什么、改了什么、花了多少钱）？能答，流程就是可观察的；不能答，它就是个黑箱——黑箱在你需要它的时候（出错、审计、改进）一律帮不上忙。

实现成本其实很低：工作流工具自带执行历史（每次运行的每个节点状态与数据都可回看）；自建脚本则养成"结构化日志"习惯——每步一行记录"时间戳 | 步骤名 | 状态 | 关键数字"，追加写入一个日志文件即可，不需要任何专业系统。真正要提醒的是两个盲区：其一，LLM 步骤要记录完整的提示与回复（或至少回复摘要），因为模型输出是最不可预测的环节，出问题时"它当时到底说了什么"是第一手证据；其二，日志里不要留敏感明文——密码、密钥、身份证号、完整卡号绝不能写进日志（日志往往没有你以为的那么私密），记录"用了哪个凭证"即可，不记录凭证本身，这是第4章数据最小化原则在留痕场景的应用。

通知策略：什么该吵醒你，什么该默默记账

可观察性的另一端是主动通知：不是等你去查日志，而是流程在关键时刻来找你。通知设计的原则是"分级"，因为通知太多等于没有通知（你会开始无视所有弹窗）。实用的三级模板：红色——立即推送并等待处理：熔断触发、人工确认请求、全流程失败、预算触顶；黄色——每日汇总一次：降级完成、重试超限后成功、数据质量异常（如记录数骤降）；绿色——不推送，只记日志：一切正常的例行执行。判断一条消息该归哪级，就问一句："这件事如果我看到晚了三天，会有实质损失吗？"会，就是红色；不会，就往下放。

还有一个和钱直接相关的观察项：成本仪表盘。调用付费模型 API 的流程，应当在日志里累计每次运行的 token 消耗与估算费用，每周汇总看一眼。这既是第5章ROI 复盘的输入，也是死循环烧钱的最早预警——费用曲线突然翘起来，往往比任何报错都先告诉你"有流程在空转"。把"每周看一次执行统计（成功率、平均耗时、总费用、人工确认驳回率）"变成固定习惯，你的自动化就从"设完不管"升级成了"有人运营"。

八、完整案例：每周周报自动化流水线

把本章全部概念装进一个流程里——示例场景，工具仅为示意，可按自己的技术栈替换

案例背景与流程总图（示例）

场景（示例）：你是三人小团队的负责人，每周一上午要向部门提交上周周报。手动做法是：翻项目管理工具里的任务状态、翻聊天记录里的关键结论、翻日历里的会议记录，然后拼成文档，耗时约 90 分钟且经常漏事。自动化目标：机器把 90 分钟压到"你花 10 分钟审核确认"。按第二节的分解四问过一遍：输入=三个系统的上周数据（格式明确）；完成标准=周报草稿包含全部项目条目、数字可溯源、格式符合部门模板；固定规则步骤=拉数据/清洗/套模板，判断步骤=提炼"本周重点与风险"；代价最大的一步=发送给部门（不可逆、对外）。

周报自动化编排图（示例，工具可替换）：
第0步 备份与预检：确认三个数据源凭证有效；创建本次执行的日志文件
第1步 并行拉数（并行×3，各自幂等可重试）：①项目管理工具接口拉上周任务变更 ②日历接口拉上周会议清单 ③聊天记录接口拉指定群的关键消息
第2步 汇合校验：三路结果齐了吗？每路记录数正常吗？——任一路失败：重试2次（退避）→仍失败则降级：用可用数据继续，周报头部标注"本期缺 XX 数据源"
第3步 清洗归一（固定规则）：统一日期格式、去重、按项目分组
第4步 AI 提炼（模型判断步）：提示词要求"从以下条目提炼本周三大重点与两大风险，每条附来源条目编号；信息不足则输出 NEED_HUMAN"；验收标准：重点≤3条、每条有编号、无编造条目
第5步 套模板生成草稿：填入部门周报模板，存到草稿区（不是正式位置）
第6步 人工确认（红色通知，推送到你手机）：附草稿全文+AI 提炼的"待核对数字"清单；你的动作：改/批注/通过；超时24小时→再次提醒，绝不自动发送
第7步 发送与存档（仅在你点"通过"后执行）：发邮件给部门；把终稿与全部日志归档到指定文件夹
保险丝：全流程步数上限30、API预算上限（示例：2元/次运行）、单步超时5分钟、连续3次相同错误熔断 对照本章概念：分解到可验证（第2节）、并行+汇合降级（第3、6节）、判断步验收标准+NEED_HUMAN 出口（第2节）、暂存区+人工确认（第4、5节）、备份先行（第5节）、三根保险丝（第6节）、全程日志+红色通知（第7节）。
📘 权威手册📋 学术研究来源：Anthropic《Building effective agents》（英文，本案例采用的"工作流为主干+单点模型判断"设计即官方推荐的 Prompt chaining/Parallelization 组合） · n8n 官方文档（英文，此类定时+并行+人工确认流程在可视化工作流工具中的实现口径）

案例的三个设计决定，和它们防住的事故

决定一：AI 只放在第4步，而不是让 Agent 全程负责。防住的事故：Agent 自主决定"怎么拉数据、要不要发"意味着每次执行路径都可能不同，某天它可能自作主张跳过校验直接发送。把模型限制在"提炼重点"这一个可验收的环节，其余全部写死——这正是第三节对照表里"确定性编排为主"的落地。决定二：草稿先进暂存区，发送必须人按。防住的事故：AI 把"上周无重大风险"提炼错了（实际有），或者数据源拉到旧数据——草稿制让你在第6步拦住，而不是部门领导替你发现。决定三：缺数据源时降级继续+显著标注，而不是整体失败。防住的事故：某个接口周一早上恰好维护，全流程罢工，你连"有 2/3 数据的半成品"都没有，只能手写全份——降级版本至少帮你省了 60 分钟。

最后是投入产出的诚实账（呼应第5章）：搭建这条流程大约需要一个周末的学习与调试时间（假设你从零开始学工作流工具）；运行成本每次约几毛到几元（模型 API 费用，示例估算，以官方定价为准）；每周节省约 80 分钟。大约一个月收回搭建时间成本，之后是净赚——但前提是你按本章的规矩把检查点和保险丝配齐，否则一次"自动发错周报"的事故，损失的就不是时间能衡量的了。编排的全部手艺，说到底就一句话：让机器干机器擅长的（重复、并行、不知疲倦），让人干人擅长的（判断、核对、承担责任）。

九、谣言粉碎：编排三误区

三个流传很广的说法，都经不起官方文档与工程实践的检验

谣言粉碎：关于任务编排的三个想当然

误区一："全自动、无人参与，才是自动化的终极形态"

恰恰相反——NIST 的 AI 风险管理框架把人类监督列为治理核心，OWASP 把"过度代理"（Excessive Agency，给 AI 过大权限与自主度）列为大模型应用的头号风险类别之一，Anthropic 的官方工程指南通篇在讲"怎么给 Agent 加约束"。业界最成熟的自动化系统（从飞机自动驾驶到工厂流水线）无一例外保留人类监督环节，差别只在监督的密度。"无人化"不是目标，"人只出现在最值钱的位置"才是。一个仍需你按三次确认键、但每次只花你十秒的流程，比一个"全自动"但你不敢用的流程，自动化程度高得多。

误区二："步骤拆得越细，自动化越可靠"

拆细的收益在"可验证"，拆细的成本在"每步都是一次失败机会+一份维护负担"。界面级的碎步骤尤其脆弱：目标软件一改版，几十个碎步骤集体失效。正确的标准不是"越细越好"，而是第二节给出的判据：拆到每步有独立验证点、每步失败有独立处置方式就停；并且凡是官方接口能一步完成的，绝不模拟界面点十步。

误区三："流程搭好跑通了，就一劳永逸了"

自动化流程活在一个变化的环境里：接口会改版、限流会调整、模型会更新（输出风格与格式可能随之变化）、你的业务模板也会换。"上周还好的流程这周悄悄失效"是常态而非意外——这正是第七节要求可观察性与每周巡检的原因。把自动化当"宠物"养（定期看执行统计、看驳回率、看费用曲线），而不是当"家具"摆。行业里有个说法：自动化坏得比你发现得快——除非你设计了让它"响亮地失败"的机制。
