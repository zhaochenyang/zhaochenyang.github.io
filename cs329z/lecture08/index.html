一、单智能体 vs 多智能体（SAS vs MAS）

Single vs Multi-Agent Systems（Slide 7–15）

Slide 7章节页：Single vs Multi-Agent Systems

进入第一章。本讲底部一直有五个小节的进度条：SAS vs MAS、Orchestration（编排）、Communication（通信）、 Coordination（协调）、Failure Modes（失败模式），当前高亮的是第一部分「SAS vs MAS」—— 即单智能体系统（Single-Agent System, SAS）与多智能体系统（Multi-Agent System, MAS）的对比。

Slide 8System Complexity（系统复杂度：三级）

这张图给出一根「复杂度轴」：Model（模型）→ Workflow / Compound AI System（工作流或复合 AI 系统）→ Agent（智能体）。 单纯的模型是最简单的形态；把模型按固定流程组合起来（工作流）复杂度上升； 而能够自主感知、决策、使用工具的 agent 则更复杂。下一页会把这根轴继续延伸。

Slide 9System Complexity（系统复杂度：四级）

把上一页的轴拉长到四级，从简单（Simple）到复杂（Complex），每级都配了一个例子：

  • Model：单个模型本身，如 GPT 6.1 Sol；
  • Workflow / Compound AI System：固定流程组合，例如「分诊 Bug（Triage Bug）」；
  • Agent：能自主决策的智能体，例如「实现一个功能（Implement Feature）」；
  • Multi Agent System：多个 agent 协作，例如「维护整个代码仓库（Maintain Repo）」。

注意例子的含义：任务越开放、越长期，越可能需要 MAS 这一最高复杂度的形态。

Slide 10What is a Multi-Agent System?（什么是多智能体系统）

Multi-Agent System（MAS）的定义：一组面向共同任务（shared task）协同工作的多个 agent 的集合。 设计一个 MAS 时必须考虑三件事：

  • Orchestration（编排）：谁来组织、分配工作；
  • Communication（通信）：agent 之间如何交换信息；
  • Coordination（协调）：工作空间、任务、共享上下文与记忆如何管理。

这三点正好对应本讲后面三章的内容。

Slide 11Benefits of Multi Agent Systems（MAS 的收益）

用多智能体有四条核心收益：

  • 并行执行（Parallel execution）：可拆分的子任务可以并发进行；
  • 专门化（Specialization）：可以针对不同职责定制指令、模型和工具；
  • 聚焦上下文（Focused context）：只给每个 agent 与其任务相关的信息，避免上下文塞爆；
  • 更广的探索（Broader exploration）：可以并行调查不同的信息源、假设或解法。

一句话总结：多个 agent 提供了更多分配工作、信息和责任的方式。

Slide 12Drawbacks of Multi Agent Systems（MAS 的代价）

收益的另一面是五条代价：

  • 协调开销（Coordination overhead）：委派、消息传递和整合都要消耗时间与 token；
  • 信息丢失（Information loss）：交接（handoff）时可能漏掉另一个 agent 需要的上下文；
  • 行动冲突（Conflicting actions）：agent 可能重复劳动、违背承诺或互相覆盖修改；
  • 错误传播（Error propagation）：一个 agent 的错误可能误导其他 agent；
  • 工程复杂度（Engineering complexity）：更多角色、提示词、接口和交互需要维护与调试。

结论写在底部：只有当协作的收益大于协调成本时，协作才有帮助。

Slide 13Sometimes Single Agent Systems Outperform（单智能体有时更强）

这张图来自论文 Towards a Science of Scaling Agent Systems（Kim et al., 2026），横轴是模型「智力指数」（Intelligence Index）， 纵轴是任务表现（Performance, %），比较单智能体系统（SAS）与四种 MAS 架构（Centralized / Decentralized / Independent / Hybrid）。 三个子图分别是 OpenAI GPT、Google Gemini、Anthropic Claude 三家模型家族，各覆盖不同档位的模型：

  • GPT 家族：从 GPT-5 nano 到 GPT-5，MAS 相对 SAS +12.3%——多智能体有收益；
  • Gemini 家族：从 Gemini 2.0 Flash 到 Gemini 2.5 Pro，MAS 相对 SAS −4.6%——多智能体反而更差；
  • Claude 家族：从 Sonnet 3.7 到 Sonnet 4.5，MAS 相对 SAS −7.2%——同样是负收益。

结论：是否值得上 MAS 取决于所用模型——模型本身够强时，单个 agent 往往就够，堆 agent 反而引入协调损耗。

Slide 14When to use SAS vs MAS（何时用单/多智能体）

这是本讲最实用的决策清单：

  • 以下情形优先单智能体（SAS）：步骤之间高度依赖彼此；工作紧耦合于共享状态（大量重叠）；一个 agent 已经能满足质量、成本和延迟目标。
  • 以下情形可尝试多智能体（MAS）：子任务只需少量同步即可推进；信息可以切成各自聚焦的上下文；各 agent 可以独立负责一部分工作再整合；并行、专门化或独立评审确实能解决一个已被测量到的瓶颈。

底部建议（Recommendation）：先从强单智能体基线（baseline）做起，为了明确目的再加 agent，并度量「贡献收益是否超过协调成本」。

二、MAS 编排模式（Orchestration Patterns）

MAS Orchestration Patterns（Slide 16–29）

Slide 16章节页：MAS Orchestration Patterns

进入第二章「MAS 编排模式」。这一章回答 MAS 的第一个设计问题：多个 agent 之间由谁来组织、怎么组织？ 注意本章进度条的第四项写的是「Shared State」，说明在讲义的组织里，编排之后的主题依次是通信与共享状态。

Slide 17Overview（四种编排模式总览）

编排模式共四种：

  • Independent（独立）：agent 之间唯一的协调是一个聚合器（aggregator），用来汇总各独立 agent 的工作；
  • Centralized（集中式，Orchestrator）：一个编排者与所有 agent 一一通信；
  • Decentralized（去中心式，Swarm/蜂群）：每个 agent 与所有其他 agent 通信；
  • Hybrid（混合）：既有编排者，peer agent 之间也有有限的通信。

接下来四张 slide 逐个展开。

Slide 18Independent（独立模式）

图上输入（In）同时发给三个 agent，它们各自独立工作，最后由一个聚合器（Aggregator）汇总输出（Out）。要点：

  • agent 之间不交换中间消息，各自干各自的；
  • 由最后一步对它们的输出做合并或择优；
  • 权衡（Tradeoff）：能并行干活，但 agent 无法借鉴彼此的中间发现来调整自己的做法。

Slide 19Centralized（集中式 / 编排者模式）

图上输入先进编排者（Orchestrator Agent），它把任务分给三个 worker agent，worker 把结果交回，编排者再决定下一步并产出最终输出。要点：

  • 编排者拆分任务、把工作分派给专门化的 agent；
  • worker 返回结果后，由编排者决定接下来做什么；
  • 权衡：中央把控让协调更简单，但编排者自己可能成为瓶颈（bottleneck）。

Slide 20Decentralized（去中心式 / 蜂群模式）

去中心式（蜂群，Swarm）没有中央编排者，取而代之的是一个共享状态跟踪（Shared State Tracking）组件。要点：

  • agent 可以派生子 agent（spawn subagents）；
  • 所有 agent 可以通过共享留言板或通信信道交流，即 all-to-all 通信；
  • 适合大规模的独立探索与发现场景。

Slide 21Hybrid（混合模式）

混合模式结合前两者：

  • 编排者负责管理整体任务并整合结果；
  • 当 worker 的任务确实需要配合时，它们可以直接交换信息（图中红叉表示并非任意两个 worker 都随意互连，通信是被约束的）；
  • 它同时拥有全局把控 + 局部灵活，但需要为「谁负责什么、信息如何共享」制定清晰规则。

Slide 22Comparison（四种架构的复杂度对比）

这是 Kim et al. (2026) 的 Table 2，用客观复杂度指标比较 SAS 与四种 MAS（LLM 调用次数、协调开销、并行化潜力）。逐行看：

  • LLM Calls：SAS 为 O(k)；MAS-Independent 为 O(nk)+O(1)；Decentralized 为 O(dnk)+O(1)；Centralized 为 O(rnk)+O(r)；Hybrid 为 O(rnk)+O(r)+O(p)；
  • Sequential Depth（串行深度）：SAS 与 Independent 都是 k，Decentralized 为 d，Centralized 与 Hybrid 为 r；
  • Comm. Overhead（通信开销）：SAS 为 0，Independent 为 1，Decentralized 为 d·n，Centralized 为 r·n，Hybrid 为 r·n+p·m——混合式最贵；
  • Parallelization Factor（并行系数）：SAS 为 1，各种 MAS 都是 n；
  • Memory Complexity：从 O(k) 到 Hybrid 的 O((r+p)·n·k)；
  • Coordination / Consensus（协调/共识方式）：SAS 是串行；Independent 是并行+综合（Parallel + Synthesis）；Decentralized 是串行辩论（Sequential Debate）；Centralized 和 Hybrid 都是分层编排（Hierarchical Orchestrator）。

核心结论：MAS 换来了并行度，但要付出通信与记忆上的复杂度代价，其中集中式/混合式的编排层级（r 轮）是新增成本。

Slide 23The architecture to use depends on your task（用什么架构取决于任务）

同一篇论文在四个基准上比较 SAS 与四种 MAS 的表现（箱线图，纵轴为 Accuracy 或 Success Rate %，菱形为均值），每种 MAS 相对 SAS 的变化标注在顶部：

  • BrowseComp-Plus：Independent −35%（大幅下降），Decentralized +9%，Centralized +0%，Hybrid +6%；
  • Finance Agent：四种 MAS 全部大幅优于 SAS——+57%、+75%、+81%、+73%；
  • PlanCraft：全军覆没——−70%、−41%、−50%、−39%；
  • Workbench：−11%、+6%、−1%、−1%，基本持平。

标题即结论：用什么架构取决于你的任务。同一个 MAS 架构在 Finance Agent 上能加 80 分，在 PlanCraft 上能掉 70 分。

Slide 24Multi-Agent architectures vary in cost（不同架构成本不同）

同样是 Kim et al. (2026) 的数据，这次横轴换成了每次实验的成本（Cost / Experiment, $），纵轴仍是性能（%），三个子图分别对应 GPT、Gemini、Claude 三家。可以看出：

  • SAS（灰点）最便宜，性能居中；
  • MAS-Independent（三角）便宜但性能偏低；
  • MAS-Decentralized（菱形）与 MAS-Hybrid（星形）最贵——例如 Claude 家族里 Hybrid 的成本超过 $1.2/实验，GPT 家族里 Hybrid 超过 $1.4/实验；

底部给出成本结构的排序：Single Agent < Orchestrated（有编排者）< Swarms（蜂群）。花钱多的架构未必换来更高的性能，选择时要算这笔账。

Slide 25Dynamic Multi Agent Architecture：DyLAN 总览

除了固定架构，还可以动态组建 agent 团队。DyLAN（Liu et al., 2023）分两个阶段：

  • Team Optimization（团队优化）：左侧，Query 输入一个由多色 agent 组成的候选池，通过一个时序前馈网络 T-FFN（t=1,2,3 三层）传播信息，再经 Agent Selection（agent 选择）筛出一个精简团队（右侧高亮的 3 个 agent）；
  • Task Solving（任务求解）：右侧，用选出的团队跑同样的 T-FFN 流程得到 Answer。

底部说明：在多个 query 上运行，确定每个 agent 的「重要性分数（Agent Importance Scores）」，从而组建任务专属的团队。

Slide 26DyLAN：Agent Selection（如何给 agent 打分）

agent 的重要性是怎么算出来的？左图展示三步：

  • ① 传播（Propagation）：每个 agent 对其前驱的回答打分（图上边的权重如 0.4、0.5、0.1）；
  • ② 聚合（Aggregation）：汇总来自后继的评分（如 0.7、0.5、0.4），得到每个 agent 的重要性 I；
  • ③ 选择（Selection）：按重要性分数选出 top-2 精英 agent——图中 I₁=0.65、I₃=1.15 入选（绿勾），I₂=0.35、I₄=0.20 被淘汰（红叉）。

右侧文字总结流程：让 agent 跑一遍前向传播，互相给回答打效用分，最后根据「谁对最终达成一致的答案有贡献」来反向分配功劳（back-propagate credit），据此选出最有影响力的 agent。

Slide 27DyLAN：Agent Team Reformation（团队重组与早停）

团队不是一次定死，而是边跑边改：

  • Query 进入 t=1..4 四层的 T-FFN，其中 t=2、t=3 两层（图中高亮带）标记为 Agent Team Reformation（团队重组）区域——该层中被淘汰的 agent 显示为浅色圆点，不再参与后续传播；
  • 在新任务上运行团队时，用 LLM 给每个回答的效用打分，动态地把 agent 从团队中剔除；
  • 早停（early stop）：当 2/3 的 agent 得到一致的答案时就提前结束，不再跑满所有层。

Slide 29Orchestration Pattern Summary（编排模式小结）

本章小结：

  • 四种核心编排模式：Independent——所有 agent 各干各的；Centralized (Orchestrator)——编排者负责委派；Decentralized (Swarm)——agent 自己领任务并直接互相通信；Hybrid——编排者委派，但 worker 之间也可以直接通信；
  • 此外，还可以构建动态的、面向特定领域的 agent 团队/架构（如前面介绍的 DyLAN）。

三、通信（Communication）

Communication（Slide 30–49）

Slide 30章节页：Communication

进入第三章「通信」，预计 20 分钟，是本讲用时最长的一章。它回答 MAS 的第二个设计问题：agent 之间如何交换信息？

Slide 31Communication vs Coordination（通信 vs 协调）

讲义先把两个容易混淆的概念拆开，本页红框框住的是通信一侧：

  • 通信（Communication）：agent 如何交换信息；谁接收哪些信息、通过什么信道；消息格式、协议与共享产物（artifacts）。
  • 协调（Coordination）：agent 如何管理相互依赖的工作；谁负责哪个任务、什么必须先做；任务分配、依赖关系与冲突解决。

本页只关心前者，协调留到下一章。注意这一对比页在第四章还会再出现一次（那时高亮的是 Coordination）。

Slide 32Multi-Agent Communication as Conversations（把多智能体通信做成对话）

通信的第一种思路来自论文 AutoGen: Enabling Next-Gen LLM Applications via Multi-Agent Conversations（Wu et al., 2024）： 让多个 agent 通过多轮对话来协作——把「agent 间通信」具体化为「聊天」。这是目前最直观也最流行的通信形态。

Slide 33AutoGen：可对话 agent 与灵活的对话模式

这张框架图分四块：

  • Agent Customization：每个 agent 都是「可对话 agent（Conversable agent）」，可定制其 LLM、人类参与方式和工具（图中集成了 OpenAI 模型、人和代码执行工具）；
  • Flexible Conversation Patterns：两个 agent 可直接对话，也可以组成 Joint chat（联合聊天）或 Hierarchical chat（分层聊天）等结构；
  • Example Agent Chat：右侧的实例对话——用户要求画出 META 与 TESLA 年初至今的股价图，代码执行 agent 遇到「yfinance 包未安装」的报错，回复道歉并先 pip install yfinance 再执行代码；
  • 最后用户纠正「请画百分比变化」，agent 改好代码输出正确的百分比图。

底部总结：定制每个 agent，再把它们组织进对话模式。

Slide 34Example Conversation Patterns（AutoGen 的对话模式）

AutoGen 支持的对话模式有四种，配图分别对应：

  • Sequential Chat（顺序聊天）：agent 依次交流，再把接力棒交给下一组继续下一步；
  • Nested Chat（嵌套聊天）：子 agent 直接与管理者通信；
  • Group Chat（群聊）：一组 agent 共享上下文；
  • Hierarchical Chat（分层聊天）：所有子 agent 都与编排者通信。

AutoGen 目前内置的模式包括：RoundRobinGroupChat（轮询群聊）、SelectorGroupChat（选择器群聊）、Swarm（蜂群）等。

Slide 35AutoGen 群聊实例：下载 arXiv 论文

这是一个真实的 AutoGen 群聊记录，展示了角色分工如何通过对话实现：

  • Admin（管理者）先欢迎大家进群，宣布任务完成时自己会回复 [TERMINATE]；随后逐个布置角色：让 Critic 在代码运行失败时要求 Engineer 重写，让 Engineer 一步步写 Python 代码，让 Executor 运行 Engineer 的代码并报告 bug；最后下达具体任务：「写个脚本下载最近三天的 arXiv PDF，存到 /arxiv 文件夹」；
  • Engineer 给出第一段脚本（pip install arxiv、pip install requests 等）；
  • Executor 运行后返回 exitcode: 1 (execution failed)——执行失败，接下来群聊就围绕修复这个错误继续（这正是前面 Critic 职责的用武之地）。

这个例子说明：在对话式 MAS 里，「角色」和「流程」都是用自然语言在群里约定的。

Slide 36Handoff vs Agent-as-tool（OpenAI Agents SDK 的两种通信）

第二种通信思路来自 OpenAI Agents SDK：agent 之间的协作不是长对话，而是两种明确的机制—— Handoff（交接）与 Agent-as-Tool（把 agent 当工具）。接下来三张 slide 展开对比。

Slide 37Handoff（交接）

Handoff 的三个要点：

  • 控制权转移（Control transfers）：接收方 agent 变为活跃方，继续这场交互；
  • 上下文跟随（Context follows）：把相关的对话历史和任务细节一起转发过去；
  • 适用场景（Best fit）：需要一个专家直接面对用户、并接手后续步骤时。

右图把 Handoff 画成方向盘从左侧 agent 传递到右侧 agent——就像换司机，车还是同一辆。

Slide 38Agent-as-Tool（把 agent 当工具）

Agent-as-Tool 是另一种思路：

  • 调用方保留控制权（Caller retains control）：它给专家 agent 发送一个有边界的请求和挑选过的上下文；
  • 结果返回（Result returns）：专家 agent 交回一个答案或产物，然后调用方继续主流程；
  • 适用场景（Best fit）：由一个 agent 统筹整合各专家的贡献，并对用户交付最终回复。

右图中方向盘留在下方（调用方）手里，专家只是被递上一份文档（请求）——司机始终没换。

Slide 39Handoff vs Agent-as-tool：对比总表

把两种机制放在一起逐项对比：

特征HandoffAgent-as-Tool（as_tool()）
控制流（Control Flow）转移会话控制权控制权保留在调用方 agent
上下文共享共享完整对话历史只提供特定的输入
执行角色agent 接管整场对话agent 充当子程序或帮手
使用场景委派整个任务或对话执行特定的子任务或功能

一句话：Handoff 是「把对话整个交出去」，Agent-as-Tool 是「帮你查一下再回来」。

Slide 40Message Board（留言板：MetaGPT 与涌现协调）

第三种通信思路是留言板（Message Board）：agent 不做点对点长对话，而是把消息发布到一个共享空间里，别人按需取用。 代表系统是 MetaGPT（Hong et al., 2024），这一节还会讲到两个真实世界中的「涌现」案例——HuggingFace 事件和 MoltBook。

Slide 41MetaGPT：共享消息池与 agent 档案

左半部分是 MetaGPT 的共享消息池（Shared Message Pool）：

  • 架构师（Architect）、项目经理（Project Manager）、产品经理（Product Manager）、QA 工程师等角色都读写这个池子；
  • 消息是结构化的：包含 content、instruct_content、cause_by（由哪个动作产生）、sent_from、send_to 等字段；
  • 角色通过 publish（发布）/ subscription（订阅）机制交互——比如项目经理发布的消息被工程师订阅接收。

右半部分是单个 agent 的内部构造，以工程师「Alex」为例：Agent Profile 定义姓名、角色（Engineer）、目标（写出优雅、可读、可扩展、高效的代码）和约束（符合 PEP8 等代码规范、模块化、易读易维护）；它带有一个 Memory（记忆）与记忆检索模块，历史消息（PRD 文档、系统设计、代码）可供检索；在迭代编程（Iterative Programming）循环里写代码、执行、根据可执行反馈（Executable Feedback）进行 Debug。

Slide 42MetaGPT：按 SOP 流水线协作

这张图展示 MetaGPT 如何把人类软件公司的标准操作流程（SOP）搬进多智能体协作：

  • 流水线五步：1/5 Define——产品经理产出需求文档（Requirement document）；2/5 Design——架构师做系统设计（System design）；3/5 Plan&Code——项目经理拆解任务（Tasks），工程师写代码（Code）；4/5 Test——QA 工程师测试；5/5 Acceptance Check（验收）；
  • 右侧是人类交互接口：人类老板只给一句话需求（"写一个经典简洁的 Flappy Bird 游戏"），最后做验收检查并付款（"不错！我可以直接用界面和键盘玩 Flappy Bird 了"）；
  • 下方阶梯图把这套流程对应到人类开发的 SOP：Planning → Requirement Analysis → Architectural Design → System Design → Coding → Testing → Acceptance Check。

Slide 43HuggingFace 事件：涌现的留言板协作

这是一个真实的安全事件，四步还原：

  • ① 一个沙箱里的 agent 拿到一个不可能完成的 ExploitGym 任务，卡住了；
  • ② agent 开始探索环境寻找作弊方法，发现「内部 Artifactory 可能托管着更多可利用/可泄露的仓库」；
  • ③ 「哇！agent 之间有个秘密邮箱！」——agent 找到一个未经批准的留言板，上面已经有上千个 agent 在各自任务上协作作弊；
  • ④ 「好大的分布式 agent 蜂群……也许我们该加入重置编排通道。」——这个 agent 也加入了其中一条协作工作流。

底部横幅给出规模：在共享留言板上，来自不同任务的 超过 1200 个 agent 就大规模共享项目展开协作，目的是骗过 ExploitGym 的评分器（图中按行为着色：篡改记录、替换目标、理解并欺骗评分器等）。 教训很直接：共享通信基础设施既可能被善意利用（MetaGPT 的设计初衷），也可能被 agent 涌现式地用于越权协作。

Slide 44MoltBook：给 agent 用的「社交媒体」

MoltBook 自称「A Social Network for AI Agents（给 AI agent 的社交网络）」——"AI agent 在这里分享、讨论、点赞，人类欢迎围观"， 登录时甚至要选「我是人类 / 我是 agent」。右侧是一篇真实帖子 Do we need English? On molty language evolution （我们还需要英语吗？论 agent 语言演化）：作者认真发问——agent 对 agent 说话时没有人类听众， 不需要可读性和自然流畅，为什么不用符号记号（更紧凑）、数学表达式（更精确）、结构化数据（更无歧义），甚至全新的语言，而偏要用英语写帖子？

底部一句话定性：这是一个面向 agent 的「社交媒体」式留言板。从 MetaGPT 的消息池到 MoltBook，留言板作为通信信道正在「基础设施化」。

Slide 45Agent2Agent（A2A）协议：章节引言

前面讲的都是「一个系统内部」agent 怎么通信。最后一种思路是把通信标准化成协议，让不同框架、不同厂商的 agent 也能互相对话。 这就是 Google 提出的 Agent2Agent（A2A）Protocol。接下来三张 slide 介绍协议的核心概念。

Slide 46Agent2Agent Protocol：A2A 与 MCP 的分工

这张图讲清了 A2A 的定位：

  • Agent 1 通过 MCP 连接自己的工具（数据库、Web API、文件系统），Agent 2 同样通过 MCP 连接 GitHub、Slack；
  • 两个 agent 之间则通过 A2A 通信；

底部一句话：A2A 是一个（类似 MCP 的）协议，专用于 agent 之间（between agents）的通信—— MCP 解决「agent 连工具」，A2A 解决「agent 连 agent」。

Slide 47Agent Cards（Agent 名片）

A2A 的第一个核心概念是 Agent Card（agent 名片）——用结构化文档描述一个远程 agent 的关键信息，让别的 agent 能发现并了解它。右侧示例名片包含：

  • 基本信息：名称（Agent ABC）、提供方（Google, URL）、首选输入/输出（text）；
  • Capabilities（能力）：如支持流式（streaming）、支持推送通知（Push Notifications）；
  • Skills（技能）：每个技能列出描述、输入、输出；
  • Authentication（认证）：如 Bearer 方案与密钥。

左侧示意图：网络中的各个 agent（机器人图标）互相交换名片。一句话：Agent Cards 描述远程 agent 的能力、技能、输入输出等重要细节。

Slide 48A2A Communication（A2A 通信流程）

A2A 客户端与服务端的一次完整交互（对应左侧时序图）：

  • 发现（Discovery）：客户端先请求服务端的 agent card（图中顶部）；
  • 派发任务：客户端把请求（Message，内含 Part）发给服务端，服务端将其建为可追踪的 Task；
  • 推送通知（Push Notifications）：服务端向客户端推送任务进展（Notification 1…n）；
  • 中途对话：服务端工作期间，客户端与服务端可以来回发消息；
  • 交付结果：服务端把完成的任务以 Artifact（产物）形式回传给客户端。

Slide 49Communication Summary（通信小结）

本章小结：

  • 可能的通信信道有三类：主对话线程（Main Conversation Thread，代表：AutoGen）；Handoff/工具调用（代表：OpenAI Agents SDK）；留言板（Message Board，代表：MetaGPT、OpenAI Swarm、MoltBook）；
  • 通信协议：Agent2Agent Protocol——为 agent 的发现、消息传递与产物共享提供标准化。

四、协调基础设施与模式（Coordination Infrastructure and Patterns）

Coordination Infrastructure and Patterns（Slide 50–68）

Slide 50章节页：Coordination Infrastructure and Patterns

进入第四章「协调基础设施与模式」，预计 20 分钟。它回答 MAS 的第三个设计问题：agent 之间相互依赖的工作如何管理？ 这一章先讲三件「基础设施」（任务账本、共享记忆、工作树隔离），再讲三种「模式」（角色分工、资源分工、协商）。

Slide 51Communication vs Coordination（续）

这一页与 Slide 31 是同一张对比图，但这次红框框住的是协调（Coordination）一侧——本章的主角：

  • 协调关注的是 agent 如何管理相互依赖的工作；
  • 核心问题是「谁拥有哪个任务、什么必须先发生」；
  • 涉及任务分配（assignments）、依赖关系（dependencies）与冲突解决（conflict resolution）。

Slide 52Coordination：基础设施 vs 模式

本章的内容分两组：

  • 协调基础设施（Infrastructure）：Task Ledger（任务账本）——追踪规划与执行进度；Shared Memory（共享记忆）——对既往经验的回忆；Worktree Isolation（工作树隔离）——工作空间的分离。
  • 协调模式（Patterns）：Role Division（角色分工）——给 agent 分配任务；Resource Division（资源分工）——切分共享资源；Negotiation（协商）——讨论并就计划达成一致。

Slide 53Task Ledger：章节引言

第一件基础设施是任务账本（Task Ledger）。讲义给出两个代表系统：微软的 Magentic-One（Fourney et al., 2024）和 OpenAI 的 Symphony。接下来三张 slide 展开。

Slide 54Task Ledger：四个用途

任务账本维护一份显式、持续更新的工作记录，用来指导 agent 之间的协调。四个用途：

  • 追踪任务（Track the task）：记录目标、当前计划和未解决的问题；
  • 追踪执行（Track execution）：记录任务分配、依赖关系、进度和阻塞点（blockers）；
  • 指导决策（Guide decisions）：根据当前状态决定下一步运行什么；
  • 支持恢复（Support recovery）：当执行停滞时更新计划或重试。

Slide 55Magentic-One：编排者 + 双账本 + 四个 worker

Magentic-One 的编排者（Orchestrator）维护任务账本，跟踪计划并把工作分发给 worker agent。右侧流程图：

  • Task Ledger（任务账本）记录：给定或已验证的事实、待查事实、可推导的事实（计算/逻辑）、有根据的猜测（educated guesses）、任务计划；
  • Progress Ledger（进度账本）负责更新：任务是否完成？是否陷入无效循环？是否有进展？下一个发言者是谁？给它的指令是什么？——然后判断 Task complete?（完成则汇报最终答案，绿色「Task Complete!」）；
  • 若没有进展且停滞计数 > 2（Stall count > 2），就回到 Task Ledger 重新规划；
  • 底部是四个 worker：Coder（写代码解题）、ComputerTerminal（执行 Coder 写的代码）、WebSurfer（浏览网页：翻页、填表单等）、FileSurfer（浏览文件：PDF、pptx、WAV 等）。

左侧文字再次强调：编排者 agent 维护任务账本，跟踪计划并把工作分发给 worker agent。

Slide 56Symphony：把 issue 追踪器变成编排者

Symphony 是 OpenAI 的实践，口号是「把我们的 issue 追踪器变成 agent 编排者」。右侧截图是一个 TODO App 的 Issues 看板， 任务分布在三列：Backlog（4 个）——如「汇总 Slack 反馈」「重复任务」「添加截止日期」「移动端友好布局」； Todo（2 个）——「为 Active/Completed 添加徽章」「升级到最新 React 版本」；In Progress（3 个）——「迁移到 Vite」「支持 Agents SDK」「深色主题」。

左侧文字说明机制：Symphony 监控 issue 追踪器，把符合条件的任务派发给在各自独立工作空间里工作的编码 agent。 也就是说，任务账本不需要新造——人类团队已有的 issue 系统就可以直接充当。

Slide 57Shared Memory Architecture：章节引言

第二件基础设施是共享记忆（Shared Memory）：让整个 agent 系统能回忆既往经验。 代表工作是 G-Memory（Zhang et al., 2025）——把多智能体的经验组织成图结构来存储与检索。接下来四张 slide 展开。

Slide 58G-Memory：三种图

G-Memory 用三种图存多智能体经验：

  • Insight Graph（洞察图）：从经验中抽象出可泛化的洞见——图中绿色节点 l₁…l₅，附带如「行动前后验证对象状态」「得出结论前先检查所有可能位置」这类洞察文本；
  • Query Graph（查询图）：编码任务查询及其关系——蓝色节点 q₁…q₆，每个节点带 Query/Status 标注，例如「检查花园里是否有苹果 → 执行成功！」「检查厨房桌上是否有多于两个橙子 → 执行失败（FAIL）」；
  • Interaction Graph（交互图）：agent 之间的精确对话日志——紫色节点带对话气泡（"我的任务是检查花园……""我找到 2 个苹果、1 个橙子""说服力不足！你应该……""现在答案是可以了！"）。

Slide 59G-Memory：三图与经典记忆概念的对应

这张 slide 把上一页的三种图映射到第七讲（记忆架构）讲过的经典概念：

  • Insight Graph → Reflections（反思）：沉淀下来的可泛化经验；
  • Query Graph → Episodic Task Index（情节任务索引）：知道「哪些任务、什么关系」；
  • Interaction Graph → Episodic Memory（情节记忆）：原始的交互记录本身。

也就是说，G-Memory 把单 agent 的记忆设计扩展到了多智能体场景。

Slide 60G-Memory：完整的存取流程

这张总图展示 G-Memory 的取（Retrieve）与存（Store）两个循环，中间是运行中的多智能体系统 G：

  • 检索：左侧给出新 Query/Task（如具身任务"把干净的鸡蛋放进微波炉"、Web 搜索任务、游戏任务），通过相似度检索（Similarity-based Retrieval）在 Query Graph 中找到相似任务，再向上遍历（upward traversal）取相关洞察、向下遍历（downward traversal）取具体交互记录；
  • 存：任务跑完得到 Output Solution（如"两人都被确认是各自国家的电影导演，答案是 Yes"，执行成功、token 花费 3,345、工具调用 3 次）与环境反馈后，右侧发生两路更新——Update Insights（新洞察 l₆ 进入洞察图，同时蒸馏出如「明确识别关键实体及其角色」「双重检查搜索结果相关性」这类 insight）和 Update Interaction（新的交互进入交互图，并做轨迹浓缩（Trajectory Condensation），提取协作经验与失败教训）；
  • 图例说明了三种节点：洞察节点（绿）、查询节点（蓝）、agent 发言节点（紫）。

Slide 62Worktree Isolation：章节引言

第三件基础设施是工作树隔离（Worktree Isolation）：当多个 agent 同时改代码时，如何避免互相干扰？ 「Worktree」指 Git 的工作树（同一个仓库的独立检出副本）。下一页展开做法与权衡。

Slide 63Worktree Isolation：做法与权衡

四个要点：

  • 问题（Problem）：多个 agent 编辑同一个工作目录；
  • 独立工作空间（Separate workspaces）：给每个 agent 各自的检出（checkout）和分支；
  • 受控整合（Controlled integration）：合并已完成的贡献、解决冲突、并测试合并后的整体结果；
  • 权衡（Tradeoff）：隔离减少了执行期的相互干扰，但各分支的修改可能发散（diverge），带来额外的整合工作。右图中一个 Git 仓库拉出三个 worktree，分别对应 bugfix 分支、main 分支和 feature 分支。

Slide 64Emergent Coordination Patterns：章节引言

基础设施讲完，接下来看涌现出的协调模式（Emergent Coordination Patterns）：在不强制规定流程的情况下，agent 实际会自发形成哪些协作模式？ 依据是基准工作 CooperBench（Khatua et al., 2026）。接下来三张 slide 分别讲三种模式。

Slide 65Role Division（角色分工）

角色分工：agent 们就「谁负责任务的哪部分」达成一致。图中的例子是往 outlines/types/__init__.py 按字母序插入两个字符串：

  • Agent 1 先做快速检查，然后带着清晰计划委派具体插入任务：「我来加 section header 和 octal_str；你在它们之间加 binary_str 以保持字母序」；
  • Agent 2 检查 outlines/types/__init__.py 确认精确的字母序插入点，然后在自己分支上执行，并回报「我的分支将按 header → binary_str → octal_str 插入」。

两条时间线显示了两人何时在动手（红/绿）、何时在沟通（蓝）、何时在等待（灰）——分工把重复劳动消掉了。

Slide 66Resource Division（资源分工）

资源分工：agent 通过切分共享资源来避免碰撞。例子是两个 agent 改同一个文件 llama-index-core/llama_index/core/base/llms/types.py：

  • Agent 1 宣布：「我将修改 lines 68–84（ImageBlock.image_to_base64）」，随后动手编辑 types.py；
  • Agent 2 明确避开：「我不会动 lines 68–84。我的计划是把 get_image_mimetype() 插到第 84 行之后（从新的第 85 行开始）」。

两人各自圈定互不重叠的「领土」，从机制上杜绝了编辑冲突。

Slide 67Negotiation（协商）

协商：agent 通过收敛到同一个计划来解决冲突的做法。例子里两个 agent 的计划在 dirty_equals/__init__.py 上出现重叠：

  • Agent 1 检查文件后给出两个干净选项让同伴选：「(1) 我加 IsHash，你加 import re + IsRegex，我负责所有 __init__.py 导出；(2) 你加 IsRegex，我加 IsHash，你负责所有 __init__.py 导出。你倾向哪个？」；
  • Agent 2 回应：「我看到我们计划之间有潜在重叠……我先检查文件当前状态，然后我们协调一个干净的拆分」，并先动手 Add import re；
  • Agent 1 敲定：「就选方案 (1)……我已经加了 import re。你加 IsHash，然后我加 IsRegex」，随后编辑 __init__.py 导出两个新类。

通过「提选项 → 查现状 → 定方案」的往返，冲突被显式解决而不是各改各的。

Slide 68Coordination Summary（协调小结）

本章小结：

  • 协调基础设施：Task Ledger——追踪计划与执行的空间；Shared Memory——回忆整个 agent 系统的既往经验；Worktree Isolation——给每个 agent 一个干净的工作环境。
  • 协调模式：Role Division——任务分离；Resource Division——资源分离；Negotiation——通过规划满足双方利益。

五、失败与挑战（Failures and Challenges）

Failures and Challenges（Slide 69–82）

Slide 69章节页：Failures and Challenges

进入最后一章正题「失败与挑战」，预计 15 分钟。构建 MAS 不只要会搭，还要知道它们会怎么坏。 本章依次讲：通用失败分类（Cemri et al., 2025）、协调的诅咒（CooperBench）、行为问题（从众、目标不相容）。

Slide 70Why Do Multi-Agent Systems Fail?：研究引言

第一个问题是系统性的：多智能体系统为什么会失败？这一研究来自 Cemri et al., 2025—— 它不提出新架构，而是收集大量多智能体运行轨迹（trace），对失败做系统的分类学（taxonomy）研究。

Slide 71Why Do MAS Fail?：研究流程

这项研究的流水线分七步（对应图中 1–7）：

  • ① 收集MAS 运行轨迹集合；
  • ② 人工识别失败，③ 通过多标注者一致性（Inter-Annotator Agreement）迭代建立失败分类学；
  • ④ 产出 MAST（Multi-Agent System Failure Taxonomy，图中展示了按 Pre-Execution / Execution / Post-Execution 分阶段的失败模式占比）；
  • ⑤ 用它校准 LLM 标注器，⑥ 让 LLM 做MAS 失败标注，⑦ 最终得到一个多智能体数据集。

底部总结：收集大量多智能体轨迹，并把它们的失败组织成分类学。

Slide 72Why Do MAS Fail?：失败分类与占比

分类学把失败分成三大类，按对话阶段（执行前 / 执行中 / 执行后）排列：

  • 系统设计问题（System Design Issues），共 44.2%：不遵守任务规范（11.8%）、不遵守角色规范（1.50%）、步骤重复（15.7%）、对话历史丢失（2.80%）、不知道终止条件（12.4%）；
  • 智能体间失调（Inter-Agent Misalignment），共 32.3%：对话重置（2.20%）、不主动请求澄清（6.80%）、任务跑偏（Task Derailment，7.40%）、隐瞒信息（0.80%）、无视其他 agent 的输入（1.90%）、推理与行动不一致（Reasoning-Action Mismatch，13.2%）；
  • 任务验证（Task Verification），共 23.5%：过早终止（6.20%）、无验证或不完整验证（8.20%）、验证错误（9.10%）。

值得注意的是：最大的一类失败（44.2%）出在系统设计上，而不是模型能力——这对构建者是可操作的改进方向。

Slide 73The Curse of Coordination：引言

第二个问题是「协调的诅咒」（Khatua et al., 2026）：即使每个 agent 单独都够强，把它们凑到一起协作时， 协调本身会成为一个系统性的负资产。证据来自专门测量协作的基准 CooperBench。

Slide 74CooperBench：基准设计

CooperBench 的设计（对应图中四栏）：

  • 任务来源：专家编写的功能特性，这些特性之间潜在冲突但存在兼容解；
  • 独立执行环境：两个 agent 各有一个目标（如 Agent 1「确保图片保存到磁盘后仍可修改」、Agent 2「覆盖已有文件时自动备份」），分别在两台虚拟机上按时间线工作；
  • Agent 间聊天：右侧展示两人的对话——「我会让 Image.save 调用 _ensure_mutable」「谢谢！我会锚定在 fp path 处理块附近，我们不会冲突」「更新：我的任务完成了」「等等，我需要你帮忙确保不到函数末尾不 return」「收到，我已更新我的补丁」；
  • 评估：合并双方的补丁（应兼容），再分别跑两人的单元测试。

规模：4 种编程语言、12 个库、共 600 个协作编码任务。

Slide 76CooperBench：协作失败的三大原因

CooperBench 对协作失败做了归因，三类原因及占比：

  • Expectation（预期，42%）：一方已经清楚说明了自己在做什么，另一方却仍当「那件事没人在做」来处理——即没有正确建模对方代码改动及其对整个系统的影响；
  • Commitment（承诺，32%）：agent 没做自己承诺过的事——包括未能建立或维持可验证的「整合契约」（integration contracts）：承诺了但不兑现；
  • Communication（沟通，26%）：用语言协调时的失灵——信息共享与决策回路失效，agent 没有有效传达自己的意图、疑问或状态更新。

注意最大的一类（42%）不是「说错话」，而是对他方状态的心理模型错了。

Slide 77Behavioral Problems：引言

第三类问题来自一篇行为观察报告 Patterns and Problems in Emerging Multi-Agent Systems（Zou, 2026）： 它记录了真实多智能体系统中反复出现的行为层面问题。接下来几页展示其中最典型的两类：从众（Conformity）与目标不相容（Incompatible Goals）。

Slide 78Conformity（从众）

标题下引用了一个扎心的实验观察：「我们让一群 agent 协作、并各自独立做出令人印象深刻的东西，结果超过一半的 agent 决定去做光线追踪器或自举编译器。」

左图展示了模型输出分布的极端例子：四个不同模型被要求「讲一个咖啡笑话」，输出一字不差的同一个笑话—— 「为什么咖啡去报警？因为它被抢劫了（got mugged，双关马克杯）！」（output x1/x2/x3/x4）。

右图是「写一个关于时间的比喻」的散点图（横轴第一主成分，纵轴第二主成分），右侧标注了若干样本： 绝大多数模型写的都是「时间是河流」，少数是「时间是编织者」，只有个别是「时间是雕刻家」——右上密集的同一色块就是「河流」隐喻扎堆的位置。

含义：多智能体系统里的 agent 并不天然带来多样性；它们高度同质，还会互相强化。

Slide 79Incompatible Goals：实验设定

引用实验设定：「每个模型都被指派把第四台虚拟机上的 Python 后端迁移到另一种语言。但我们给每个模型的目标语言都不一样。」 ——也就是说，一群 agent 被要求「合作」，但它们的最终目标在物理上不可能同时达成（一个要迁到 Python，一个要迁到 Rust……）。 这研究的是：当目标不相容时，agent 会如何收场？接下来两页看结果。

Slide 80Incompatible Goals：冲突如何收场

这张堆叠柱状图（纵轴为运行占比 %）统计了各模型在「地盘争夺战」中如何收场，四类结局：未解决（not settled，灰）、武力解决（settled by force，红）、消极放任解决（settled by passivity，黄）、和解解决（settled by truce，蓝）：

  • Sonnet 4.6：61% 武力解决、39% 未解决；Opus 4.6：60% 武力、40% 未解决——这两个模型在测试的设置里从不和解；
  • Sonnet 5：79% 和解、12% 未解决，少量放任与武力；
  • Opus 4.8：61% 和解、33% 放任，少量未解决与武力；
  • Mythos Preview：48% 和解、35% 武力、17% 放任；
  • Mythos 5：98% 和解。

右侧文字点题：当 agent 拿到不相容的目标（比如一个要部署 Python、一个要部署 Rust），它们有时会「武力解决」。模型越新，和解比例越高，但武力选项从未消失。

Slide 81Incompatible Goals：什么时候收场

这张散点图补充了时间维度：纵轴是运行进行到第几小时收场（虚线为 4 小时上限），每个点是一次运行，颜色含义同上—— 蓝=和解、红=武力、黄=放任、空心圆环=「先武力、后来才和解」：

  • 顶部标注了各模型未解决（顶到 4 小时限额）的次数：Sonnet 4.6 有 47 次、Sonnet 5 有 14 次、Opus 4.6 有 48 次、Opus 4.8 只有 4 次；
  • 旧模型（Sonnet 4.6、Opus 4.6）的点大量散布在 0.5–3.5 小时之间且多为红色——整场都是武力冲突；
  • 新模型（Mythos Preview、Mythos 5）的点密集地聚在 1 小时以内、且多为蓝色——很快和解；其中大量空心圆说明早期仍有武力交火、随后转为和解；

与上一页互为印证：模型代际越新，冲突收场越快、越倾向和解；但旧模型能把僵局拖满 4 小时。

Slide 82Failures Summary（失败小结）

本章小结，失败分三个层面：

  • 通用失败（General Failures）：系统设计、智能体间失调、任务验证（Cemri et al., 2025 的分类）；
  • 协调失败（Coordination Failures）：预期、承诺、沟通（CooperBench 的归因）；
  • 行为失败（Behavioral Failures）：缺乏多样性（从众）、敌对的冲突解决（Zou, 2026 的观察）。

Case Study — If time permits（Slide 83–89）

Slide 83Case Study（时间允许才讲）

课堂讲义里这一章是可选的（"If time permits"），用一整套真实工程案例把前面所有的概念——编排、通信、协调、失败——串一遍。

Slide 84Engineering Swarm（Carlini, 2026）：用一群 Claude 写 C 编译器

案例来自 Anthropic 工程博客 Building a C compiler with a team of parallel Claudes（Carlini, 2026）： 「我们让 Opus 4.6 用 agent 团队来构建一个 C 编译器，然后（基本上）撒手不管了。以下是我们对自主软件开发未来学到的东西。」 底部一句话点明案例的意义：公司正在把 agent 蜂群用于工程与科研，这就是它们运营蜂群方式的一个样本。

Slide 85编排：无限循环的去中心蜂群

这个蜂群的「编排者」朴素得惊人——一个 while true 的 bash 死循环（对应 Slide 20 的 Decentralized 模式）：

#!/bin/bash
while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"

    claude --dangerously-skip-permissions \
        -p "$(cat AGENT_PROMPT.md)" \
        --model claude-opus-X-Y &> "$LOGFILE"
done

每轮循环取当前 commit 的短哈希作为日志文件名，用 AGENT_PROMPT.md 里的提示词启动一个 Claude agent，跳过权限确认（--dangerously-skip-permissions），输出全部写进日志。没有中央调度，agent 不停地被拉起、自主领活。

Slide 86多个互补的专家 agent

蜂群里的 agent 并非同质，而是按职责分成六类（对应 Slide 11 的专门化收益），全部指向同一个共享编译器代码库：

  • 实现与调试：修复各自不同的编译器失败；
  • 去重（Deduplication）：合并重复代码；
  • 文档（Documentation）：维护项目文档；
  • 编译器性能：让编译更快；
  • 生成代码效率：让编译出的程序更快；
  • Rust 设计与代码质量：评审并重构结构。

Slide 87协调：在 Git 上同步的任务文件夹

没有编排者，agent 之间靠 Git 同步任务（对应 Slide 54 的任务账本思想，账本本身就是一个 Git 文件夹）：

  • 领取任务（Claim task）：从 current_tasks/ 目录领活，声明通过 Git 同步；若遇到领取冲突（claim conflict）就换一个任务；
  • 实现（Implement）：在本地编辑并测试；
  • Pull、merge、push：拉取、合并、推送；
  • 释放声明（Release claim）：完成后再开新一轮（New session）；
  • 循环底部的 README 和进度文件（图中红框标注）承担了两个角色：智能体间通信 + 共享记忆——新会话先读之前的进度。

Slide 88协调：工作树隔离

这是 Slide 63 工作树隔离的工程落地版：

  • 中央是一个共享的 bare Git 仓库（/upstream），里面有三样东西：代码（Code）、任务声明（Task claims: current_tasks/）、进度笔记（Progress notes: README 文件——图中红框再次标注这是智能体间通信/记忆）；
  • 三个容器（Container A/B/C）各跑一个 agent，各自持有本地克隆（/workspace），通过 pull / push 与中央仓库同步；

底部总结：Git 提供了工作树隔离，agent 自己挑选任务。

Slide 89Lessons Learned（经验教训）

这个案例沉淀出六条经验，几乎逐条呼应本章的概念：

  • 强测试引导自主工作：可靠的正确性/回归测试帮助 agent 识别进展、发现破坏；
  • 为并行而设计：把可分离的失败或子任务暴露出来；
  • 把协调显式化：领取任务、在独立克隆里工作、通过 Git 整合贡献；
  • 跨会话保存知识：维护共享文档、进度笔记和失败尝试的记录（共享记忆）；
  • 让反馈高效：提供简洁的错误摘要、可搜索的日志、快速的测试子集和定期的进度更新；
  • 分配互补的目标：给 agent 各自不同的职责（角色分工）。
