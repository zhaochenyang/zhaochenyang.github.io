二、工作流与程序的框架：DSPy

Frameworks for Workflows and Programs — DSPy（Slide 19–51）

Slide 19分节页：Workflows（工作流与程序的框架）

进入第二部分：工作流与程序的框架。这一部分用两个代表性框架——DSPy 与 LangGraph—— 演示同一类任务（邮件 → 提取事件 → 选 emoji → 写入日历）的两种编程范式。

Slide 20YOU ARE HERE（工作流框架的位置）

在框架谱系图上，YOU ARE HERE 指向中间的 Workflow / Compound AI System 列—— 逻辑与编排（logic and orchestration）掌握在程序手中，而非模型手中。

Slide 21DSPy

第一个框架：DSPy（Stanford NLP 出品）。本讲必读阅读材料精讲即为 DSPy。

Slide 22DSPy 三大概念

DSPy 的三个核心概念：

  • Signatures（签名）——描述「做什么」（What）：输入输出的声明；
  • Modules（模块）——描述「怎么做」（How）：调用 LLM 的策略（如 ChainOfThought、ReAct）；
  • Optimizers（优化器）——用数据与指标自动改进程序。

Slide 23Live Demo（DSPy 现场演示分节页）

注：S24 起的 DSPy 页面多为现场编程演示的备用页（页面底部红条标注 "This is a backup slide in case we cannot do the live demo."），课堂上以 notebook 现场演示为准。

Slide 24Signatures（签名）

Signatures 小节开始：签名用一行字符串或类型化的类声明 LLM 任务的输入与输出， 是 DSPy 描述「做什么」的方式。

Slide 25最简单的签名：一行字符串

最简单的签名只需一行字符串：chat = dspy.Predict("message -> response")—— 声明输入 message、输出 response，即一个聊天模块。

Slide 26字符串签名的问题：格式不一致

以情感分析为例说明纯字符串签名的问题：模型输出的格式不稳定（如 "positive"、"Positive"、 "The sentiment is positive" 等不一致写法），下游程序难以可靠解析。

Slide 27类型化签名：Literal 与 confidence

用 Python 类型解决格式问题：类型化签名（typed_signature）用 Literal 约束输出取值 （如只能是 "positive" / "negative" / "neutral"），并可同时输出 confidence（置信度）， 使输出结构化、可解析。

Slide 28类型化签名示例：ExtractEvent

本讲贯穿示例的签名：定义 class ExtractEvent—— 输入字段（InputField）email（邮件原文）； 输出字段（OutputField）event_name、date、start、duration_minutes （事件名、日期、开始时间、时长）。类型化字段保证提取结果可直接被程序使用。

Slide 29Modules（模块）

Modules 小节开始：模块描述「怎么调用 LLM」—— 直接预测（Predict）、链式思考（ChainOfThought）、代理循环（ReAct）等，并可用纯 Python 把多个模块组合起来。

Slide 30ChainOfThought：输出中多一个 reasoning

把模块从 Predict 换成 dspy.ChainOfThought：同样的签名下， 模型会先输出一个 reasoning（推理过程）字段，再给出最终答案—— 用「先思考后回答」的策略提高质量。

Slide 31PickEmoji：为事件选 emoji

第二个模块 PickEmoji：输入事件名（event_name），输出一个合适的 emoji—— 同样用 ChainOfThought 实现，演示多个签名/模块在同一程序中共存。

Slide 32组合模块：UpdateCalendarFromEmail

把两个模块组合成一个完整程序：class UpdateCalendarFromEmail(dspy.Module)—— 先调用事件提取模块，再调用 emoji 选择模块，两次 LLM 调用之间用纯 Python 控制流衔接 （判断、字段传递等），体现「编排逻辑在程序里」。

Slide 33组合模块的两次调用输出

运行 UpdateCalendarFromEmail 的输出：第一次调用提取出事件的结构化字段， 第二次调用为事件选出 emoji，展示模块组合的实际效果。

Slide 34tinycal 日历界面

tinycal 是本讲演示用的迷你日历应用（周视图）： DSPy 程序提取出的事件最终被写入这个日历，作为贯穿全讲的可视化目标。

Slide 35Optimizers（优化器）

Optimizers 小节开始：DSPy 的优化器利用训练数据与评测指标， 自动改进程序的提示词/指令乃至权重，而不是靠人手调 prompt。

Slide 36优化器的三类输入

优化器围绕三大支柱工作：

  • Data（数据）：Training Data、Rollouts、Demonstrations、Human Feedback 等；
  • System or Model（系统或模型）：Language Model、Compound AI System / Workflow、Agentic System 等——优化器改进的对象；
  • Evaluation + Metric（评测与指标）：Pass Rate、Exact Match、LLM Judge、Cost/Latency 等——优化的目标信号。

Slide 37准备标注数据：50 封邮件

优化需要数据：准备 50 封带 gold labels（标准答案标注）的邮件， 每封邮件对应正确的事件提取结果，作为优化与评测的基准。

Slide 38划分训练集与测试集

把 50 封标注邮件划分为 30 封训练集（train）与 20 封测试集（test）： 优化器在训练集上改进程序，测试集只用于最终评估，防止过拟合。

Slide 39评测指标：三字段全匹配

定义评测指标（metric）：提取结果的 event_name、date、start 三个字段全部匹配才算正确——一个严格的精确匹配指标。

Slide 40基线：强模型直接达标

用强模型（gpt-5.4-nano）跑未经优化的程序，在该指标上已达 100%—— 强模型基线已经很好，但成本更高；这为下面「用优化把弱模型提上来」提供对照。

Slide 41基线：弱模型只有 55%

换成开源弱模型 Gemma 3 12B：同一程序、同一指标，准确率掉到 55%—— 模型能力不足时，需要用优化器来弥补。

Slide 42运行 GEPA 优化器

用 GEPA 优化器改进 Gemma 3 12B 的程序：配置评测预算 max_metric_calls=100，并指定一个 reflection_lm（反思用模型）—— GEPA 通过反思执行轨迹来迭代改进提示词（本讲阅读材料精讲含 GEPA 论文）。

Slide 43优化后：弱模型也到 100%

GEPA 优化后，Gemma 3 12B 在测试集上从 55% 提升到 100%—— 优化后的程序（更好的指令/提示）让便宜的开源模型达到了与强模型相当的效果。

Slide 44优化改了什么：只有 instructions 文本

对比优化前后，模型与代码结构都没变，变化的只有 instructions（指令）文本—— GEPA 自动写出的指令包含了从训练样例与失败反思中总结出的规则。这就是「优化器即自动提示工程」。

Slide 45Agents（DSPy 中的 agent）

Agents 小节开始：把工作流的固定控制流换成由模型决定调用顺序的 agent—— DSPy 用一行 dspy.ReAct 即可构造。

Slide 46dspy.ReAct：一行 agent

一行构造 agent：agent = dspy.ReAct("request -> summary", tools=tinycal.TOOLS)—— 指定输入输出签名与可用工具集。调用它处理复合请求（"在 10 月 7 日下午讲座之后安排与 John 的 30 分钟咖啡， 并给那周所有讲座加上书本 emoji"），8.3 秒返回 summary： 给两场 CS329Z 讲座加了 📚，并排定了 Coffee with John（10 月 7 日 15:00–15:30 ☕）。

Slide 47tinycal：ReAct agent 的结果

tinycal 日历界面展示 ReAct agent 的执行结果——咖啡约会与带 emoji 的讲座均已正确写入， 验证 agent 自主调用多个工具完成了复合任务。

Slide 48dspy.RLM：递归语言模型

另一个 agent 模块 dspy.RLM（Recursive Language Model，递归语言模型）： 演示用它回答关于收件箱（inbox）的问题——RLM 可以把长上下文卸载到代码执行环境中按需读取。

Slide 49ReAct 论文

dspy.ReAct 的出处：ReAct（Reasoning + Acting）论文—— 模型在「思考（thought）→ 行动（action）→ 观察（observation）」循环中交替推理与调用工具。 论文：arXiv:2210.03629（本讲阅读材料精讲亦含 react）。

Slide 50RLM 架构图

RLM 的架构：模型把长文本当作环境中的对象，通过代码按需切片读取， 并且可以深度派生子 RLM（recursively spawn child RLMs）来处理子任务， 突破单次上下文窗口的限制。

Slide 51DSPy Summary

DSPy 小结：用 Signatures 声明做什么、用 Modules（Predict / ChainOfThought / ReAct / RLM） 声明怎么做、用 Optimizers（如 GEPA）凭数据与指标自动改进—— 程序逻辑始终是显式的 Python，模型只负责被声明好的子任务。

二（续）、工作流与程序的框架：LangGraph

LangGraph — State / Nodes / Edges（Slide 52–77）

Slide 52LangGraph

第二个框架：LangGraph（LangChain 团队出品）—— 用「图」（State、Nodes、Edges）显式描述工作流的控制流。

Slide 53Outline：State（共享工作区）

LangGraph 核心概念之一——State（状态）：所有节点共享的工作区 （workspace），节点通过读写 State 交换数据。

Slide 54Outline：Start / End

每个图都有显式的入口 __start__ 与出口 __end__—— 数据从入口流入，在出口汇总结果。

Slide 55Outline：Nodes（节点）

Nodes（节点）：就是普通函数——读取 State、做计算（包括调用 LLM）、 把结果写回 State。

Slide 56Outline：Edges（边）与条件边

Edges（边）定义控制流：固定边把节点顺序连起来； 条件边（conditional edges）根据 State 的内容动态决定下一个节点。

Slide 57Outline：概念汇总

把四个概念合到一张图上：State 是共享工作区，__start__/__end__ 是出入口， Nodes 读写 State，Edges（含条件边）决定控制流。

Slide 58Agent 图：LLM ⇄ Tools 循环

用图描述 agent：LLM 节点决定调用工具，工具节点执行后把结果写回 State 再交还 LLM—— agent 循环就是图上 LLM 与 Tools 之间的环（直到 LLM 决定结束、走向 __end__）。

Slide 59Live Demo（LangGraph 现场演示分节页）

注：S60 起的 LangGraph 页面同为现场编程演示的备用页 （底部红条 "This is a backup slide in case we cannot do the live demo."）。

Slide 60Building the Graph：结构化输入输出

开始用 LangGraph 构建同一个邮件→日历程序。第一步给 LLM 调用加上结构化输出： 用 pydantic 定义 ExtractEvent 模型， 通过 with_structured_output 让模型直接返回类型化对象。

Slide 61Structured I/O：ExtractEvent

结构化输入输出（Structured I/O）：pydantic 的 ExtractEvent 声明 event_name / date / start / duration_minutes 等字段，模型输出被约束为该 schema—— 与 DSPy 的类型化签名异曲同工。

Slide 62State：TypedDict

定义图的 State：用 Python 的 TypedDict 声明共享工作区的字段（如 email、event 等）， 所有节点都读写这个结构。

Slide 63Node：extract

第一个节点 extract：读取 State 中的 email，调用带结构化输出的 LLM 提取事件， 把结果写回 State。

Slide 64Graph：组装与编译

组装图：StateGraph 创建图、add_node 加节点、add_edge 连边、 compile 编译为可运行对象。此时是最简单的线性图： __start__ → extract → __end__。

Slide 65运行：graph.invoke

用 graph.invoke 运行图：传入含 email 的 State，得到填充好字段的 ExtractEvent 对象——线性图跑通。

Slide 66Conditional Edges and Workflows（条件边）

进入条件边（Conditional Edges）小节：根据提取结果动态决定后续路径 （有事件才继续选 emoji 并入日历，否则直接结束）。

Slide 67扩展 State：CalendarState

扩展 State 为 CalendarState：在原字段基础上增加 emoji 与 status，供后续节点与条件路由使用。

Slide 68新增节点：pick_emoji 与 add_to_calendar

新增两个节点：pick_emoji（为事件选 emoji）与 add_to_calendar （把事件写入 tinycal），都读写 CalendarState。

Slide 69条件边：route 函数

条件边由一个路由函数实现：route 根据 State 返回 Literal["pick_emoji", "__end__"]——有事件走 pick_emoji，没事件直接结束。 控制流以显式代码表达。

Slide 70完整图与分支结构

完整的图：__start__ → extract →（条件边）→ pick_emoji → add_to_calendar → __end__， 或无事件时 extract → __end__。配分支示意图。

Slide 71两次 invoke 的结果

两次 graph.invoke 演示条件边：含预约的邮件 → 提取出 Dentist、选 emoji 🦷、 状态 added；无关邮件（Credits）→ 无事件，直接结束（None）。

Slide 72tinycal：条件分支写入结果

tinycal 日历展示条件分支的实际效果：有效事件被写入，无效邮件不产生任何日历条目。

Slide 73Agents（LangGraph 中的 agent）

最后一小节：把图换成由模型控制循环的 agent——LangGraph 提供 create_agent 一行构造 LLM ⇄ Tools 循环。

Slide 74create_agent：两行代码

create_agent 只需两行（指定 model 与 tools）即得到 agent； 配图展示 model ⇄ tools 的循环：模型决定调用哪个工具，工具结果回流给模型，直至结束。

Slide 75运行 agent：移动咖啡时间

invoke 该 agent 处理「把咖啡约会挪 30 分钟」之类的请求，tinycal 中事件更新为 3:30–4:00pm——与 DSPy ReAct 相同的任务，用图框架的 agent 抽象完成。

Slide 76LangGraph Summary

LangGraph 小结（五条要点）：State 是共享工作区；Nodes 是读写 State 的函数； Edges 定义控制流；条件边让控制流依赖运行时状态；agent 即 model ⇄ tools 的循环图。 一切控制流都以显式代码表达。

Slide 77Recap（第二部分小结）

第二部分回顾（四条要点）：工作流框架把工作流写成显式程序；DSPy 以签名/模块/优化器组织， LangGraph 以 State/Nodes/Edges 组织；两者都能在一行内升级为 agent。 页面同时展示四个同类框架的 logo：DSPy、LangGraph、LlamaIndex、crewAI—— 框架选型空间很大。

三、开源 Agent Harnesses

Open Source Agent Harnesses（Slide 78–89）

Slide 78分节页：Agent Harnesses

进入第三部分：开源 Agent Harnesses——围绕 LLM 的「运行时外壳」， 决定工具、记忆、上下文管理与执行方式等设计选择。

Slide 79Framework Landscape：Agent 列

在框架谱系图上，YOU ARE HERE 指向最右端的 Agent 列（红框）—— 控制流交给模型，harness 负责模型之外的一切。

Slide 80What is an Agent Harness（什么是 agent harness）

Agent Harness 的架构图：Planning & Reasoning 与 Memory 汇入 LLM Core， LLM 通过 Tools 产生 Agent actions， 与环境之间以 observe/act 交互。（图引自 CS329Z 第一讲）

Slide 81不同 harness 的差异

什么让 harness 彼此不同：

  • 构建 agent 涉及一系列设计选择：工具、记忆、上下文管理、执行方式；
  • 不同 harness 为各自的任务与运行环境做出不同的权衡（tradeoffs）；
  • 好的 harness 在任务成功率、成本、延迟、用户控制之间取得平衡——最佳平衡取决于用例。

Slide 82Mini SWE-Agent

Mini SWE-Agent——极简主义：

  • 除 bash 外没有其他工具；
  • 完全线性的 history——每一步只是追加到 messages；
  • 动作用 subprocess.run 执行——每个动作完全独立（而不是保持一个有状态的 shell 会话）。

Slide 83OpenHands

OpenHands：

  • 每一步存为一个 event——磁盘上每 event 一个 JSON 文件，发给模型的消息在每步从 event 重建；
  • 维护持久 terminal——一个 tmux 会话，cd、环境变量、virtualenv 跨命令保留；
  • 卡住时自停——同一动作与结果重复 4 次后，检测器终止执行。

Slide 84Pi Agent

Pi Agent：

  • 只有四个工具——read、write、edit、bash，system prompt 不到 1000 tokens；
  • 无权限系统——以启动时的权限运行；
  • history 存为树而非列表——可以回到之前的消息并从那里分支；
  • 刻意简单——没有 plan mode、没有 sub-agent 工具。

Slide 85OpenClaw

OpenClaw（常驻型个人助理 harness）：

  • 每 30 分钟自动唤醒——heartbeat 回合按调度运行，agent 回复 NO_REPLY 以保持安静；
  • 作为单个长驻 Gateway 运行——一个进程管理所有聊天渠道；
  • 用 Markdown 文件构建身份——AGENTS.md、SOUL.md、IDENTITY.md、USER.md、MEMORY.md 注入 system prompt；
  • 每晚 3AM 存记忆——后台任务回读当天笔记，把值得保留的部分写入 MEMORY.md。

四、编排与遥测

Orchestration and Telemetry — Temporal & Observability（Slide 90–122）

Slide 90分节页：Orchestration and Telemetry

进入第四部分：编排（Orchestration）与遥测（Telemetry）—— 让长时间运行的 agent 系统可靠、可调试、可观测。

Slide 91Framework Landscape：可靠性/可观测性

在框架谱系图上，YOU ARE HERE 指向横贯全局的顶条 Reliability / Observability——这一层不属于某个框架， 而是所有 agent 系统都需要的工程基础设施。

Slide 92Why needed：任务时长指数增长

METR 的「时间视野（time horizons）」图：不同 LLM 能以 50% 成功率完成的软件任务时长 （人类所需时间）随模型发布呈指数增长——从 GPT-2 的约 4 秒（回答问题）、GPT-4 的约 6 分钟， 到 Claude Opus 4.6 / Claude Mythos Preview 的约 16 小时量级 （如「最优地压缩语言模型规模」）。图中也注明：超过 16 小时的测量在当前任务集下尚不可靠。

Slide 93Why needed：基础设施必须跟上

为什么需要编排与遥测：

  • agents 运行时间越来越长（上一页是按人类时间计），支撑它们的基础设施必须可靠；
  • 日志与可观测性工具利于调试；
  • 这些都是软件工程实践中来之不易的教训，同样适用于 agent。

Slide 94Temporal

本部分的代表工具：Temporal——durable execution（持久化执行）平台， 把工作流的每一步记录在案，进程崩溃后可从记录恢复继续。

Slide 95Temporal Execution Model（1）：Activities

执行模型渐进图第一步：你的代码作为 Client， 其中的 Activities（红圆）是可能失败的功能单元 （functional units that can fail）——如一次 LLM 调用、一次写日历。

Slide 96Temporal Execution Model（2）：Workflows

第二步：Workflows（绿线）把 activities 链接起来—— 工作流代码描述步骤之间的编排逻辑，其执行历史被服务器记录。

Slide 97Temporal Execution Model（3）：Workers

第三步：右侧出现 Server 侧，底部是 Workers—— Activity Workers（执行可能失败的具体任务）与 Workflow Workers （重放工作流逻辑）两类进程。

Slide 98Temporal Execution Model（4）：Server

第四步：完整的 Server 侧——Task Queue（Activity Queue / Workflow Queue） 分发任务，Execution History & State 记录每次执行的历史与状态， 最终落盘到 Storage。这就是「durable」的来源：状态在服务器，worker 可随时被杀死再拉起。

Slide 99Live Demo（Temporal 现场演示分节页）

注：S100 起的 Temporal 页面同为现场编程演示的备用页 （底部红条 "This is a backup slide in case we cannot do the live demo."）。

Slide 100Durable Workflows（持久化工作流）

演示主题：Durable Workflows—— 把第三部分的邮件→日历流程改写成 Temporal 的 activity + workflow。

Slide 101Making a Durable Workflow: Activities

把三个步骤声明为 activities（@activity.defn）： extract_event（复用 DSPy 的提取模块，缺字段返回 None）、 select_emoji（复用 DSPy 的 emoji 模块）、add_to_calendar（写 tinycal）。 Activities 是可失败的功能单元，由 workflow 编排。

Slide 102Making a Durable Workflow: Workflow

Workflow 类 CalendarWorkflow（@workflow.defn）： 对每个可能失败的调用都用 workflow.execute_activity 包裹， 配 RetryPolicy(initial_interval=1s, maximum_attempts=5) 与 1 分钟超时。 关键约束：workflow 必须确定性（自身不做 LLM 调用与 I/O）， 因为 Temporal 会依据记录重放它。

Slide 103Making a Durable Workflow: Worker

Worker 是真正运行 workflows 与 activities 的进程： Worker(client, task_queue="calendar", workflows=[CalendarWorkflow], activities=[extract_event, select_emoji, add_to_calendar], activity_executor=ThreadPoolExecutor(4))，然后 asyncio.create_task(worker.run()) 启动。

Slide 104Making a Durable Workflow: Run it

运行：两次 client.execute_workflow(CalendarWorkflow.run, ...)—— 「Office hours are Thursday October 8th at 3pm」→ added to calendar； 「Thanks for sending the slides, they look great!」→ no event found in email。 注释提示：每一步都被记录，可打开 http://localhost:8233 查看 calendar-1。

Slide 105tinycal：workflow 写入结果

tinycal 周视图（2026 年 10 月 4–10 日）：周四出现 🕐 Office hours（3:00–4:00pm）， 验证 durable workflow 端到端跑通。

Slide 106Temporal UI：Timeline

Temporal 内置 UI 的 Timeline 视图（10/4/26 4:06:56 AM PDT）： 三个 activity 依次执行——extract_event（约 10–18ms）、select_emoji（约 23–28ms）、 add_to_calendar（约 33–34ms）。可观测性开箱即用。

Slide 107Retries（重试）

下一演示主题：Retries（重试）—— activities 天然可能失败（限流、超时、网络抖动），重试策略由服务器按 RetryPolicy 自动执行。

Slide 108Retrying Flaky Activities：模拟不稳定服务

用一个「不稳定」activity 演示：@activity.defn(name="select_emoji")（activities 按名字匹配） 定义 flaky_select_emoji——打印当前 attempt，前两次尝试抛 RuntimeError("503 Service Unavailable")，第三次才真正调用 emoji 模块。

Slide 109Retrying Flaky Activities：服务器自动重试

换用含 flaky activity 的 worker（task_queue="retries"）并 invoke 一条「散步」邮件： 输出显示 select_emoji attempt 1 / 2 / 3 后返回 'added to calendar'（4.1s）—— 服务器按 RetryPolicy 替你重试，workflow 代码无需任何改动。

Slide 110tinycal：重试后写入成功

tinycal 更新：周二 9:00–9:30am 出现 🚶 Go for a walk——两次失败重试后最终成功写入。

Slide 111Temporal UI：重试在 Timeline 上可见

Timeline 上 select_emoji 显示为「3 · select_emoji」的红色条 （4:15:17–4:15:20 AM PDT）——重试次数与耗时一目了然，失败与恢复全程可观测。

Slide 112Server Based Orchestration（基于服务器的编排）

下一演示主题：Server Based Orchestration—— 定时器、等待等编排能力由服务器承担，而非依赖某个活着的进程。

Slide 113Server Based Timing：workflow.sleep

ReminderWorkflow：先通过 workflow.execute_child_workflow 跑日历子流程，再 await workflow.sleep(seconds) 等到提醒时刻。 要点：一个 workflow 可以一行代码「睡」数月甚至数年——睡眠由服务器计时，不占用 worker。

Slide 114杀掉 worker，workflow 仍在运行

实验：启动 ReminderWorkflow（Lab meeting，20 秒后提醒），等日历步骤完成、 在 sleep 中途 cancel 掉 worker——handle.describe() 显示 workflow 状态仍为 RUNNING（已无任何 worker 存活）。状态在服务器，进程死了流程不死。

Slide 115拉起新 worker：定时器照常触发

重新拉起 worker 后：定时器触发，workflow 正常结束，返回 Reminder! (Lab meeting on Thursday, October 8th, 2026 at 11am for 60 minutes.)； 日历中只有一个 Lab meeting（不是两个）——LLM 步骤不会重跑，因为结果早已被记录。

Slide 116tinycal：Lab meeting 只出现一次

tinycal 确认：周四 11:00am–12:00pm 出现 📅 Lab meeting 一次—— 崩溃恢复没有造成重复写入（exactly-once 语义的直观体现）。

Slide 117Temporal UI：20 秒睡眠在 Timeline 上

Timeline 上可见一条 「1 (20s)」橙色 timer 条（4:23:18–4:23:38 AM PDT） 与 CalendarWorkflow 子流程条——20 秒的服务器端睡眠及其跨 worker 重启的恢复全程留痕。

Slide 118Additional Observability Frameworks

编排之外，还有专门的可观测性框架——用于追踪、记录、分析 LLM 应用的每一次调用。

Slide 119MLFlow

MLflow（Databricks）：Experiments 面板记录 DSPy 实验（如 dspy-paper-su…）， 点开 LM.__call__（0.01s）可见 Inputs（prompt：「Please tell me what MLflow is for.」、 messages）与 Outputs（模型回答原文），并可 Show timeline。

Slide 120LangSmith

LangSmith（LangChain）：ProductionTraces 项目面板—— TOTAL RUNS 578、TOTAL TOKENS 23,010、LATENCY P99 1.20s / P50 3.20s、FEEDBACK （helpfulness/coherence/relevance 等）；Runs 表逐条列出 LLMChain 的输入、延迟与反馈分； 右侧 Filters 可按反馈、来源、运行类型、状态等筛选。

Slide 121LangFuse

Langfuse：Home 仪表板六面板—— Model latencies（分位数折线）、Model usage（按模型成本）、Observations by type（Default/Debug/Error）、 Model costs（$57.44，按模型列 token 与美元）、Traces（4.78K，按名称统计）、 Scores（12.32K，如 # answer-fit 平均 0.75）——成本、延迟、质量一站式监控。

第四部分回顾：

  • 编排让 agents 保持可靠（Orchestration keeps agents reliable）；
  • 可观测性支撑调试与监控（Observability enables debugging and monitoring）；

五、最佳实践与挑战

Best Practices and Challenges（Slide 123–130）

Slide 123分节页：Best Practices and Challenges

进入最后一部分：把全讲内容沉淀为可执行的最佳实践，并直面框架带来的挑战。

Slide 124Keep it Simple（保持简单）

「Model → Workflow or Compound AI System → Agent」轴上标注： Model 是更大系统的一小部分；Workflow 的逻辑与编排在程序里；Agent 的控制流交给 AI 模型。三条建议：

  • 你不一定总要构建 agent——有时 workflow 就适合任务；
  • 真要构建 agent 时，仔细考虑该包含哪些工具；
  • 如果数据充足，你甚至可能端到端优化一个模型就够了。

Slide 125Make Failures Observable and Recoverable

让失败可观测、可恢复：

  • 追踪模型调用、工具调用、状态变化与错误；
  • 设置超时、重试上限与执行预算；
  • 记录输出并诊断失败；
  • 监控系统状态。

右侧列出对应工具：Temporal / mlflow / Langfuse 等；底部终端截图展示一个被拦截的错误命令， 配文：You can raise the error to the agent to try again.（可以把错误抛给 agent 让它重试）。

Slide 126Example: Shepherd（元 agent 示例）

Shepherd 论文（arXiv:2605.10913）的 meta-agent：一个更强的 agent 观察、拦截、回退（revert）、分叉（fork） 另一个 agent 的执行轨迹（代码示例：@agent(LLM="haiku") implement 被 @agent(LLM="opus", tool=[observe, revert, fork]) oversee 监管）。三项结果：

  • (a) 运行时干预（CooperBench, Pair Coding）：无 meta-agent 28.8% → Sonnet 4.6 w/ meta-agent 45.3% → Opus 4.7 w/ meta-agent 54.7%；
  • (b) 反事实优化（LiveCodeBench）：CRO 51.0% 高于 GEPA 48.7%、MetaHarness 40.0%、未优化 30.7%；
  • (c) Tree-GRPO（TerminalBench-2）：Qwen3.5-35B-A3B 26.1→39.4、Nemotron-3-Super-120B-A12B 30.3→37.2。

Slide 127Run Evaluations（跑评测）

跑评测（配天平插图，喻指权衡）：

  • 做设计决策的最好方式是把它们建立在 evals 之上；
  • 评测使优化成为可能；
  • 构建一个恰当的 eval 是制作 AI 系统最重要的步骤之一；
  • 明智地选择指标（准确率、成本、延迟等）；
  • 测试代表性任务、边界情况与失败场景。

Slide 128Run Evaluations：自建领域评测

左侧给通用编码基准（TERMINAL-BENCH、SWE-bench、DeepSWE）打上红叉， 右侧推荐 Your Custom Domain Eval!（你的自建领域评测）打上绿勾。 底部说明：除非你在构建通用编码 agent harness、或在测试通用 agent 系统改进， 否则标准编码基准不是你应该攀比的指标。

Slide 129Challenges / Limitations（挑战与局限）

框架带来的挑战：

  • 抽象让你远离底层系统细节，所以要确保知道引擎盖下在发生什么（know what is going on under the hood）；
  • 构建复杂 AI 系统时很难定位失败来源——一定要看 traces（Make sure to look at the traces!）；
  • 建立在框架之上意味着依赖外部库，需要它们持续被维护。

右侧 meme（Hamel Husain 博客配图）：库宣传「pip install llm-magic 就能得到最佳输出」， 而 Batman 一巴掌——「SHOW ME THE PROMPT」（把 prompt 给我看），呼应「抽象之下仍是 prompt」。

Slide 130Recap（第五部分小结）

最佳实践回顾：

  • 以 Building → Running → Evaluating → Improving 循环来工程化 agents——工程过程是一个环；
  • 从简单开始，为新增的复杂度提供理由；
  • 为失败与恢复而设计；
  • 用证据与评测评估质量、成本与延迟；
  • 完全理解你的系统如何工作。

  • DSPy：Signatures 声明「做什么」（一行字符串到类型化类）、Modules 声明「怎么做」（Predict / ChainOfThought / ReAct / RLM，纯 Python 组合控制流）、Optimizers 凭数据与指标自动改进（GEPA 把 Gemma 3 12B 从 55% 提到 100%，改的只是指令文本）。
  • LangGraph：State 共享工作区、Nodes 读写状态、Edges（含条件边）定义控制流；agent 即 model ⇄ tools 的循环图；一切控制流都是显式代码。
  • Agent Harnesses：harness 决定工具/记忆/上下文/执行的设计选择——Mini SWE-Agent（极简）、OpenHands（event 存盘 + 持久 tmux）、Pi Agent（四工具 + 树状 history）、OpenClaw（常驻 + 心跳 + Markdown 身份）；Terminal-Bench 2 显示同一模型换 harness 成本与成功率差异显著；Meta-Harness 用搜索循环自动发现更优 harness。
  • 编排与遥测：METR 任务时长指数增长要求基础设施可靠；Temporal 以 Activities/Workflows/Workers/Server（队列+执行历史+存储）实现 durable execution——自动重试、服务器端定时、worker 崩溃后不重跑已记录步骤；MLflow / LangSmith / Langfuse 提供 LLM 级追踪与成本/延迟/质量监控。
  • 最佳实践：保持简单（不必总是 agent）、让失败可观测可恢复、用自建领域评测驱动决策、知道抽象之下在发生什么（SHOW ME THE PROMPT）。
