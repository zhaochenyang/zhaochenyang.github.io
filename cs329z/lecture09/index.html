一、优化的前提条件（Conditions for Optimization）

Conditions for Optimization（Slide 7–11）

Slide 7章节页：Conditions for Optimization

进入第一章。本讲底部一直有五个小节的进度条：Conditions（条件）、Context/Prompt（上下文/提示词）、Weights（权重）、Agents（智能体）、Which to Use?（如何选择）， 当前高亮的是第一部分「Conditions」——在动手优化之前，先回答两个问题：优化一个 AI 系统需要具备什么？什么时候值得优化？

Slide 8Three Pillars of AI Systems（AI 系统的三大支柱）

要优化一个 AI 系统，三根支柱缺一不可：

  • Data（数据）：Training Data（训练数据）、Rollouts（轨迹采样）、Demonstrations（示范样例）、Human Feedback（人类反馈）等；
  • System or Model（系统或模型）：Language Model（语言模型）、Compound AI System / Workflow（复合 AI 系统或工作流）、Agentic System（智能体系统）等；
  • Evaluation + Metric（评测 + 指标）：Pass Rate（通过率）、Exact Match（精确匹配）、LLM Judge（LLM 评分）、Cost/Latency（成本/延迟）等。

底部一句话：要优化一个 AI 系统，这三样必须同时具备！没有数据无从学起，没有系统无处施加，没有评测就不知道好坏。

Slide 9Is (Context) Optimization Necessary?（优化真的有必要吗？）

先回应一个常见质疑：既然模型随规模越来越大越来越好，我们还需要费劲调 prompt 吗？ 讲义的回答借用物流业的「最后一公里（LAST MILE）」比喻：通用大模型提供的是出色的通用解（general solution）， 但一旦你知道自己的具体场景（exact setting），就能针对细节做适配——这正是优化发挥价值的地方： 优化适用于 LAST MILE（最后一公里）适配。右侧的配送信息图形象地展示了这一点：干线运输（前 99% 的路程）可以规模化、标准化， 而最后 1 英里才是最难、最贵、最需要定制的部分。

Slide 10When to Optimize（什么时候该优化）

判断「该不该上优化」的三条信号：

  • 你拥有适合自己领域的数据和评测——例子（examples）和反馈（feedback）能够传达那些很难在 prompt/系统里完整表达出来的需求； 有时一份好的评测（evals）比文字更能传达意图，你可以直接把系统调到评测上表现最好；
  • 系统包含许多复杂组件，手工很难调优——组件一多，组合空间爆炸，人工试错不现实。

换句话说：当「意图说不清、组件调不动」的时候，就该让优化算法登场。

Slide 11Benefits of Optimization（优化的收益）

做好优化能带来五条收益：

  • 更高的可靠性（Greater reliability）：减少反复出现的错误，提升跨任务的一致性；
  • 领域适配（Domain adaptation）：在专门的任务、工作流和需求上提升表现；
  • 更低的成本与延迟（Lower cost and latency）：用更小的模型、更短的 prompt 或更少的工具调用维持同等质量；
  • 从经验中学习（Learning from experience）：把成功轨迹和失败反馈转化为持久的改进；
  • 适应力（Adaptability）：当模型、工具和任务需求变化时，可以随之调整行为。

二、上下文优化（Context Optimization）

Context Optimization（Slide 12–69）

Slide 12章节页：Context Optimization

进入第二章「上下文优化」。这一章讲的是不改模型权重、只优化上下文（提示词、few-shot 示例、指令）的算法。 本章又分两个子主题：Fewshot Optimization（示例优化）与 Reflective Optimization（反思式优化）。

Slide 13子章节页：Fewshot Optimization

子章节「Fewshot Optimization（少样本示例优化）」：优化放进 prompt 里的那几个示例（few-shot demonstrations）——选哪些、按什么顺序放。

Slide 14Fewshot Prompting（少样本提示）

先复习概念。Few-shot prompting：在任务描述（task description）之外，模型还能看到该任务的几个示例（examples）， 例如「sea otter => loutre de mer」「cheese => …」。整个过程不做任何梯度更新（no gradient updates）—— 这正是它区别于微调的地方：所有「学习」都发生在上下文里。既然示例全在上下文里，那么选哪些示例、按什么顺序摆放就成了可优化的自由度，本章余下内容都在回答这两个问题。

Slide 15Fantastically Ordered Prompts and Where to Find Them [Lu et al., 2022]（示例顺序敏感性与熵度量）

这篇论文（Lu et al., 2022）发现：few-shot 示例的排列顺序会显著影响模型输出，甚至能让准确率在接近随机到接近最优之间波动。 他们的方法是：在训练集（trainset）上尝试一堆不同的 prompt 排列顺序，然后度量每种顺序在探测集（probing set）上引发的标签变化—— 有趣的是，并不使用探测集的真实标签（ground truth labels）。 图中流程：左侧 Train 1–4 组 (sentence, label) 与 (Prompt)，按不同排列顺序输入 PLM（预训练语言模型），生成不同结果，右侧用绿色框的 Probing Set (sentence, label) 评估。 论文提出两个不依赖标签的度量：GlobalE（全局熵）＝对整个探测集答案分布的熵 GlobalE_m = Σ −p·log p； LocalE（局部熵）＝对每个探测样本的答案分布求熵再取平均。熵高＝模型对该排列「拿不准」；挑熵低的顺序即可。

Slide 16Global Entropy（全局熵：高低对比）

用同一批四条影评示例对比两种排列：

  • 高全局熵（High Global Entropy）：四种排列下模型给出的标签混杂不一（0、1、0、1）——说明模型对这个顺序「举棋不定」，整体输出分布熵大；
  • 低全局熵（Low Global Entropy）：标签高度一致（几乎全是 0）——模型对这个顺序的判断很「笃定」。

公式 GlobalE_m = Σ_{v∈V} −p_m^v log p_m^v 就是对标签分布求熵。直觉：应优先选择低熵的排列。

Slide 17Local Entropy（局部熵：高低对比）

局部熵换一个视角：不问「整体标签混不混杂」，而问「单个样本上模型拿不拿得准」。每个探测样本都看一下 0/1 两类的 logprobs 小柱状图：

  • 高局部熵（High Local Entropy）：0 和 1 两根柱子高度接近——模型在这道题上摇摆；
  • 低局部熵（Low Local Entropy）：一根柱子显著高——模型很确信。

公式 LocalE_m = (ΣΣ −p log p) / |D| 即对所有探测样本的熵取平均。GlobalE 看全局一致性，LocalE 看逐样本置信度，两者都不需要真实标签。

Slide 18用熵选顺序的效果（逼近 Oracle 排序）

结论页：用探测集 + 熵度量来挑排列，其准确率可以逼近 Oracle 排序（Oracle＝在开发集上穷举所有排列挑最好的那种，代价极高）。 表格节选（准确率，下标为标准差）：

  • GPT-3 2.7B 组：如 SST-2 上原始 78.0₁₀.₇ → LocalE 81.0₆.₀ → GlobalE 80.2₄.₂，而 Oracle 是 89.8₀.₇——熵方法拿到了大部分可挖掘的收益，且标准差更小（更稳定）；
  • GPT-3 175B 组：SST-2 上 93.9 → LocalE 93.8 / GlobalE 93.9，Oracle 94.7；Subj 上 71.2 → 76.3（GlobalE）；AGNews 上 85.1 → 85.9（LocalE）；CB 上 75.1 → 79.9（GlobalE）；
  • 基线对照：Majority（多数类基线）约 50 上下，Full Finetuning 在多数任务上仍是天花板（如 DBPedia 99.3）。

要点：不训练、不标注，仅靠「选个好的示例顺序」就能稳定白拿几个点的准确率，并大幅降低方差。

Slide 19Bootstrap Reasoning（自举推理）

接下来解决另一个问题。我们知道 Chain-of-Thought（CoT，思维链）推理很重要—— 论文截图对比很直观：同样是「Roger 有 5 个网球，又买 2 罐每罐 3 个」「食堂 23 个苹果用掉 20 个又买 6 个」两道题， 标准提示直接给答案会错（27，应为 9），而先写推理过程（5+6=11；23−20=3，3+6=9）就能答对。 但问题在于：few-shot 的标注示例通常只带答案、不带推理过程（reasoning）——标注成本高，人写的推理还未必是模型最「顺」的推理方式。怎么办？接下来几页给出「自举（bootstrap）」方案。

Slide 20Bootstrap Reasoning: STaR [Zelikman et al., 2022]

STaR（Self-Taught Reasoner）的做法：用拒绝采样（rejection sampling）来「挖」推理轨迹。 流程：Question → 语言模型生成 Rationale + Answer → 用正确性检查分流—— 答对的 (Question, Rationale, Answer) 直接进数据集，微调回流更新模型；答错的走 Rationalize 路径： 把正确答案作为提示（hint）再生成一次推理，成功后同样回收。 图中示例：「什么东西可以用来装小狗？」模型生成「篮子（basket）是用来装东西的，所以答案是 basket (b)」这样的推理。 核心思想：模型自己生成推理、用答案正确性当过滤器，循环自我改进。

Slide 21Bootstrap Reasoning: DSPy [Khattab et al., 2023]

DSPy 把「自举推理」用到了上下文优化场景：我们甚至不需要微调——只要拒绝采样出成功的推理（rejection sample successful reasoning）就行。 流程图上下两行：同一个 Input 喂给 Model，产出 Reasoning+Output，交给 Metric 打分—— 得分好的 trace 保留（Keep，绿框绿拇指），得分差的丢弃（Discard，红框红拇指）。 保留下来的「输入＋模型自己的推理」就成了一条现成的 few-shot 示例。右侧补充：随后在开发集（devset）上尝试不同的示例组合，找出表现最好的那组 few-shot 示例。

Slide 23子章节页：Reflective Optimization

子章节「Reflective Optimization（反思式优化）」： 前面优化的是「示例」，接下来优化的是「指令（instruction）」本身——让 LLM 观察、反思、改写自己的提示词。

Slide 24Large Language Models as Optimizers（OPRO）[Yang et al., 2024]

OPRO（Optimization by PROmpting）的思路：让 LLM 看到过去的指令及其各自的成绩，然后请 LLM 写一条新的指令。 左图流程：objective function evaluator 给候选解打分 → 分数与 meta-prompt（包含 solution-score pairs 与任务描述）一起喂给「LLM as optimizer」→ 生成新的候选解 → 循环（完成时取 top solutions）。 右图是 meta-prompt 实例：把历史指令按分数升序排列（如 "Let's figure it out!" 61 分、"Let's solve the problem." 63 分）， 附上任务示例与 <INS> 占位说明，最后要求「写一条与旧的不同、分数尽可能高的新指令，写在方括号里」。 本质上这是把「优化」变成一个序列生成问题，用上下文里的 (解, 分数) 轨迹引导 LLM 向更优解移动。

Slide 26MIPROv2 [Opsahl-Ong et al., 2024]（总览）

MIPROv2 把前两个子章节的方法整合成一个完整的 prompt 优化器，分三步：

  1. Bootstrap Demonstrations（自举示例）：跑 N×K 次程序过 Metric 筛出成功 trace（若程序是 CoT，则包含推理/输出）；
  2. Propose Instructions based on Reflection（基于反思提出指令）：收集程序代码与数据摘要等信息，让 LLM 提案 N 条候选指令；
  3. Search the Combinations（搜索组合）：用 Bayes Search 在「指令 × 示例组」的组合空间里搜索最优搭配。

跑出来一次失败的尝试：程序下方展开的「物种预测推理与输出（Rationale and Output）」橙色高亮条被红叉划掉，Metric 旁是红色拇指朝下。 规则：如果输出在度量上得分差，就丢弃这条 trace。

Slide 64Feedback Gradients (TextGrad) [Yuksekgonul et al., 2024]

TextGrad（文本梯度）：让 LLM 反思「这个输出哪里可以改进」，并把这条反馈像梯度一样沿系统中的各个 prompt 反向传播。 左图把整个系统画成一张计算图：Inputs（Prompt、Query、Tool Prompt）各自经过 LLM / Search Engine / Tool Caller 产出中间输出，汇入 LLM 得到 Final Output，再经 Evaluation Instruction 算出 Loss； 两条「反向弧」上写着 ∂Loss/∂Prompt = "this prompt can be improved by..."、∂Loss/∂Response = "this response can be improved by..."—— 即用自然语言 criticism 代替数值梯度。右侧实例：初始化 prompt（"You will answer a reasoning question. Think step by step.…"）准确率 77.8%， 优化后 prompt（要求逐项列出数量、直接求和、校验相关性、复核计数等）准确率升到 91.9%。

Slide 65Genetic Pareto Prompt Evolution (GEPA) [Agrawal et al., 2026]

GEPA（遗传式帕累托提示演化）是一个进化搜索框架，主循环为 While Budget > 0：

  • 候选池（Candidate Pool P）：各候选 prompt 像树一样繁衍（P₀ 生成 P₁、P₂，P₁ 生成 P₃、P₄…），每个候选在每个任务上有得分（Scores Matrix：绿勾通过、红叉失败）；
  • 帕累托过滤（Pareto-based Candidate Filtering）：每个任务保留至少一个「该任务最优」的候选，构成 Filtered Pool（Pareto Frontier，帕累托前沿）——不选单一最优，而是保留「各有擅长」的多样化种群；
  • 提出新候选（Propose New Candidate）两条路线：(a) Reflective Prompt Mutation（反思式提示变异）——在训练集 minibatch M 上执行候选、用 μ_f 收集文字反馈，反思后提出新 prompt；(b) System Aware Merge（系统感知合并）——为每个模块策略性地从两个候选中选 prompt：若某模块在 P₂ 中演化过而 P₃ 没有，就从 P₂ 取，反之亦然；
  • 评估分流：新候选先做 minibatch 评估（Performance improved?）——有提升则在全部任务上评估并加入候选池（绿框），否则丢弃（红框）。

Slide 72Recall: Cross Entropy Loss（复习：交叉熵损失）

复习语言模型训练的基本损失。交叉熵损失（Cross Entropy Loss）公式 L = −Σ_{i=1}^{V} y_i log(p_i)，逐部件标注：

  • y_i（蓝框）：当该 token 是数据里的真实 token 时取 1，不是则取 0（one-hot 目标）；
  • Σ_{i=1}^{V}（红框）：对词表（vocabulary）中的每一个 token 求和；
  • log(p_i)（绿框）：该 token 的对数概率（log probability）。

一句话：SFT 就是最大化数据中真实 token 的对数似然。

Slide 73Recall: Instruction Finetuning（复习：指令微调）

复习 Instruction Finetuning（指令微调）（Flan 系列，Image Credit: arxiv.org/pdf/2210.11416）： 训练时混用多种任务形式——普通指令微调（「氮气的沸点是多少？」→ "-320.4F"）、思维链微调（「请一步步推理回答」→ 苹果题的完整推理）， 以及多任务指令微调（1.8K 个任务）；推理（Inference）时模型能泛化到未见过的任务—— 例如「Geoffrey Hinton 能和 George Washington 对话吗？先给理由再回答」，模型会推理「Hinton 生于 1947 年，Washington 卒于 1799 年，因此不能对话，答案 no」。

把 SFT 用到 agent 上的配方：

  • 让 teacher（教师）模型在 agent 任务上 rollout（跑轨迹）；
  • 用 teacher 完成的任务对 student（学生）模型做后训练（post-train）；
  • 重点是任务与环境的多样性（diversity of tasks and environments）；
  • 学生学到的是任务执行（task execution）能力。

Slide 80子章节页：Reinforcement Learning

子章节「Reinforcement Learning（强化学习）」：不再模仿 teacher 的轨迹，而是让学生自己在环境里试、用奖励信号学。

Slide 81RL For Agents（面向 agent 的 RL）

RL 版配方：

  • 让 student（学生）自己在 agent 任务上 rollout（注意与 SFT 的区别：SFT 是 teacher 跑，RL 是学生跑）；
  • 学生成功完成任务就获得奖励（reward）；
  • 重点是环境与任务复杂度的多样性；
  • 可验证性（Verifiability）是关键——奖励必须能客观判定任务是否完成。

右侧闭环流程图：Agent → Roll out → Trajectories → Evaluate → Rewards → Update weights → 回到 Agent。

Slide 82RL 环境：外部奖励与分组采样

右侧批注解释 RL 的两个机制：「外部奖励（external reward）验证任务是否成功完成」—— 截图中同一道任务由学生执行，最后由 VERIFIER 用 cmp -s "$EXPECTED" "$OUTPUT"（与参考输出精确匹配）判定， 通过则给 Terminal reward 1；「同一 prompt 在组内跑若干次、若干组组成一个 batch」—— 这是为下一页 GRPO 的「组相对优势」做准备。

Slide 83PPO vs GRPO（对比总览）

进入具体算法。上图为 PPO（Proximal Policy Optimization），下图为 GRPO（Group Relative Policy Optimization）（图例：黄=被训练模型，蓝=冻结模型）：

  • PPO：query q → Policy Model 生成输出 o → 三个辅助模型协同：Reference Model（冻结，算 KL 惩罚，与 reward 相加得 r）、Reward Model（打分）、Value Model（训练，估计每个 token 的价值 v）；r 与 v 经 GAE 算出优势 A；
  • GRPO：q → Policy Model 生成一组输出 o₁…o_G → Reference Model 算 KL ＋ Reward Model 打分得 r₁…r_G → Group Computation（组内计算）直接得出 A₁…A_G——不需要 Value Model。

Slide 84PPO 各部件标注

给 PPO 图逐个部件贴标签（红色标注）：

  • Reference Model 的 KL 项：「KL per Token（每个 token 的 KL）」；
  • Reward Model 的输出 r：「One reward for entire output（整条输出只有一个奖励）」/「Per token reward」；
  • Policy Model 生成 o：「Generate an Output（生成一条输出）」；
  • Value Model 的输出 v：「Value per Token / Per token value（每个 token 的价值）」；
  • GAE：「Generalized Advantage Estimate：这个 token 相比其他可能的 token 有多大用处？」。

注意复杂度来源：奖励是序列级的，但要为每个 token 估价值、算优势、算 KL。

Slide 85PPO 的代价 ①：四个模型

PPO 代价清单第一条：内存里要同时放四个模型！（Policy Model、Reference Model、Reward Model、Value Model——对大模型来说这是巨量的显存。）

Slide 86PPO 的代价 ②：每步训练两个模型

第二条：每一步要同时训练两个模型！（红框移到 Policy Model 与 Value Model 上——不仅策略在学，价值网络也要跟着学。）

Slide 87PPO 的代价 ③：多个逐 token 的昂贵步骤

第三条：还有多个（昂贵的）逐 token 计算步骤！（红框圈出 per-token KL、per-token value 与 GAE——这些逐 token 前向/反向是PPO 训练慢和贵的主要来源。）

Slide 88GRPO 各部件标注

换到 GRPO，同样贴标签：

  • Token Level KL：Reference Model 仍按 token 算 KL（这是唯一逐 token 的部分）；
  • Generate a Group of Outputs：策略模型对同一 prompt 生成一组输出；
  • Per Output Rewards：每条输出一个奖励 r₁…r_G（不再有 per-token value）；
  • Group Advantage：组内计算直接得到各输出的优势 A₁…A_G。

Slide 89GRPO 的改进 ①：三个模型

GRPO 改进第一条：内存里只需三个模型！而且注意——「Reward Model」不一定非得是个模型（可以是规则验证器、单元测试等，呼应 Slide 81「可验证性是关键」）。

Slide 90GRPO 的改进 ②：每步只训练一个模型

第二条：每一步只训练一个模型！（红框只剩 Policy Model——没有 value 网络要跟着训了。）

Slide 91GRPO 的改进 ③：只有 KL 逐 token

第三条：只有 KL 是逐 token 的，其余全在序列级！（奖励、优势、损失都以整条输出为单位——昂贵的逐 token 计算几乎全部消失。）

Slide 92GRPO：Advantage 计算（组内 z-score）

没有 value model，优势从哪来？答案写在公式里：对每条输出的奖励做组内 z-score 标准化—— Â_i = (R_i − mean) / std，减去组均值（baseline）再除以组标准差。红字结论： 「Compute the z-score for each output reward!」奖励高于组平均的输出被正强化，低于均值的被抑制。

Slide 93GRPO 目标函数（全标注）

把 GRPO 的目标函数拆开看（各部件对应彩色标注）：

J_GRPO(θ) = E[q∼P(Q), {o_i}∼π_θold(O|q)] · (1/G) Σᵢ (1/|o_i|) Σₜ [ min( (π_θ/π_θold)·Â_{i,t}, clip(π_θ/π_θold, 1−ε, 1+ε)·Â_{i,t} ) − β·D_KL[π_θ‖π_ref] ]

  • 期望 E：对「从数据集抽的一个 prompt ＋ 该 prompt 采样出的一组输出」求期望；
  • 1/G Σ（蓝）：组内平均（Avg over group）；
  • 1/|o_i| Σₜ（绿）：对响应中的 token 取平均（Avg over tokens in response）；
  • 重要性比率 π_θ/π_θold（紫）：「这个 token 在新策略下相比旧策略有多重要？」；
  • Â（橙）：Advantage（优势）——组相对优势；
  • clip（灰）：「不要在任何单个 token 上过度更新」（Don't over update on any one token）；
  • −β·D_KL（青）：「别偏离参考策略太远」（Don't deviate too far from reference）。

Slide 96子章节页：On-Policy Distillation

权重优化的第三种方法：On-Policy Distillation（在策略蒸馏）—— 结合 SFT 的「稠密信号」与 RL 的「在策略采样」，用 teacher 的 token 概率直接指导学生的采样输出。

Slide 97开场比喻：在自己下过的棋上学棋

本小节的开场比喻（底部原文）：「教练指导你亲自下过的一盘棋，比指导你只旁观的一盘棋，要有用得多。」 右图是 Chess.com 的复盘界面：本局白方第 26 步 Qe2 被标记为「!!」（brilliant，妙手），评分 0.00，面板给出后续变化与完整棋谱。 「在策略（on-policy）」的含义正来自于此：学习信号作用在学生自己生成的轨迹上，而不是别人（teacher）的棋谱上。

Slide 98SFT vs RL vs On Policy Distillation（示意对比）

三种方法在同一道题（prompt："What is 5 + (2 × 3)?"）上的机制对比：

  • SFT：学习 teacher trajectory（"2 × 3 equals 6, add 5 to get 11."），每个 token 下标注学生的条件逐 token 概率（20%、80%、95%、40%、99%、99%、30%、70%、40%、50%、95%、95%，红底深浅随概率变化）——信号是稠密的，但轨迹不是学生自己走的（off-policy）；
  • RL：学习 student trajectory（"5 + 2 is 7, and 7 × 3 is 21."——注意学生算错了），整条轨迹只有 reward: 0 一个信号——在策略，但信号稀疏；
  • On-Policy Distillation：同一条学生轨迹，但每个 token 标注teacher 的条件逐 token 概率（40%、80%、5%、15%、99%、99%、40%、80%、90%、99%、70%、99%、99%）——既在策略，信号又稠密。

Slide 99SFT vs RL vs On Policy Distillation（二维对比表）

把上一页压缩成一张表：

Slide 100On Policy Distillation Loss（损失函数）

损失就是一个反向 KL 散度，两个彩色标注点明关键：

  • 红色（期望算子 E）：「对从策略（学生自己）采样出的响应求期望」——这就是 on-policy 的含义；
  • 蓝色（log 差值项）：「每个 token 上：学生的 logprobs 减去 teacher 的 logprobs」——逐 token 的稠密信号。

直觉：学生照着自己平时的路走，每走一步都问 teacher「这里你会怎么做」，把差距压到最小。

Optimization with Agents（Slide 105–116）

Slide 105章节页：Optimization with Agents

进入第四章：换一个视角——让 agent 本身充当优化器：给它环境、日志与执行能力，让它自己迭代改进。本章两个案例：Self-Improvement（自我改进）与 Auto-Research（自动化研究）。

Slide 106子章节页：Self Improvement

子章节「Self Improvement（自我改进）」：agent 优化的是它自己——自己的代码、自己的 harness。

Slide 107Darwin Gödel Machine [Zhang et al., 2026]（机制）

Darwin Gödel Machine（DGM，达尔文·哥德尔机）的机制（底部原文）：「按与性能成正比、与子代数量成反比的方式选择父代进行自我修改。」 流程图拆解：

  • Archive（档案库）：保存所有历史 agent 变体的节点树（红=parent 父代，黄=child 子代，如 Coding agent → New coding agent）；
  • select / add 循环：从档案树中选父代 → 自我修改（Self-modify）：给 coding agent 它自己的代码仓库＋自我改进指令，产出「改进自身的代码 diff」；
  • Evaluate on benchmark：把新变体放到任务仓库（如 GitHub repo）＋任务指令（如 GitHub issue）上评测，产出「解题的代码 diff」；
  • 好的变体作为新节点 add 回档案树，循环继续。

Slide 108Darwin Gödel Machine（搜索过程）

两幅图展示 DGM 的搜索过程：

  • 左图 Archive Tree：约 80 个节点的树，颜色按 SWE-bench 得分着色（colorbar 0–0.5）；空心圈标记三类节点：10 tasks（无基本功能）、60 tasks、200 tasks（当时得分 ≥0.4 且居档案前二）；黑色星形为主 lineage（0→4→20→24→47→56…），即最终最佳 agent 的祖先链；
  • 右图 DGM Progress：横轴 Iterations（0–80），纵轴 SWE-bench Score（0.20–0.50）。Best Agent（蓝阶梯线）：起点 0.20 → 约 2 轮升 0.25 → 约 20 轮跳 0.41 → 约 46 轮 0.43 → 约 63 轮达 0.50 并保持。注释气泡标注了关键的自我改进：「非空补丁校验与重试」「用字符串替换做更细粒度的文件编辑」「按行做更细粒度的文件查看」（约 20 轮）、「上下文超限时自动摘要」（约 45 轮）、「多次补丁生成与排序」「带历史感知的补丁生成与排序」（约 63 轮冲上 0.50）。

注意：分数的跃升都对应 agent 给自己写的新工具/新能力——它在改自己的 harness。

Slide 109Darwin Gödel Machine（消融实验）

结论（底部原文）：「自我改进（父代修改自己而非由 meta-agent 修改）与探索（可以回退到先前的父代、而不是总在最新版本上叠加）两者都至关重要。」 消融曲线：

  • 左图（SWE-bench Score of Best Agent，0.20–0.50）：完整 DGM（蓝）阶梯升至 0.50；去掉开放式探索（黄）长期卡在 0.20 附近、约 38 轮才升到 0.23；去掉自我改进（绿）只爬到 0.39 就平台；红色虚线为开源 SOTA（约 0.51）；
  • 右图（Polyglot Score，约 0.15–0.40）：完整 DGM（蓝）最高爬到约 0.36–0.38；两个消融变体分别只到约 0.18 与 0.28；基线 Aider 约 0.165。

去掉任何一个设计都会显著变差——「能改自己」＋「能回头」缺一不可。

Slide 110Meta-Harness（机制）

Meta-Harness 的思路（底部原文）：「让一个 meta agent 看到全部过往经验，由它决定下一步改什么。」 流程：①文件系统（Filesystem w/ All Experience，目录 1、2、…）保存一切历史 → meta agent 以「Maximize（最大化性能）」为目标提出 harness 代码（Propose Harness Code）→ harness 与 LLM 组成 Harness+LLM 在 Tasks 数据库上评估 → 每次评估的产出（Proposed Code / Reasoning Traces / Eval Score）→ ③ 把全部日志存回文件系统，进入下一轮。

Slide 111Meta-Harness（效果）

结论（底部原文）：「随着时间推移，meta-agent 能利用这些上下文为 agent 构建越来越好的 harness，去解决面向特定领域的问题。」两幅图：

  • 左图（搜索进度）：横轴 Harness Evaluations（0–40+），纵轴 Best Performance (%)（30–55+）。Meta-Harness（红）一路升到约 55–57%；TTT-Discover（青）约 45.7%；OpenEvolve（深蓝）约 42.8%；基线 ACE（灰虚线）约 41%、Few-shot 约 36.5%、Zero-shot 约 33%；
  • 右图（TerminalBench-2 通过率）：模型优化的 harness（红柱）对 human-written（深蓝）：Meta-Harness 37.6 vs 人工版；横向对比其他 harness：Goose 35.5、Terminus-KIRA 33.7、Mini-SWE-Agent 29.8、Terminus-2 28.3、Claude Code 27.5。

Meta-Harness 优化出的 harness 甚至超过了人工写的版本与知名 agent 框架。

Slide 112子章节页：Auto Research (Optimize Anything)

子章节「Auto Research（自动化研究：优化任何东西）」——同样的循环可以泛化到「任何跑在软件上的东西」。

Slide 113Auto-Research（循环机制）

Auto-Research 的循环（底部原文）：「给 agent 代码仓库的访问权。让它头脑风暴、写一个改动。跑实验看改动是否正向。指标提升就保留并在其上继续，否则回滚。记录发现。」 流程图：read context → propose change → commit and train → 判断 metrics improved?—— yes 走绿框 accept (keep change)，no 走红框 revert (git reset)，两路汇入 log to results.tsv，黑色箭头 repeat 回到起点。

Slide 114Auto-Research Prompt（实验循环 prompt 原文）

这是 Karpathy 的 autoresearch 仓库里驱动整个循环的 prompt（"The experiment loop"，要点）：实验在专用分支上跑（如 autoresearch/mar5）；LOOP FOREVER：

  1. 查看 git 状态（当前分支/commit）；
  2. 带着实验性想法直接改 train.py；
  3. git commit；
  4. 跑实验：uv run train.py > run.log 2>&1（重定向一切输出——不要用 tee、别让输出淹没了上下文）；
  5. 读结果：grep "^val_bpb:\|^peak_vram_mb:" run.log；
  6. grep 为空说明跑崩了：tail -n 50 run.log 读堆栈尝试修复，几次不行就放弃；
  7. 把结果记入 tsv（注意：results.tsv 不进 git）；
  8. val_bpb 变低（改进）→「推进」分支，保留 commit；
  9. 持平或变差 → git reset 回到起点。

收尾段：「你是一个完全自主的研究者，尝试、保留或丢弃，并推进分支以持续迭代。如果感觉卡住了可以回退，但应该极其克制地这么做（如果非要的话）。」

Slide 115Auto-Research（83 次实验的进展图）

真实跑出来的结果：83 次实验，只保留 15 次改进（图题）。横轴 Experiment #（0–83），纵轴 Validation BPB（越低越好，0.975–1.000）； 灰点为 discarded（丢弃），绿大点为 kept（保留），绿色阶梯线为 running best。保留的改进按时间序包括： baseline（约 0.998）→「总 batch 524K 减半为 262K（更多步数）」（约 0.991）→「warmdown 0.5→0.7」→「加 5% warmup」→「depth 9、aspect ratio 57」→「x0 lambda init 0.1→0.05」→「unembedding LR 0.004→0.008」→「S5SSL 窗口模式（更多滑窗）」→「短窗口 1/4、1/8 上下文（256 tokens）」→「embedding LR 0.6→0.8」→「RoPE base 10000→50000→100000→200000（三次递进）」→「随机种子 42→137」（约 0.9775）。 大量灰点散布在阶梯线上方——绝大多数尝试无效，但循环保证了整体单调向下（变好）。

Slide 116Optimization with Agents Summary（小结）

本章三条结论：

  • Agent 是相当称职的优化器（relatively capable optimizers）；
  • 给它们一个能记录结果、提出想法、并动手执行的环境，它们就很擅长优化任何「跑在软件上的东西」；
  • 此时最关键的控制点变成了度量/评测（metric/evals）本身——agent 会拼命优化你给的指标，所以指标必须定义正确（否则就是 Goodhart 定律现场）。

Which Strategy to Use（Slide 117–122）

Slide 117章节页：Which Strategy to Use

Slide 118BetterTogether [Soylu et al., 2024]（交替优化）

结论（底部原文）：「有时最好的做法是：先优化 prompt，再优化权重，然后再优化一轮 prompt。」 左侧 Algorithm 1 伪代码非常直白：Π′ ← OptimizePrompts(Φ, X, μ) → Θ′ ← FinetuneWeights(Φ⟨Θ,Π′⟩, X, μ) → Π″ ← OptimizePrompts(Φ⟨Θ′,Π′⟩, X, μ)——prompt 与权重交替迭代。 右侧结果表（HotPotQA / GSM8K / Iris，三个 7–8B 模型）选摘：

  • Vanilla Zero-shot 基线很低：如 Llama-2-7B 只有 13.2/24.0/0.0；
  • 单步策略：Prompt Optimization (Π) 如 Llama-3-8B 上 46.9/77.9/79.3；Weight Optimization (Θ) 普遍不如 prompt 优化；
  • BetterTogether 策略（Π→Θ→Π）在多数组合上最佳：mistral-7b HotPotQA 37.6、llama-2-7b HotPotQA 34.8 与 Iris 65.3；Θ→Π 在 llama-2-7b GSM8K 48.3、mistral GSM8K 66.7、llama-3-8b GSM8K 78.9。

要点：prompt 优化与权重优化不是二选一，交替进行往往最强。

Slide 119GEPA：prompt 优化的样本效率远高于 RL

结论（底部原文）：「Prompt 优化的样本效率（sample-efficient）远高于 RL。」两幅图（横轴都是 rollout 数量 0–25000，圆点=验证性能，星形=测试集性能）：

  • (a) HotpotQA：GEPA（蓝）约 200 次 rollout 就冲到约 57.5，随后到约 59，测试星形约 62.5（约 6500 处）；MIPROv2（绿）约 55.5–57.7；GRPO（橙）缓慢爬到约 52.4，测试仅约 43.7（耗尽约 23500 rollouts）；Baseline 星形约 42.4；
  • (b) IFBench：GEPA 约 500 次 rollout 升至约 79.5，测试约 83.5；MIPROv2 约 74.5 升至约 82.5；GRPO 缓升至约 63.5（测试约 35.8）；Baseline 约 66.3。

GEPA 用不到 GRPO 几十分之一的 rollout 拿到更高的分——当环境交互昂贵时这是决定性优势。

Slide 120OpenThoughts-Agent：权重优化更能吃数据

硬币的另一面（底部原文）：「权重优化更吃数据（data hungry），但能随着成千上万的样本持续变强。」三幅图与 Slide 77 同源：

  • SWE-Bench Verified (100)：OT-Agent Qwen3-32B 从 316 条到 100K 一路 16→19→30.7→35→48.5→55.7；SERA (swe-agent) 中途到 53 后回落至 52；Base 基线仅约 4；
  • Terminal-Bench 2.0：OT-Agent 32B 13.5→11→17→17→21.5→26.2；Nemotron 32B 约 25.5；基线约 2–4.2；
  • All Average：OT-Agent 32B 25→26.5→31→32→39.5→45.3，曲线未见饱和。

与 Slide 119 对读：prompt 优化省样本但天花板出现早；权重优化前期性价比低，但数据管够时上限更高。

Slide 121Reasons to use context optimization（何时选上下文优化）

三个选上下文优化的理由：

  • 为 API 访问的模型做优化：一些很强的模型不开放微调（fine-tuning）入口——只能动 prompt；
  • 需要频繁、快速地重跑优化：上下文优化比权重优化跑得更快、基础设施更简单；
  • 环境交互成本高昂：上下文优化的样本效率更高（见 Slide 119 GEPA vs RL）。

Slide 122Reasons to use weight optimization（何时选权重优化）

三个选权重优化的理由：

  • 上下文优化失灵时：小模型有时几乎不会听指令（instruction following 能力太弱），prompt 调不动；
  • 有强 teacher、想要更便宜的模型：直接蒸馏（distill）进一个 student 模型往往有效（见 On-Policy Distillation）；
  • 上下文已经太长：prompt 优化会让 prompt 越来越复杂（context-bloat），有时该用权重优化「把知识烧进参数里」，给上下文减负。
