一、RAG 收尾：RAG 的局限

Wrap up RAG（Slide 4–13）

Slide 4Issues with RAG（RAG 的问题，九宫格总览）

承接上一讲，RAG 的问题可按三个环节归类：

  • 检索侧（Retrieval）：召回上限（Recall ceiling，证据缺失限制智能体）、过期索引（Stale index，嵌入未更新）、权限泄漏（Permission leak，使用了无权访问的内容）；
  • 阅读器侧（Reader）：迷失在中间（Lost in the middle）——位置偏差（高亮强调）、干扰（Distraction，相似但不相关的内容）、证据冲突（Evidence conflict，来源之间或与参数化知识矛盾）；
  • 循环侧（Loop）：误差累积（Compounding error，早期错误影响后续决策）、无停止规则（No stopping rule，缺乏明确终止条件）、提示注入（Prompt injection，检索到的文本劫持智能体）。

Slide 5Problem: How many documents can we use?（问题：能用多少文档？）

一个自然的想法：与其费力检索，不如直接把大量文档塞进上下文。本页给出输入上下文示例——三段文档（其中第二段加粗标出与问题相关）， 问题为「谁获得了第一个诺贝尔物理学奖？」（who got the first nobel prize in physics），期望答案为 Wilhelm Conrad Röntgen（威廉·康拉德·伦琴）。问题是：当文档数量增长时，模型还能从中找到并利用证据吗？

Slide 6LM's can't pay attention to the entire context（LM 无法关注整个上下文，Liu et al., 2023）

Liu et al. (2023) 的多文档问答实验：检索 10/20/30 篇文档拼进上下文，把答案所在位置沿上下文扫描， 模型精度呈 U 形曲线——答案放在开头或结尾时表现好，放在中间时明显变差。 参测模型包括 claude-1.3、claude-1.3-100k、gpt-3.5-turbo-0613、gpt-3.5-turbo-16k-0613、mpt-30b-instruct、longchat-13b-16k。 两个参考基准：最佳闭卷（Best Closed-Book）为 GPT-3.5-Turbo 约 56%；最佳 Oracle（只喂入相关文档）为 GPT-3.5-Turbo 约 88.5%。 可见多文档输入远达不到「只给相关文档」的效果。

Slide 7In practice: LMs cannot use many documents（实践中：LM 用不了很多文档）

检索器召回（contriever，黄色曲线）随文档数增加缓慢上升，到 50 篇时约 90%； 但 RAG 整体精度在 10–20 篇文档后就迅速饱和（约 55–60%）。 瓶颈不在检索器找不到证据，而在阅读器无法有效利用越来越多的上下文。

Slide 8LLMs citation and hallucinations (1)（LLM 的引用与幻觉）

RAG 的独特好处之一是能引用来源；但这些引用本身也是 LLM 生成的，因此引用同样可能被幻觉出来。 本页示例为 Bing Chat 的多伦多行程规划回答，正文带编号引用（1–5），底部列出 Learn more 来源 （cntower.ca、travel.usnews.com、bing.com、rom.on.ca、tripadvisor.com）——引用「看起来」可靠，但未必真实或相关。

Slide 9LLMs citation and hallucinations (2)（Liu et al., 2023）

对四家商用搜索增强聊天机器人的评测（Liu et al., 2023）：

指标Bing ChatNeevaAIperplexity.aiYouChat均值
感知效用（Perceived Utility，1–5）4.344.484.564.624.50

Slide 10LLMs citation and hallucinations (3)（幻觉引用进入学术论文）

幻觉引用问题已从聊天机器人蔓延到学术写作：

  • GPTZero 分析了 4841 篇 2025 年录用论文，其中 100+ 篇确认存在幻觉引用（NAZAR SHMATKO，2026 年 1 月 21 日）；
  • ICLR 官方博客《Taking Actions on Hallucinated References》宣布：对含幻觉参考文献的投稿予以 desk reject（直接拒稿）。

Slide 11Pressure Testing Claude-2.1 200K（Needle In A HayStack）

「大海捞针」压力测试：把一条事实随机插入不同深度的文档中，在不同上下文长度（1K→200K tokens）下测试 Claude-2.1 的检索精度。 结果随上下文长度增长，检索精度整体下降——超长上下文的「全量塞入」路线并不可靠。

Slide 12Pressure Testing GPT-4 128K（Needle In A HayStack）

对 GPT-4（gpt4-1106-preview，128K）的同类测试：当事实被放在文档深度的 10%–50% 区间、且上下文较大时，开始出现退化。 测试工具开源：github.com/gkamradt/needle-in-a-haystack。

Slide 13Issues with RAG（小结回顾页）

收束 RAG 部分：检索侧（召回上限、过期索引、权限泄漏）、阅读器侧（迷失在中间、干扰、证据冲突）、 循环侧（误差累积、无停止规则、提示注入）——这些局限正是本讲转向「工具使用」的动机。

二、为什么需要工具

Why tools?（Slide 14–17）

Slide 14Lecture Overview（进度页：进入「为什么需要工具」）

进度页：第一部分「Wrap up RAG」已完成（变灰），当前进入第二部分「为什么需要工具」（Why tools?）。

Slide 15LLMs Cannot Solving That?（LLM 算不了？）

LLM 在计算任务上不可靠：GPT-4 的多位数乘法精度仅约 59%； o1-mini 的位数热图显示，随着参与运算的数字位数增加，精度持续下降。计算正是需要工具的第一类场景。

Slide 16LLMs Struggle as Task Complexity Increases（任务复杂度上升，LLM 表现下滑）

Dziri et al. (2023) 的结果：随着任务的组合深度（步数）增加，LLM 的精度系统性下降。 多步推理链中每一步的小误差会复合放大——这是需要工具把「可靠子步骤」外包出去的第二重动机。

Slide 17Why Tools?（为什么需要工具）

把「LLM 为什么需要工具」归纳为三类缺口，每类对应一种工具方案：

  • 不能算（Computation）：算术、排序、聚合等确定性计算不可靠 → 计算器/代码执行工具；
  • 训练没见过（Knowledge）：训练截止后的新知识、私有数据 → 检索/搜索工具；
  • 够不着（Access / Interaction）：发消息、下单、改数据库等真实世界动作 → 可执行的工具/API。

（页内配图以一张 SpongeBob 梗图形象化「LLM 独自硬撑 vs 借助工具」的对比。）

三、什么是工具

What are tools?（Slide 18–20）

Slide 18What Are Tools?（什么是工具）

工具的定义：工具是通往外部程序的函数接口（function interface）—— 语言模型负责生成函数调用与参数，由外部程序执行并返回结果。 参考：Wang et al., arXiv:2403.15452 (2024)。

Slide 19Scenarios of Tool Use（工具使用的五类场景）

工具使用可归纳为五类场景（每类配示例签名）：

  • 知识访问（Knowledge access）：获取训练语料之外/之后的信息（如搜索）；
  • 计算（Computation）：可靠的数值/符号计算（如计算器）；
  • 交互（Interaction）：与外部系统/用户通信（如发消息、下单）；
  • 非文本（Non-textual）：处理图像、音频、视频等非文本模态；
  • 专项技能 LMs（Special-skilled LMs）：调用在特定任务上更强的专用模型。

Slide 20Basic Tool Use Examples（基础工具使用示例）

两个最小示例，演示「模型生成调用 → 外部执行 → 结果回填」的完整回路：

  • 计算器：17423 × 892 → 工具返回 15,541,316；
  • 天气：调用 check_weather() → 经 API 查询 → 返回 sunny。

四、学习调用工具：Toolformer 及其变体

Learning to call tools: Toolformer（Slide 21–35）

Slide 21Lecture Overview（进度页：进入 Toolformer）

进度页：Wrap up RAG、Why tools?、What are tools? 三部分已完成（变灰），进入「学习调用工具：Toolformer」。

Slide 22LLMs can teach themselves to use tools（LLM 能自学使用工具，Schick et al., 2023）

Toolformer（Schick et al., 2023）让 LM 自己学会：调用哪些 API、何时调用、传什么参数、以及如何最好地把结果融入文本。 方法采用自监督学习，每个 API 只需少量演示（a handful of demonstrations）。右侧四个内嵌调用示例：

  • 问答 API：QA("Who is the publisher of The New England Journal of Medicine?") → Massachusetts Medical Society；
  • 计算器：Calculator(400 / 1400) → 0.29；
  • 机器翻译：MT("tortuga") → turtle；
  • 维基搜索：WikiSearch("Brown Act") → The Ralph M. Brown Act is an act of the California State Legislature…。

Slide 23Toolformer: Candidate Tools（候选工具）

Toolformer 使用的五类候选工具：问答系统（Q&A system）、计算器（calculator）、搜索引擎（search engine）、翻译系统（translation system）、日历（calendar）。 图示每类的输入→输出示例：

  • 问答：「What other name is Pittsburgh known by?」→ The Steel City；
  • 搜索：「War memorial Flodden」→「[…] was created in memory of the Battle of Flodden.」；
  • 计算器：3435*235/9 → 89691.67；
  • 日历：∅ → Thursday, March 10, 2019；
  • 翻译：「Os Melhores Escolas em Jersey」→ The Best Schools in Jersey。

Slide 24Toolformer: Method（方法总览）

方法两步走：构造一个用 API 调用增强（augmented）的新数据集，再用该数据集微调 GPT-J（6B）。 流水线三步：① Sample API Calls（采样候选调用）→ ② Execute API Calls（执行调用）→ ③ Filter API Calls（按效用过滤）。 示例：原文「Pittsburgh is also known as the Steel City.」经增强后变为 「Pittsburgh is also known as [QA(What …? → Steel City)] the Steel City.」——只保留真正降低预测损失的调用。

Slide 25Toolformer: (1) Sample API Calls（采样 API 调用）

对输入 x，选出满足 p_i > τ_s 的位置 i，再在这些位置采样 API 调用候选 c_i^1, c_i^2, … c_i^m，其中 p_i = p_M(<API> | P(x), x_{1:i-1})。 采样本身用少量演示引导：提示形如「Your task is to add calls to a Question Answering API to a piece of text […] Input: Pittsburgh is known as the Steel City. Output:」，模型输出带内嵌调用的文本。

Slide 26Toolformer: (2) Execute API Calls（执行 API 调用）

实际执行这些 API 调用，并过滤掉所有未能降低后续 token 损失 L_i 的调用。 示例：c_i^1（What other name is Pittsburgh known by?）执行后得到 r_i^1 = Steel City； c_i^2（Which country is Pittsburgh in?）得到 r_i^2 = United States。

Slide 27Toolformer: (3) Filter API Calls（过滤 API 调用）

效用判定基于加权交叉熵损失：L_i(z) = −Σ_{j=i}^{n} w_{j−i} · log p_M(x_j | z, x_{1:j−1})（权重随距离衰减）。比较两个量：

  • L_i^+ = L_i(e(c_i, r_i))：同时插入 API 调用与其执行输出；
  • L_i^− = min(L_i(ε), L_i(e(c_i, ε)))：不调用、与「调用但不给输出」两者取较小。

仅当 L_i^− − L_i^+ ≥ τ_f（收益超过阈值）时保留该调用——即调用必须确实帮助预测后续文本。

Slide 28Toolformer: (3) Filter API Calls - Example（过滤示例）

以预测「the Steel City」为例，记 L•(PREFIX) = −log p(the Steel City. | PREFIX)：

  • A. 无 API 调用（Pittsburgh is known as）：2.5；
  • B. 调用但不执行（…[QA("What other name is Pittsburgh known by?") → ?]）：2.1；
  • C. 调用并执行（…→ Steel City]）：0.8。

Usefulness = min(L_A, L_B) − L_C = min(2.5, 2.1) − 0.8 = 1.3 > 0，故保留该调用。

Slide 29Example Text and Usefulness Scores（效用分数示例）

三个增强文本示例与对应 Usefulness 分数：

  • 2.11：「The WL will be open on Friday, [Calendar() → Today is Thursday, March 9, 2017.] March 10, and Sunday, March 19 for regular hours.」——日历调用有助于推断「Friday」；
  • 1.59：「…Venus' main temperature to be 499 K rather than 735 K which is [Calculator(735 / 499) → 1.47] 1.47 times hotter.」——计算器给出倍数；
  • −1.23：「The last time I was with [QA("Who was the last time I was with?") → The Last Time] him…」——负分：调用无助于预测，会被过滤掉。

Toolformer（6B）与基座 GPT-J (6B)、大 30 倍的 GPT-3 (175B) 对比：

Slide 31GPT-2 Models with and without Toolformer（不同规模 GPT-2 对比）

在 LAMA、Math、QA 三类基准上，随模型参数（M）增加：开启 Toolformer（蓝线）的精度始终高于关闭版（红线，Toolformer disabled）， 且在远小于 GPT-3（紫虚线）的规模上就达到甚至超过 GPT-3 水平——工具学习能替代一部分模型规模。

Slide 32View Tools as "Words"? Toolken GPT（把工具当「词」？Hao et al., 2024）

ToolkenGPT（Hao et al., 2024）把每个工具表示为一个新 token（「toolken」）并学习其嵌入； 一旦某个 toolken 被触发，LM 就接着补全该工具的执行参数。词表由普通词与三类 toolken 组成（KB：winner_of/father_of；Math：square/GCD；Robot：grab/walk）。 花园示例（长 64 米宽 48 米，划分最大正方形区块）：推理模式先调用 GCD(64, 48) 得边长 16 米， 再切换工具模式执行 square(16) → 256，最后把结果填回文本——三步：① 模式切换、② 调用工具、③ 回填文本。

Slide 33ToolkenGPT Framework（框架流程）

LLM 统一预测下一个 token（词或 toolken）：P(t_i | t_<i) = softmax([W_ν; W_τ] · h_{i−1})（词嵌入矩阵与 toolken 嵌入矩阵拼接）。五步流程：

  • Toolken predicted：预测出 toolken（模式切换）；
  • Generation pauses：生成暂停，上下文移入新提示；
  • Tool-mode prompt：工具模式提示，含 [tool](args) 语法的演示；
  • Arguments filled：由上下文学习（ICL）补全参数；
  • Tool executes：工具执行，返回值重新进入推理模式。

Slide 34Learning Toolken Embeddings（学习 toolken 嵌入）

训练语料改写示例「the area is 256 square feet」：原序列中的结果 token「2 5 6」在改写序列 s′ 中被替换为 [square]（在第一个结果 token 处预测出 toolken）加两个 [N/A]（结果 token，在损失中跳过）。 损失只在 toolken 位置计算：L(W_τ) = Σ_{(s,s′)∈D} Σ_i −log P(t′_i | t_<i) · 𝟙[t′_i ≠ N/A]。 训练数据：带 ground-truth 工具调用的数据集，以及合成数据。

Slide 35ToolkenGPT involving different numbers of tools（不同工具数量的表现）

左表（GSM8K-XL (4) / FuncQA (13) One-Hop / Multi-Hops）：0-shot ChatGPT 0.17 / 0.55 / 0.09；CoT 0.18 / 0.20 / 0.03； ReAct 0.32 / 0.57 / 0.06；ToolkenGPT 0.33 / 0.73 / 0.15（各项最优）。 右图：随测试集所用关系（工具）数从 30 增到 234，ToolkenGPT (sup) 保持约 0.95 以上基本不掉， ToolkenGPT (syn) 从约 0.6 降到 0.26，而 ICL / ICL (desc) / Prompting 均显著下滑——嵌入化的工具表示在工具数量扩展上更稳。

五、扩展到海量工具：ToolLLM 与 Gorilla

Scaling to many tools: Gorilla（Slide 36–45）

Slide 36Lecture Overview（进度页：进入「扩展到海量工具」）

进度页：前四部分（含 Toolformer）已完成（变灰），进入第五部分「扩展到海量工具：Gorilla」。 该部分同时涵盖把工具规模推向 16k 的 ToolLLM/ToolBench。

Slide 37ToolLLM: Enable LLMs to Use 16k+ APIs（ToolLLM：让 LLM 用上 16k+ API）

ToolLLM：微调 LLaMA 得到 ToolLLaMA，并为其配备一个神经 API 检索器， 为每条指令推荐合适的 API。数据流水线：API Collection（源自 RapidAPI）→ Instruction Generation → Solution Path Annotation （由 ChatGPT 辅助）→ 汇成 ToolBench → 对 LLaMA 做 SFT 得到 ToolLLaMA。 代码：github.com/OpenBMB/ToolBench。

Slide 38ToolLLM: Enable LLMs to Use 16k+ APIs（训练 + 推理全流程）

同一张图补全推理流程：新指令先经 API Retriever 检索出 Retrieved APIs（相关 API 集合）， 连同指令一起交给 ToolLLaMA 迭代执行（×N，调用真实 RapidAPI），产出 Final Answer，并由 ToolEval 评估。训练与推理共用同一套 API 检索器与数据构建机制。

Slide 39Arising Issue in Tool Use and Hallucination（工具使用中的幻觉问题）

提示：「Help me find an API to convert the spoken language in a recorded audio to text using Torch Hub.」三个模型给出的调用代码：

  • GPT-4：torch.hub.load('snakers4/silero-models', 'asr', source='local') —— Hallucinate!（不存在的模型名/参数）；
  • Claude：torchaudio.pipelines.WAV2VEC2_ASR_PIPELINE("audio.wav") —— Wrong library!（用错了库）；
  • Gorilla：torch.hub.load('snakers4/silero-models', 'silero_sst') + asr_model.transcribe(audio_path) —— Good to go!

闭源大模型会「凭空捏造」API 签名，而基于真实 API 库训练的 Gorilla 能给出可执行的调用。

Slide 40Gorilla: LLMs connected with massive APIs（Gorilla：连接海量 API 的 LLM，Patil et al., 2023）

Gorilla（Patil et al., 2023）：数据集构建——1,645 条 API 调用，其中 Torch Hub 94 条（穷尽）、 TensorFlow Hub v2 626 条（穷尽）、HuggingFace 925 条（每个 domain 取 Top 20）；用 self-instruct 加上下文示例生成 16,450 组 {instruction, API} 对，用于训练 Gorilla-7B。 推理：用户说「I want to see some cats dancing in celebration!」→ Information Retriever 从 API Database 检索参考 API → Gorilla 生成调用 StableDiffusionPipeline.from_pretrained(stabilityai/stable-diffusion-2-1) → 执行得到猫咪跳舞图像（Execution Results!）。 该回路既可走检索，也可纯零样本（Zero-shot）。

Slide 41Data: Scaling to Many Tools（数据：扩展到海量工具）

Slide 42Retrieval Aware Training（检索感知训练，RAT）

Retrieval Aware Training (RAT) 的三要点：

  • 微调模型学会使用或忽略检索到的上下文；
  • 在指令微调阶段同时引入正确与错误的检索结果；
  • RAT 确保模型对低质量检索保持鲁棒——检索错了也能自己纠正，而不是照单全收。

Gorilla 推理支持两种模式：zero-shot 或 retrieval（图示与 Slide 40 相同的检索回路）。

Slide 43AST Sub-Tree Matching to measure hallucination（AST 子树匹配度量幻觉）

把模型生成的调用（如 torch.hub.load('pytorch/vision:v0.10.0', 'densenet121', pretrained=True)） 解析成调用链树（torch → hub → load → pytorch/vision → densenet121 → pretrained=True）， 再检查它是否是真实 API 抽象语法树（AST）的子树（右侧：torch 下含 utils/hub/Tensor， hub 下含 load，load 下含各 repo/model/pretrained 取值）。匹配失败即判定为幻觉调用。

Slide 44Improved accuracy with reduced hallucination（精度提升、幻觉下降）

Slide 46Lecture Overview（进度页：进入「标准接口」）

Slide 47Why Standard Interfaces?（为什么需要标准接口）

思路的转变：

  • 左侧（旧范式）：Change the model to fit the tools——Toolformer、ToolkenGPT、Gorilla 每接入一个新 API 就意味着又一次训练；
  • 右侧（新范式，红框）：Change how the tools are described so any model can use them——REST、函数调用、MCP 在运行时给出 schema，而不是为每个 API 逐一微调。

Slide 48Standard Interfaces: Three Generations（标准接口的三代演进）

三代接口，面向的对象逐层升级：

  • 面向人（Human-facing）— REST API：端点 + 文档；每个服务各自鉴权；LLM 必须读文档并手写请求；没有机器可读契约。示例：GET /v1/weather?city=SF；
  • 面向模型（Model-facing）— Function Calling：每个工具一份 JSON schema；模型输出 name + args；由 harness 校验并分发；schema 存放在代码库中。示例：{"name":"get_weather","arguments":{"city":"SF"}}；
  • 面向生态（Ecosystem-facing）— MCP：一个协议、任意客户端；服务器暴露工具、资源、提示词；运行时发现；一次编写、跨宿主复用。示例：tools/list → tools/call。

Slide 49REST APIs: Tools Over HTTP（REST：HTTP 之上的工具）

REST 示例：GET https://api.weather.com/v1/current?city=Stanford → 200 {"temp_f": 74, "conditions": "sunny"}。四个动词语义：GET 读、POST 建、PUT 改、DELETE 删。 局限：模型必须事先知道 URL、参数名与响应结构。

Slide 50Function Calling: Tools as JSON Schemas（函数调用：工具即 JSON Schema）

工具以 JSON Schema 描述（Tool Schema）：{ "name": "get_weather", "description": "Current weather", "parameters": { "type": "object", "properties": { "city": {"type": "string"} }, "required": ["city"] } }； 模型据此输出（Model Output）：{ "tool_call": { "name": "get_weather", "arguments": {"city": "Stanford"} } }。 三个角色：schema 描述工具输入，tool_call 是模型输出，result 回填给模型。 局限：为一家 API 写的工具，换一家就得重写。

Slide 51Model Context Protocol (MCP)（模型上下文协议）

MCP 是居中的标准化协议（Standardized protocol），两侧双向连接：

  • AI 应用侧：聊天界面（Claude Desktop、LibreChat）、IDE 与代码编辑器（Claude Code、Goose）、其他 AI 应用（5ire、Superinterface）；
  • 数据源与工具侧：数据与文件系统（PostgreSQL、SQLite、GDrive）、开发工具（Git、Sentry 等）、生产力工具（Slack、Google Maps 等）。

延伸阅读：本讲必读材料精讲——MCP 规范。

Slide 52MCP Architecture: MCP Host, MCP Client, MCP Server（MCP 架构三要素）

MCP 的三个角色：MCP Host（AI 应用，如 IDE 或聊天客户端）内含若干 MCP Client（本页 4 个），每个 Client 与一个 MCP Server 维持 Dedicated connection（专用连接）。Server 可以是本地的（Server A：Filesystem；Server B：Database）， 也可以是远程的（Server C：Sentry，由 Client 3 与 Client 4 共同连接）。

Slide 53MCP: Tool Discovery (tools/list)（工具发现）

工具发现相当于问服务器 「What tools do you have?」：

  • REQUEST：{"jsonrpc": "2.0", "id": 2, "method": "tools/list", "params": { "_meta": { … } }}；
  • RESPONSE：{"id": 2, "result": { "tools": [ { "name": "weather_current", "title": "Weather Information", "description": "Current weather for a location", "inputSchema": { "type": "object", "properties": { "location": {"type": "string"}, "units": {"enum": ["metric", "imperial"]} }, "required": ["location"] } }, { "name": "calculator_arithmetic", … } ], "ttlMs": 300000 }}。

服务器返回一个列表；每个工具都有 name、description 与 JSON inputSchema。

Slide 54MCP: Tool Execution (tools/call)（工具执行）

工具执行相当于命令 「Run this tool with these arguments」：

  • REQUEST：{"jsonrpc": "2.0", "id": 3, "method": "tools/call", "params": { "name": "weather_current", "arguments": { "location": "Stanford", "units": "imperial" }, "_meta": { … } }}；
  • RESPONSE：{"id": 3, "result": { "content": [ { "type": "text", "text": "Current weather in Stanford: 68°F, partly cloudy, wind W 8 mph" } ] }}。

name 从已列出的工具中选取；arguments 遵循该工具的 inputSchema； 结果是一个 content 数组，由 host 交还给 LLM。

Slide 55Example: Course LMS API → MCP Tools（示例：课程 LMS API 转 MCP 工具）

把课程 LMS 的 REST 路由映射为 MCP 工具：GET /assignments → list_assignments； GET /submissions → get_submissions；POST /grade → post_grade（写操作，红框标出）。 用 FastMCP 可从 OpenAPI 规范自动生成这些工具：

from fastmcp import FastMCP
import httpx

api = httpx.AsyncClient(
    base_url="https://lms.stanford.edu/api/v1")

spec = (await api.get("/openapi.json")).json()

mcp = FastMCP.from_openapi(
    openapi_spec=spec,
    client=api,
    name="Course MCP",
)

# → list_assignments, get_submissions, post_grade

参考：gofastmcp.com/integrations/openapi。

Slide 56Example: Inbound vs. Outbound Auth（示例：入站与出站鉴权）

MCP server 居中，鉴权分两个方向：inbound（agent → server）用 AGENT_TOKEN； outbound（server → LMS）用 LMS_TOKEN。对应代码：

import os, httpx
from fastmcp import FastMCP
from fastmcp.server.auth.providers.jwt import StaticTokenVerifier

# outbound: server → LMS
api = httpx.AsyncClient(
    base_url="https://lms.stanford.edu/api/v1",
    headers={"Authorization":
        f"Bearer {os.environ['LMS_TOKEN']}"})

# inbound: agent → server
who_may_call = StaticTokenVerifier(tokens={
    os.environ["AGENT_TOKEN"]: {"client_id": "ta-agent"}})

mcp = FastMCP.from_openapi(openapi_spec=spec, client=api,
    name="Course MCP", auth=who_may_call)
mcp.run(transport="http", port=8001)

参考：gofastmcp.com/servers/auth/token-verification。

  • (b) τ-airline 示例轨迹：用户「Change flight」→ 智能体 get_reservation_details[JK9O19] → 读数据库 {'cabin': 'basic_economy', 'created_at': '20240514-1800'…} → 智能体依据政策回复「基础经济舱不可改签，但在 24 小时内可取消并重订，要我操作吗？」→ 用户「那就取消吧」→ 智能体 cancel_reservation[JK9O19] → 写数据库 {…, 'status': 'cancelled'}。

Slide 64Pass^k to reward reliability and consistency（pass^k：奖励可靠性与一致性）

τ-bench 用 pass^k 奖励可靠且一致的智能体：

  • pass^k = E_task[ C(c,k) / C(n,k) ]——给定 n 次尝试中 c 次成功时，抽样的 k 次全部成功的概率；
  • pass@k = 1 − E_task[ C(n−c,k) / C(n,k) ]——抽样的 k 次中至少 1 次成功的概率。

Slide 67Failure Modes in Tool Use（工具使用的失效模式）

工具使用的失效模式按三个层面归类：

  • 单次调用（Single call）：Selection——选错工具，或本不需要工具却调了；Arguments——编造字段、类型或单位错误；Hallucinated tool——调用根本不存在的 API；
  • 多步链（Multi-step chain）：Sequencing——跳过前置调用、顺序错误；Recovery——对同一个失败调用反复重试，而不是回退换路；
  • 对话（Conversation）：Policy——在规则禁止时仍行动；Interaction——自行假设而不去询问用户；Non-determinism——一次通过、重试却失败（pass^k 要度量的正是这种不一致）。

  • Why tools：LLM 训练时没见过的、或够不着的东西（what LLMs didn't see in training, or can't reach）；
  • Toolformer：LM 自学调用哪些 API、何时调用、传什么参数；
  • Gorilla：在 1.6k API 上训练；用 AST 匹配度量幻觉；
  • REST / function calling / MCP：从手写请求到 tools/list、tools/call；
  • BFCL / ToolBench / τ-bench：单次调用、多步链、工具-智能体-用户三个评测层面；
  • Failure modes：选错工具、编造参数、顺序错误。

本讲以「RAG 的局限 → 为什么需要工具 → 如何学会调用 → 如何标准化暴露 → 如何评测」为主线：

  • RAG 的局限：多文档上下文呈 U 形精度（迷失在中间）、RAG 在 10–20 篇文档后饱和；引用本身也会被幻觉（商用聊天机器人引用精确率均值 74.5%、召回率均值 51.5%；幻觉引用已进入学术论文并遭 ICLR desk-reject）；超长上下文的大海捞针测试同样退化。
  • 为什么需要工具：三类缺口——不能算（GPT-4 多位数乘法仅约 59%）、训练没见过、够不着；工具把可靠子步骤外包出去。
  • 学习调用工具：Toolformer 用「采样→执行→按损失过滤」自监督构造含 API 调用的数据集，6B 模型在数学/时间任务上反超 175B GPT-3；ToolkenGPT 把工具做成新 token（toolken），234 个工具下精度不掉。
  • 扩展到海量工具：ToolLLM/ToolBench 从 RapidAPI 爬 6000+ API、ChatGPT 标注解法路径；Gorilla 用 1645 条真实 API + GPT-4 自指令生成 16,450 对训练，RAT 保证对低质量检索鲁棒，AST 子树匹配度量幻觉，精度更高且幻觉更少。
  • 标准接口：范式从「改模型适配工具」转向「改工具描述适配任意模型」；三代演进 REST（面向人）→ Function Calling（面向模型，JSON schema）→ MCP（面向生态，tools/list + tools/call，运行时发现、一次编写跨宿主复用），并用课程 LMS 的 FastMCP 示例演示从 OpenAPI 自动生成工具与入站/出站双向鉴权。
  • 评测：BFCL 覆盖 AST 离线/真实执行/状态评估并测试相关性拒答；τ-bench 引入工具-智能体-用户三方交互与领域政策，用 pass^k 奖励可靠性；失效模式按单次调用（选错/编造参数/幻觉工具）、多步链（顺序/恢复）、对话（政策/交互/非确定性）三层归类。
