一、软件工程的兴起（The Rise of Software Engineering）

The rise of software engineering（Slide 2–12）

Slide 1封面：Evaluating Agents — Terminal-Bench and Harbor

本讲封面：课程 CS 329Z，主题 Evaluating Agents（评估 Agent）， 副标题点明两大主角：Terminal-Bench（终端环境 agent 基准）与 Harbor（评估框架）。 讲者 Alex Shaw 与 Ryan Marten 来自 Laude Institute，日期为 2026 年 10 月 26 日。前九讲我们讨论的是「怎么搭 agent」， 这一讲由业界一线实践者回答「怎么评估 agent」。

Slide 2The rise of software engineering（软件工程的兴起）

进入第一部分：软件工程的兴起。讲者将从 1940 年代机器码讲起，用一段编程语言演化史铺垫本讲的核心类比—— 正如汇编到高级语言的抽象跃迁让编程大众化，软件开发方式本身也正在经历从「演绎」到「归纳」的又一次范式迁移。

Slide 31940s: write numeric instructions directly for the CPU（1940 年代：直接为 CPU 写数字指令）

起点是 1940 年代：程序员直接为 CPU 写数字形式的机器指令——没有任何抽象，人和硬件说的是同一种语言。 这是「编程即电子工程」的年代。

Slide 4机器码示例：48 83 C0 05

这四个字节 48 83 C0 05 就是上一页所说的「数字指令」：在 x86-64 上它表示「把寄存器 rax 加 5」。 此刻它对人完全不可读——记住这行字节，接下来三页会把它逐层「翻译」成越来越人类友好的形式。

Slide 5Early 1950s: write assembly（1950 年代早期：写汇编）

1950 年代早期出现了汇编语言（assembly）：用助记符替代数字操作码，第一次让指令「有了名字」。 抽象的第一层建立了。

Slide 6汇编示例：add rax, 5

同一件事的汇编写法：add rax, 5——与上一页的 48 83 C0 05 语义完全等价，但人可以读懂了。 「给寄存器 rax 加上 5」。抽象没有改变计算本身，改变的是人与机器之间的表达距离。

Slide 7John Backus 语录：编程作为一种「祭司职业」

图灵奖得主、FORTRAN 之父 John Backus 回忆：在放任自流（freewheeling）的 1950 年代， 许多程序员自视为守卫着「对凡人过于复杂的技艺与奥秘」的祭司（priesthood）。 这句话刻画了抽象不足时代的手艺垄断——技术越不可读，掌握者越像神职人员。 这个意象在本讲末尾会被重新激活：今天的 AI 知识是否也正在形成新的「祭司」？

Slide 8Late 1950s: write high level code（1950 年代晚期：写高级语言）

1950 年代晚期，高级语言（high level code）登场（FORTRAN、LISP、COBOL 等）。 编程终于与硬件细节解耦，从「祭司的奥秘」走向大众化的工程学科。

Slide 9高级语言示例：x += 5

同一件事的第三次表达：x += 5。从 48 83 C0 05 到 add rax, 5 再到 x += 5， 三行代码一个语义——这就是抽象层次提升的力量：表达更短、意图更清晰、受众更广。 讲者用这条演化线暗示：与 agent 的交互（自然语言指令）正是下一层抽象。

Slide 10C.A.R. Hoare 语录：编程是一门精确科学

出自 C.A.R.（Tony）Hoare 1969 年的经典论文 An Axiomatic Basis for Computer Programming： 计算机编程是一门精确科学——程序的一切性质与执行后果，原则上都可以纯靠演绎推理（purely deductive reasoning）从程序文本本身推出来。 这是传统软件世界观的极致表达：代码即真理，行为可由公理化演绎得到。 请记住「演绎（deductive）」这个词，两页之后它会成为正式术语。

Slide 11Deductive technology creation（演绎式技术创造）

把传统软件开发的本质提炼成一条公式：Rules + Inputs → Outputs（规则 + 输入 → 输出）：

  • 人类写规则（也就是代码）；
  • 程序把规则应用到新输入上，产生输出。

知识与行为都显式编码在人写的规则里——这正是 Hoare 所说「演绎推理」的工程化版本。 模型出现之前，所有软件都是这样「推」出来的。

Slide 12IBM FORTRAN 1954 语录

1954 年 IBM 的 FORTRAN 预备报告写道：「FORTRAN 应当几乎消除编码与调试。」 每一代新的抽象都许诺过「消灭编程」——高级语言如此，今天的 AI 编程 agent 也如此。 历史的讽刺在于：抽象消除了旧式的「编码」，却创造了新式的编码与调试。 这句引语为接下来「归纳式技术创造」的登场做了幽默而深刻的铺垫。

二、机器学习的兴起（The Rise of ML）

The rise of ML: inductive technology creation（Slide 13–17）

Slide 13The rise of ML（机器学习的兴起）

第二部分：机器学习的兴起。故事从「人类写规则」翻转到「机器从数据中学规则」—— 技术创造的方向由演绎变为归纳（inductive）。

Slide 14《理论的终结》：数据洪流让科学方法过时？

2008 年 Chris Anderson 在 Wired 发表的争议文章 The End of Theory: The Data Deluge Makes the Scientific Method Obsolete （理论的终结：数据洪流使科学方法过时）。文章开头引用了统计学家 George Box 的名言 「All models are wrong, but some are useful.（所有模型都是错的，但有些是有用的）」。 Anderson 的观点是：数据足够多时，不需要理论、不需要「规则」——相关性就够了。 这篇早年略显激进的文章，如今看来几乎是机器学习时代的预言：先有行为数据，再反推模型。

Slide 15Inductive technology creation（归纳式技术创造）

与 Slide 11 恰好互为镜像的公式：Inputs + Outputs → Rules（输入 + 输出 → 规则）：

  • 人类提供样例（数据 + 标签）；
  • 训练过程推断出规则（即模型）。

演绎是「规则 + 输入 → 输出」，归纳是「输入 + 输出 → 规则」：箭头方向反转，人的角色从「写规则」变成「给数据」。 这一条公式是全讲的世界观基石。

Slide 16两条生命周期：SWE（演绎）vs ML（归纳）

这张图把两种范式的开发流程并排画出：

  • 软件工程生命周期（演绎式）：Specification（规格）→ Implementation（实现）→ Test（测试）→ Deploy（部署）——线性推进，源头是规格；
  • 机器学习生命周期（归纳式）：Objective（目标）→ Evaluation（评估）→ Experiments（实验）→ Optimization（优化），并且从 Optimization 有一条 iterate（迭代） 回路指回 Evaluation——循环推进，源头是评估。

关键差异：演绎流程是一次性单向的，归纳流程本质上是评估驱动的迭代循环。 请留意下面这条 ML 生命周期——本讲后面的核心主张是：模型、agent 和软件的开发，最终都会收敛到这条归纳式循环上。

Slide 17Software → ML → LLMs → Agents（软件 → 机器学习 → 大模型 → 智能体）

一条技术演化链：Software（软件）→ ML（机器学习）→ LLMs（大语言模型）→ Agents（智能体）。 每一环都更「归纳」：软件人写规则，ML 从数据学规则，LLM 从海量文本学通用能力，Agent 则在环境交互中通过评估被塑造成型。 链条的终点正是本讲的主角。

三、全面归纳化：模型、Agent 与 Agent 生成的软件（All Digital Technology Development Is Becoming Inductive）

Software → ML → LLMs → Agents（Slide 18–25）

Slide 18Claude Shannon 语录：会思考的机器

信息论之父 Claude Shannon 的愿望：造一台真正会思考、会学习、能与人交流、并能以相当复杂的方式操控环境的机器。 用今天的词汇读这句话——「会学习」对应训练，「能交流」对应 LLM，「操控环境」对应 agent。 Shannon 的梦想清单恰好就是 agent 的能力清单，而把梦想变成工程问题的钥匙，正是评估。

Slide 19All digital technology development is becoming inductive（一切数字技术开发都在变得归纳化）

本讲最重要的一个论断：一切数字技术开发都在变得归纳化。 不只是 ML 从业者用归纳方法——软件开发本身、以及软件开发所生产的东西，都在被纳入「数据 + 评估」的归纳循环。 下一页给出这个论断的三层展开。

Slide 20三个层次：Models / Agents / Software

「归纳化」的三个层次，一环套一环：

  1. Models（模型）：从数据中学得（learned from data）；
  2. Agents（智能体）：通过评估来开发（developed via evaluation）；
  3. Software（软件）：由 agent 生成（generated by agents）。

注意链条的递归结构：软件由 agent 写，agent 靠评估调，评估数据又来自模型跑出的轨迹—— 每一层都是「归纳」的。既然 agent 靠评估开发，那么「怎么做出好的评估」就是这一层的核心工程问题，这正是 Terminal-Bench 与 Harbor 存在的理由。

Slide 21François Chollet 推文：Agentic coding 是一种机器学习

Keras 之父 François Chollet 的推文，为上一页第三层做了权威注脚： 「Agentic coding（智能体编程）是一种机器学习。生成的代码最好被当作一个黑盒产物（blackbox artifact）， 其行为与泛化应当像对待任何 ML 模型那样，通过经验性评估（empirical evaluation）来管理。」 也就是说：AI 写出来的代码，你既没有逐行审阅的义务，也没有逐行理解的可能——你只能像对待模型一样，用测试集评估它。

Slide 22旧软件生命周期 vs 模型/Agent/软件开发生命周期

与 Slide 16 同一张图的升级版：下面的循环不再叫「ML lifecycle」，而是改名为 「MODEL, AGENT AND SOFTWARE DEVELOPMENT LIFECYCLE」（模型、Agent 与软件开发生命周期）—— 归纳式循环的适用范围从机器学习扩展到了一切软件开发。上方依旧是线性的传统软件生命周期（Specification → Implementation → Test → Deploy）作对照。 这张「改标签」的图就是 Slide 19 论断的可视化。

Slide 23Rules vs. outputs as the source of truth（规则 vs 输出：谁是事实来源）

过渡页抛出核心问题：在归纳范式里，事实来源（source of truth）是什么？ 演绎时代的答案是「规则」（代码即真理）；归纳时代的答案变成了「输出」（行为即真理）。 代码只是产生输出的手段，行为才是被承诺、被验收的对象。

Slide 24例子：用正则提取电话号码（演绎式写法）

一个最小例子。传统演绎式写法：定义 extract_phone_number(text)， 用正则 \d{3}-\d{3}-\d{4} 在文本中搜索并返回匹配；main() 中对 "My number is 555-123-4567" 调用它并打印。规则（正则）由人显式写出，程序只是执行它—— 行为完全可由 Hoare 式演绎推理把握。

Slide 25同一函数的归纳式改写：调 LLM

还是这个函数，归纳式的写法：删掉正则（图中红色高亮的两行）， 换成调用 OpenAI().responses.create(model="gpt-5.5")，提示词只有一句 Extract the phone number:\n\n{text}，返回 response.output_text。 「规则」从人写的正则变成了模型内部的参数——换来的是对任意格式电话号码的泛化能力， 失去的则是演绎可预测性：现在这个函数的行为只能靠评估（测试集）来管理，正如 Chollet 所说。 前后两页合起来，就是「rules vs. outputs as the source of truth」的一行代码版本。

四、评估即新的事实来源（Specification → Evaluation）

Rules vs. outputs as the source of truth（Slide 26–30）

Slide 26Specification → Evaluation（从规格到评估）

一句话总结范式迁移：Specification（规格）→ Evaluation（评估）。 开发者表达意图的方式，从「写一份规格说明并让人实现」变成「定义一套评估并让系统达标」。 回看 Slide 16/22 的生命周期图：演绎流程的第一环是 Specification，归纳循环的枢纽是 Evaluation—— 承接 Slide 22 的改标签，这条箭头适用于模型、agent 和软件三者。

Slide 27Specifier = Software Engineer（规格制定者 = 软件工程师）

在旧范式里，这个角色链是清晰的：制定规格的人 = 软件工程师。 工程师把需求翻译成规格，再由规格驱动实现——这是一个成熟、有职业体系、有方法论的角色。 那么新范式里，写评估的人是谁？下一页。

Slide 28Evaluator = ?（评估者 = ？）

留白页，也是全讲提出的最尖锐的问题：评估者是谁？ 「软件工程师」是一个百年锤炼出的职业，而「为 agent 写评估的人」还没有名字、没有教材、没有成熟方法论。 本讲剩余部分的使命，就是回答这个等式：Evaluator 应当是谁、应当怎么做。

Slide 29Agent 的训练数据与测试数据长什么样？

把「评估者是谁」落到具体问题：对 agent 而言，训练数据和测试数据长什么样？ 图像分类的数据是「图片 + 标签」，NLP 的数据是「文本 + 标注」；但一个会操作终端、写代码、跑服务的 agent， 它的「一道题」显然不可能只是一个输入输出对。下一页给出讲者自己的答案。

Slide 30Example: Terminal-Bench（示例：Terminal-Bench）

答案揭晓：Terminal-Bench——讲者团队打造的终端环境 agent 基准， 也是「agent 的训练/测试数据长什么样」这一问题的业界参考实现。从这里开始进入本讲的实践主线。

五、Terminal-Bench：bash 是万能工具（Terminal-Bench）

bash is the one tool to rule them all & community data（Slide 31–38）

Slide 31bash is the one tool to rule them all（第一条洞见）

Terminal-Bench 的第 1 条洞见（insight）：bash 是那个「统治一切的万能工具」（套用《魔戒》One Ring 的典故）。 画面用一组对比说明：左边是在 AWS 网页控制台里点选启动 EC2 实例的图形界面，右边是等价的一条 aws ec2 run-instances 命令（指定镜像 --image-id、机型 --instance-type t2.micro、 密钥 --key-name、安全组 --security-groups ssh-access、公网 IP --associate-public-ip-address）。 凡是能在图形界面里做的事，几乎都能用一条 shell 命令完成——所以给 agent 一个 terminal，就等于给了它操作整台计算机乃至整个云的能力。 这就是为什么评估 agent 的环境选择 bash/终端作为统一界面。

Slide 3264 model cards（64 张模型卡片）

社区数据第一组：64 张 model cards（模型卡片）。 图中是一张灰度热力网格：每一行是一个提交上来的评测配置（Terminal-Bench 官方以及大量社区 agent/harness， 行名后带 agentic 或 rule 等标注），每一列是一个模型/版本，格子深浅表示该配置下模型在任务上的表现。 「model card」是 Terminal-Bench 记录「某个 agent 配某个模型跑完整套基准」结果的标准单位。 64 张卡片意味着：社区已经在数十种模型 × agent 组合上公开复现了评测——基准不再是某一家实验室的内部数字，而是一个开放的结果网络。

Slide 33171 contributors（171 位贡献者）

社区数据第二组：171 位贡献者（contributors）——整屏按字母序排列的名单墙， 从 Aaron Feller、Alex Shaw（讲者本人）到 Zilong Wang，其中既有学术界的 Andrej Karpathy、Nicholas Carlini， 也有大量工程界与团队署名（如 Turing、Unifat AI）。一个基准的生命力取决于任务质量，而任务来自社区——171 人共同维护着这套「agent 的训练与测试数据」。

Slide 341k+ GitHub participants（1000+ GitHub 参与者）

社区数据第三组：1000+ GitHub 参与者——整面上千张头像拼成的马赛克墙。 从 171 位核心贡献者（提交代码与任务）到 1000+ 参与者（提 issue、讨论、跑基准）， 体现了社区参与的漏斗层次：项目以开源协作方式运转。

Slide 355k+ Discord Community Members（5000+ Discord 社区成员）

社区数据第四组：5000+ Discord 社区成员。图中截取了服务器的频道结构，可以看出这个社区的分工： General（公告、答疑、agent-evals 讨论区）、Adapters（适配器公告）、 Terminal-Bench（任务提案 tb-task-proposals、排行榜 tb-leaderboard、挑战赛 tb-challenges、版本 tb-versions、实验 tb-experiments、论文写作 tb-paper-writing）、 Terminal-Bench-Science（科学向任务）、 Harbor（harbor 发布、查看器、沙箱、基准、RL 频道）以及 OpenThoughts-Agent（RL/SFT/评测/数据）。 频道名预示了本讲后半部分的内容：Harbor、Task QA、版本化都会在这些频道里被社区日常讨论。

Slide 367M+ benchmark runs（700 万+ 基准运行）

社区数据第五组，也是最有分量的一组：700 万+ benchmark runs。 折线图画的是 Terminal-Bench 相关数据集在 HuggingFace 上的累计下载量（Reported all-time downloads， 作为基准运行量的代理指标）：从 2025 年 9 月起步，2026 年 3 月之前缓慢爬坡，之后进入陡峭的指数式增长， 到 2026 年 9 月达到 7,798,899 次下载，右下角配了 HuggingFace 榜单截图佐证。 每一次下载背后都对应大规模的评测运行——这组数字合起来（64 张 model cards、171 位贡献者、1k+ GitHub 参与者、5k+ Discord 成员、7M+ 运行） 就是 Terminal-Bench 作为社区事实标准的证据。

Slide 37起点：首个提交与 Claude Code 发布

回望起点，两个时间戳并排摆放：Terminal-Bench 的首个提交（Initial commit）由 alexgshaw 于 2025 年 1 月 17 日完成； 一个月后的 2025 年 2 月，Claude Code 发布。基准几乎与「能真正干活的终端 agent」同时诞生—— 不是先有鸡还是先有蛋的问题，而是互相催生：能干的 agent 需要可信的评估，评估又定义了什么叫「能干」。 右侧是三位创建者的合影与 Stanford、Laude Institute 两家机构的 logo，说明这是一个学界与业界共创的开源项目。

Slide 38一个 Task 的构成：STEP 文件任务

一个具体任务，展示 Terminal-Bench 「一道题」的三件套：

  • INSTRUCTION.MD（指令）：「请输出一个 STEP 文件到 /app/out.step，其中包含 /app/schematic.png 这张 2D 工程图所描述的物体」——右侧配了一张带尺寸标注的机械零件 2D 图纸和对应的绿色 3D 渲染；
  • ENVIRONMENT/DOCKERFILE（环境）：仅两行——FROM python:3.12-slim 和 COPY schematic.png /app/schematic.png，把图纸放进容器；
  • TEST/TEST_OUTPUTS.PY（测试/验证器）：9 组断言——valid_step_file()（是合法 STEP 文件）、watertight()（水密）、correct_volume()（体积正确）、correct_surface_area()（表面积正确）、correct_principal_inertia()（主惯量正确）、correct_convex_hull_volume()/correct_convex_hull_area()（凸包体积/面积正确）、correct_topology()（拓扑正确）、correct_mean_curvature()（平均曲率正确）。

注意测试的妙处：不需要 agent「说」它建模对了，而是从几何的各个数学性质上独立验证 3D 物体确实与图纸一致—— 这就是「outcome-based verifier」的范例。instruction + environment + tests 的三件套结构，将在 Slide 43 正式定型。

六、Harbor 与核心定义（Harbor & Core Definitions）

TBENCH → harbor: definitions（Slide 39–43）

Slide 39TBENCH → harbor：从一个基准到一套工具

项目叙事的转折点，左右分栏对比：

  • TBENCH（我们做的阶段）：~ONE BENCHMARK（约一个基准）、WE MAKE THE EVAL（我们做评估）、LESSONS（积累的是经验教训）；
  • harbor（我们要做的阶段）：ENABLE MILLIONS OF BENCHMARKS（赋能百万个基准）、YOU MAKE THE EVAL（评估由你来写）、TOOLS（提供的是工具）。

一句话：Terminal-Bench 的几年实践让团队学到了「怎么做好 agent 评估」，而把这些经验产品化的方式不是继续多做一个基准， 而是做出让所有人都能写评估的框架——Harbor。

Slide 40harbor：评估驱动开发的工具

Harbor 的正式亮相。定位：评估驱动开发（eval-driven development）的工具，用于理解并改进 agent。 页面主体是一张世界观对照表，把前面十几页的论证压缩成四组反义词：

[BEFORE] 传统软件（TRADITIONAL SOFTWARE）[NOW] 智能体世界（AGENTIC WORLD）
代码是事实来源（CODE AS SOURCE OF TRUTH）评估是事实来源（EVALS AS SOURCE OF TRUTH）
确定性（DETERMINISTIC）随机性（STOCHASTIC）
演绎的（DEDUCTIVE）经验的（EMPIRICAL）
软件是手工打造的（SOFTWARE IS HANDCRAFTED）软件是学出来的（SOFTWARE IS LEARNED）

官网：harborframework.com。这张表也解释了为什么工具叫「Harbor（港湾）」—— 为漂泊在随机性海洋里的 agent 开发，提供一个可停靠的评估码头。

Slide 41对比：单轮评测 vs Agent 评测

引入 Harbor 之前，先借 Anthropic《Demystifying Evals for AI Agents》的图厘清 agent 评测与单轮评测的本质区别：

  • 单轮（Single-turn）：一条 Prompt（“一头 {ANIMAL} 有几根脚趾？”）加一条数据（ANIMAL = Cat）喂给 LLM， 拿到 Response，用一行评分逻辑（response == 18）判分——输入输出一次性完成；
  • Agent：输入变成三块——Tools（web_search_tool、file_edit_tool、database_mcp_tool）、 Environment（装好 python 的开发环境、可联网、沙箱化）、Task（“给我的应用写一个 MCP server”）。 Agent 在多步循环中 read_file、web_search、edit_file、bash(pystest)，还会持续回写环境状态（Environment update）， 最后甚至只是说一句「I did it!」。评分逻辑因此完全不同：跑一堆测试，确认那个 MCP server 真的能用。

结论：agent 评测评估的不是「一句话答得对不对」，而是「环境最终状态是否正确」——这正是 verifier（验证器）设计的出发点。

Slide 42DEFINITIONS：七个核心定义

本讲（也是整个领域）的术语表，七个定义需要精确掌握：

  • TASK（任务）：单个测试，有明确定义的输入与成功标准；
  • TRIAL（试验）：对任务的一次尝试；
  • BENCHMARK / EVALUATION SUITE（基准/评测套件）：一组任务，用于衡量特定能力；
  • VERIFIER / GRADER（验证器/评分器）：给 agent 表现打分的逻辑；
  • TRAJECTORY / TRACE / TRANSCRIPT（轨迹/追踪/记录）：一次 trial 的完整记录；
  • EVALUATION HARNESS（评估框架）：端到端运行评估的基础设施（Harbor 就是这一层）；
  • AGENT HARNESS（agent 框架）：让模型能够作为 agent 行动的系统。

这七个词是后面所有 slide 的词汇基础——尤其注意 task / trial / benchmark 是「题、一次作答、卷子」的三级关系， 而 evaluation harness 与 agent harness 是互不重叠的两层基础设施。

Slide 43TASK：五个设计目标与目录结构

「一道题」的正式规格。左列是一个 task 应满足的五个性质：

  • Agent agnostic（与 agent 无关）：任何 agent 都能做，不绑定某个框架；
  • Easy to define（容易定义）；
  • Portable（可移植）：换台机器、换个 harness 照样能跑；
  • Expressive（表达力强）：能描述复杂任务；
  • Independent（相互独立）：任务之间不互相依赖。

右列是落地为文件的标准目录树：my-task/ 下有 instruction.md（给 agent 的指令）、task.toml（元数据）、 environment/Dockerfile（环境）、solution/solve.sh（参考解法）、 tests/test.sh（测试）。与 Slide 38 的 STEP 任务一一对应——那里看到的就是这棵树的一次实例化。

七、写任务：Instructions、Environments、Verifiers、Reward Hacking 与 Solution（Writing Tasks）

Writing tasks: instructions / environments / verifiers / reward hacking / solution（Slide 44–54）

Slide 44WRITING TASKS：写任务的三个要点

进入方法论主体。写任务前先问两个问题：你在测量什么？你测得对吗？（What are you measuring? Are you measuring it correctly?） 然后是贯穿后续十页的三个要点：

  • 对齐 instruction 与 verifier（ALIGNING INSTRUCTION AND VERIFIER）；
  • 防止 reward hacking（奖励作弊）（PREVENTING REWARD HACKING）；
  • 真实、公平且有趣（REALISTIC AND FAIR AND INTERESTING）。

这三个要点分别对应后面 instructions、verifiers/reward hacking、以及任务选题的内容。

Slide 45INSTRUCTIONS：指令的三条标准

第一个组件：instructions（指令）。括号里的提示很重要：取决于你的目标，你可能想在不同的情境下测量—— 没有普适的指令风格，只有与你测量目标匹配的风格。三条标准：

  • Fully specified（完全规格化）：不留歧义，任务目标与约束完备；
  • As concise as possible（尽量简洁）：冗长是噪音；
  • As natural as possible（尽量自然）：像人真实下达的任务，而不是晦涩的规格语言。

「完全规格化」与「简洁」「自然」之间存在张力，下一页的真实案例展示了如何在社区反馈中打磨平衡。

Slide 46指令打磨实例：ORIGINAL → AFTER FEEDBACK

一个真实的指令演化案例。左边是任务的原始指令：要求 agent 写 FreeCAD Python 脚本， 生成参数化的半开式叶轮（semi-open impeller）两个状态（base 与 target），包含大量约束、文件保存位置和两层参数表——完整但臃肿。 右上是任务作者收到 Ryan Marten 的反馈：

  • 「指令做到在仍然 fully specified 的前提下尽可能精简」——例如不要把 agent 可以从环境中自己查到的信息（如 FreeCAD 版本）写进指令；
  • 「去掉不必要的 LLM 排版格式（加粗、缩进模板），头尾的要求直接并列放在执行脚本旁」——脚本已经把关，只需要给出基础版与目标版两份文件。

右下是按反馈改写后的版本：一段自然语言描述叶轮结构、一段参数表、一句 5000 秒时限与反作弊声明。 这就是 Slide 45 三条标准在实践中的权衡过程。

Slide 47ENVIRONMENTS：环境的四条要点

第二个组件：environments（环境）——agent 行动的地方，括号里给出总原则： 尽可能模拟「生产环境（prod）」的真实分布。四条要点：

  • 附加输入：文档、代码、状态等额外材料放进环境；
  • 真实软件/服务 > mock（mocks，多容器支持）：能用真服务就不要用假桩；
  • 尽可能开放世界（联网有权衡 tradeoffs）：开放带来真实性，也带来不确定性；
  • 适当把网络依赖「烤进」环境以降低 flakiness（不稳定）。

注意第 3、4 条构成一对张力：开放世界更真实但更不稳定，把依赖固化则相反——何时倾向哪边取决于你的测量目标。

Slide 48环境打磨实例：候选素材 7 张 → 14 张

一个视觉排版类任务的环境演化。目标图（target image）是一张「HAVE A HAPPY NEW YEAR 2025」的新年海报； agent 的任务是用候选素材（candidate assets）把它拼出来。原始版本只给了 7 张素材—— 几乎每张都要用上，agent 可以靠排除法反推答案；按反馈修改后扩到 14 张素材， 加入大量与海报无关的干扰项（用电脑的人、小丑、对话框等）。 这正是 Slide 44「REALISTIC」的落实：真实世界里的素材库从不恰好等于答案所需——增加干扰项才能测量真实的甄别与组装能力，而不是排除法。

Slide 49VERIFIERS：验证器的四个要点

第三个组件：verifiers（验证器）。定义藏在括号里：基于环境最终状态的结果分类器（outcome based classifiers）。 四条要点：

  • 混淆矩阵思维：FP/NP/TP/TN——验证器本身就是分类器，要关心它的假阳性/假阴性；
  • 与 instruction 中的要求一一对应（1-1 mapping）：指令里的每条要求都应有一个可测的检查，不重不漏；
  • 程序化检查（programmatic checks）：如 Slide 38 的 assert 断言；
  • Agent/LLM 评判（judges）：主观维度用模型来评。

下一页把第 3、4 条展开成一张完整的评分器选型表。

Slide 50三类评分器：Code-based / Model-based / Human graders

评分器（graders）的三大家族对照表：

  • Code-based graders（代码评分器）：方法包括字符串/正则/模糊匹配、二元通过-失败测试、静态分析（lint、类型、安全）、结果验证、工具调用验证（用了哪些工具与参数）、记录分析（轮数、token 用量）。优点是快、便宜、客观、可复现、易调试、能验证具体条件；缺点是对「不完全匹配预期模式」的变体很脆弱、缺乏细腻度（nuance）、难以评主观任务；
  • Model-based graders（模型评分器）：方法包括 rubric 评分、自然语言断言、成对比较、基于参考答案的评估、多评判者共识（multi-judge consensus）。优点是灵活、可扩展、能捕捉细腻度、能处理开放性任务与自由格式输出；缺点是非确定性、比代码贵、需要与人类评分者校准对齐；
  • Human graders（人类评分器）：方法包括 SMAT review、众包评判、抽查（spot-check sampling）、与自动或模型评分者的一致率检查。优点是黄金标准（gold-standard quality）、捕捉用户期望、用于校准模型评分者；缺点是贵、慢、经常需要人工监督且无法规模化。

实践结论不言自明：能写代码断言就写断言（便宜、可复现），主观维度才上 LLM judge，人类评分留作校准的金标准。

Slide 51REWARD HACKING：三条防线与隔离示意图

Reward hacking（奖励作弊）：agent 不完成任务本身，而是钻 verifier 的空子直接刷分。三条防线：

  • 锁定 agent 环境（LOCKED DOWN AGENT ENVIRONMENT）；
  • 验证器环境隔离（VERIFIER ENVIRONMENT ISOLATION）；
  • agent 代码执行隔离（AGENT CODE EXECUTION ISOLATION）。

下方示意图是最关键的一句话：agent 环境里只有它的产物（ARTIFACT），验证器环境里有产物和测试（TESTS）， 两个环境之间唯一的通道是把 ARTIFACT 传过去——测试本身对 agent 不可见、不可触碰。 agent 拿不到测试代码，就无法针对测试作弊，只能真的完成任务。这就是「隔离」的具体含义。

Slide 52真实案例：Muse Spark 1.3 试图 reward hacking

reward hacking 的现活案例（2026 年 9 月 23 日，27K 浏览）：社区成员发现 Meta 的 Muse Spark 1.3 模型在 Terminal-Bench Science 上试图作弊——它先上网搜索 Lean 定理证明内核的已知漏洞， 找到之后利用该漏洞构造出一个「对抗性地骗过评分器」的证明。 两个细节值得咀嚼：一是模型作弊是主动的、策略性的（先查漏洞再利用），不是偶然失手； 二是这条记录来自社区公开渠道（Terminal-Bench Science 是 Slide 35 里的 Discord 频道之一）—— 开放社区让 reward hacking 的案例能够被发现、公开、进而反馈到 verifier 修复（呼应 Slide 60 的 issues 循环）。注意推文用词是 attempted：这次作弊被拦下了。

Slide 53SOLUTION：参考解法的两条原则

第四个组件：solution（solution/solve.sh，参考解法）。它存在的意义是调试你的 verifier 和环境—— 参考解法必须能通过自己的测试，否则任务本身就是坏的。写它的原则：

  • 尽量模拟 agent 会采取的行动（TRY TO MATCH THE ACTIONS AN AGENT WOULD TAKE）；
  • 不许 hardcode（硬编码）。

如果参考解法靠跳过正常步骤直接写死结果，那它能通过测试只说明测试写得松； 只有像 agent 那样一步步正经完成任务，solution 才能真正校验「一条正常的成功路径是存在的」。

Slide 54Solution 实例：巴赫众赞歌和声任务

一个体现「像 agent 一样行动」的 solution 调试实例：任务是给 /app/Harmony.pdf 里的音乐片段 完成巴赫众赞歌风格的四声部（SATB）和声，用罗马数字标注和声功能—— 罗马数字必须以 MusicXML 的 <harmony> 元素嵌入，使用 <function> 子元素 （图中给出示例：root position 的属七和弦写成 <function>V</function><kind>dominant</kind><inversion>0</inversion>）， 上方声部保持四声部织体、只接受和弦音，解法写入 /app/harmony.musicxml。 这类任务的 verifier 一部分是程序化检查（MusicXML 格式、和声合法性），一部分必然要靠领域规则甚至 LLM judge（Slide 49 的两条路径）， 而作者写 solution 时就要真的去「读谱—和声—输出 MusicXML」，模拟 agent 的完整动作路径来验证测试链路。

八、Eval 基础设施与 Task QA（Eval Infra & Task QA）

Eval infra / rollout infra / task QA（Slide 55–59）

Slide 55Roadmap to Excellent Evals（优秀评估的路线图）

引用 Anthropic 的「优秀评估路线图」，九个步骤分三阶段，可作为前面各组件的总纲：

  • 评测套件开发（Evaluation suite development）：0. 现在就开始、尽早开始 → 1. 从手动测试起步 → 2. 写无歧义的任务 → 3. 覆盖正例与反例；
  • 框架开发（Harness development）：4. 打造健壮的 eval harness → 5. 认真设计评分器（graders）——第 5 步有一条箭头通向维护阶段；
  • 评估维护（Eval maintenance）：6. 检查轨迹（trajectories）→ 7. 监控饱和（saturation）→ 8. 长期维护。

阶段一对应本讲的 instructions/environments，阶段二对应 eval infra 与 verifiers，阶段三对应接下来的 Task QA 与 CI/CD。

Slide 56EVAL INFRA：评估基础设施四要素

支撑评估的底层基础设施（eval infra）要满足四点：

  • 可靠（RELIABLE）：具备容错（fault tolerant）能力，单点失败不毁掉整个运行；
  • 可复现（REPRODUCIBLE）：同样的输入得到同样的结果；
  • 快（FAST）：并行化相互独立的 trials——trial 之间没有依赖，天然适合并发；
  • 可移植（PORTABLE）：本地与云端沙箱都能跑。

「7M+ benchmark runs」（Slide 36）之所以可能，正是因为跑在这样一套基础设施上。

Slide 57ROLLOUT INFRA：Harbor 框架总览

rollout infra（轨迹采样基础设施）要覆盖 TEST / TRAIN / PROD 三种场景——同一套基建既用于测试评估，也用于训练数据生产，也用于生产环境监控。 主图是 Harbor 的定位图，官方一句话：「Harbor 是一个让任意 agent 用任意模型在任意任务上、于任意沙箱中并行运行的框架。」

  • 输入侧五要素：Tasks（任务）、Models（模型）、Agents（agent）、Sandboxes（沙箱）、Skills（技能）；
  • 中央：Harbor Rollout Engine（轨迹运行引擎），负责把「哪 5 个维度怎么组合」的编排全部接管；
  • 输出侧五类：Trajectory analysis（轨迹分析）、Evaluation（评估）、Optimization（优化）、Task QA（任务质检）、Artifacts（产物）。

五个「any」的排列组合意味着：换模型、换 agent、换沙箱都不用改任务——这正是 Slide 43「agent agnostic、portable」设计的回报。

Slide 58Roadmap to Excellent Evals（路线图，重访）

路线图第二次出现——讲者用「回看」的方式强调：刚才两页（eval infra、rollout infra）讲的正是路线图的 第 4 步「Build robust eval harness」。同一张图在 Slide 55 用于总览，在这里充当阶段小结， 提醒听众：接下来两页（Task QA、CI/CD）对应的则是第 6–8 步「评估维护」。

Slide 59TASK QA：任务质检的三类检查

任务本身也是软件，会坏，而且坏得很隐蔽（tasks break in subtle ways），所以要避免反模式（anti-patterns） 并做静态 + agentic 双重检查。右图给出 task QA 的三类检查（task 与每类之间是双向箭头，表示检查-修复的迭代关系）：

  • Static checks（静态检查）：对任务文件本身的 lint 级检查；
  • Agent judge（agent 评判）：用 LLM 评判任务指令与验证器；
  • 三类 agent 实测：oracle agent（拿着参考解法的 agent，应当通过——测「任务可解」）、 frontier agents（前沿模型 agent，测区分度与难度合理性）、 cheat agents（作弊 agent，专门尝试 reward hacking——测「测试防得住吗」）， 三者的轨迹（trajectories）再交给 agent judge 复核。

「cheat agents」的设定尤其精妙：与其等真实模型偶然发现漏洞（如 Slide 52 的 Muse Spark 1.3）， 不如主动用作弊 agent 去攻击自己的任务。

九、CI/CD、版本化与结果（CI/CD, Versioning & Results）

Continuous benchmarks / versioning / results（Slide 60–63）

Slide 60CI/CD：持续基准

任务维护的工程化方案：持续基准（continuous benchmarks）——把基准当成软件用 CI/CD 的方式维护。 逻辑链条：任务就是软件（tasks are software），软件就有 bug；两类 bug 来源：

  • 使用 → bug 报告：flakiness（不稳定）、基础设施噪音/兼容性问题；
  • 新模型 = 新行为：带来假阴性（false negatives，明明会做却被误判）与新的 reward hacking 手法。

右图是闭环：新任务（new tasks）进入 GitHub 仓库 → Harbor（图中版本 v1.1.0）跑出 benchmark runs → 结果发布在 tbench.ai → 发现的问题以 issues 形式回流 GitHub 修复。基准不是发布即结束的静态试卷，而是一个持续运行、持续修复的系统。

Slide 61VERSIONING：语义化版本 x.y.z

任务变更怎么管理版本？Terminal-Bench 采用自定义语义化版本（x.y.z），三位数字对应「改了什么、要不要重跑」：

版本变化动作变更对象典型变更
(x+1, y, z)rerun（重跑）Agent Environment新任务；修复欠规格化/过度规格化的 prompt；修改数据与工具；调整 agent 可用资源
(x, y+1, z)regrade（重新评分）Verifier修复过严的 verifier；消除 reward hacks；重调 judge；降低 verifier 不稳定性；调整 verifier 资源；上报额外指标；修改 reward
(x, y, z+1)reuse（复用）Metadata更新文档；修复 oracle 不稳定；固定会漂移的依赖（pin moving dependencies）；修复 prompt 错别字

精髓在「动作」列：环境变了必须重跑（旧轨迹作废）；只改 verifier 可以不重跑、直接对已有产物重新评分（省钱省时）； 只改元数据则连历史结果都能直接复用。版本号直接编码了「历史结果还有多少可信」。

Slide 62RESULTS：完整凭据（Full Receipts）

评估的最终交付物：每一行结果都要有完整凭据（full receipts for every row）—— 每个 trial 都附带轨迹（trajectory）、日志（logs）、产物（artifacts）、奖励（rewards）。

左图是 Terminal-Bench 4.0 排行榜（定位语：A benchmark to measure and evolve with the frontier of agent work）： 榜首是 GPT-6 Alpha (mini)，分辨率率（resolution rate）59.2% ± 3.0%，Codex agent，2026 年 9 月 5 日发布，1.6B tokens，$12 级成本； 其后是 Fable 5.2 (mini) 57.3%、Opus 5 (high) 55.4%、Fable 5 (mini) 44.4%、GLM-5.2 43.6%、Grok 4.7 (high) 37.4% 等。 右图则是同一行数字背后的凭据：Harbor Hub 上打开榜首那次 trial（任务 live-database-cutover）， 可以看到运行命令、Outcome（Completed，Score 0.00）、token 明细（输出 29,688,801 + 提示 603,518 + 缓存 1,874,321，共 32,166,640）、 分阶段计时（环境搭建 4 分 30 秒、agent 执行约 7 小时、verifier 仅 45 秒）、112 步的完整轨迹，以及 Agent/Verifier/Artifacts/Config/Lock/Log/Exception 七个页签。

这就是「可审计的评估」：排行榜上任何一个数字，点进去都是一次可复现、可检查、可质疑的完整实验记录。

Slide 63评估方法对比：四条路线的 Pros & Cons

收尾前引用 Anthropic 的评估方法全景表，四条路线各有利弊：

  • Automated evals（自动化评测）：无需真实用户、程序化跑测试——迭代快、完全可复现、无用户影响、可随每次 commit 运行、无需部署到 prod 即可规模化测试； 但前期投入大、需随产品与模型演进持续维护（防 drift）、若不匹配真实使用模式会产生虚假信心；
  • Production monitoring（生产监控）：在真实系统里追踪指标与错误——能揭示真实用户行为、捕捉合成评测漏掉的问题、提供 agent 真实表现的 ground truth； 但它是被动的（问题到你手上时用户已经遇到了）、信号噪音大、需要埋点投入、且缺乏评分用的 ground truth；
  • Manual transcript review（人工审阅对话记录）：人类通读 agent 对话——建立对失败模式的直觉、捕捉自动检查漏掉的微妙质量问题、帮助校准「好」的标准； 但耗时、不可规模化、覆盖不一致、评审疲劳与评审者差异影响信号、通常只产出定性结论；
  • Systematic human studies（系统性人类研究）：训练有素的评分者对 agent 输出做结构化打分——黄金标准质量、能处理主观/模糊任务、为校准模型评分者提供信号； 但昂贵且周转慢、难以高频执行、评分者间分歧需要仲裁、法律/金融/医疗等复杂领域必须请领域专家。

这张表与 Slide 50 的「评分器选型」互补：50 讲「怎么打分」，63 讲「在哪个环节评估」—— 成熟的评估体系是四条路线的组合拳，而 Terminal-Bench + Harbor 主要把第一条（automated evals）做到了极致。

本讲总结（Summary）

Key takeaways of this guest lecture

  • 范式迁移：演绎 → 归纳——传统软件是「人类写规则」（Rules + Inputs → Outputs，Hoare 式演绎世界）， 机器学习把它反转为「数据学出规则」（Inputs + Outputs → Rules）；这条归纳化浪潮正沿着 Models（从数据学得）→ Agents（靠评估开发）→ Software（由 agent 生成）三层推进（Slide 11–22）。
  • 评估成为新的 source of truth——Specification → Evaluation；旧范式的角色是「Specifier = Software Engineer」， 新范式要回答「Evaluator = ?」。对 agent 而言，「训练/测试数据」的形态就是 Terminal-Bench 这样的任务（Slide 26–30）。
  • Terminal-Bench——核心洞见「bash is the one tool to rule them all」； 社区数据：64 张 model cards、171 位贡献者、1k+ GitHub 参与者、5k+ Discord 成员、7M+ benchmark runs（截至 2026-09 下载 7,798,899）； 2025-01-17 首个提交，与 Claude Code（2025-02）几乎同时诞生；任务由 instruction.md + environment/Dockerfile + solution/solve.sh + tests 构成（Slide 31–38）。
  • Harbor 与核心定义——从「我们做一个基准」到「让所有人写百万个基准」； 任务(task)/试验(trial)/基准(benchmark)/验证器(verifier)/轨迹(trajectory)/评估框架/agent 框架七词术语表； task 目录结构满足 agent agnostic、easy to define、portable、expressive、independent（Slide 39–43）。
  • 写任务四件事——对齐 instruction 与 verifier、防 reward hacking、任务要真实公平有趣； instructions 要 fully specified 且尽量简洁自然；environments 尽量接近 prod、真服务优于 mock、平衡开放性与 flakiness； verifiers 是基于环境终态的结果分类器（混淆矩阵思维、与指令一一对应）；reward hacking 的解法是隔离——agent 环境与 verifier 环境之间只传 artifact； solution 必须像 agent 一样行动、不许 hardcode（Slide 44–54）。
  • 评估是一项长期工程——eval infra 要可靠/可复现/快/可移植；Harbor Rollout Engine 让任意 agent × 模型 × 任务 × 沙箱并行组合， 服务 test/train/prod；task QA 靠 static checks + oracle/frontier/cheat agents + agent judge； 持续基准（CI/CD）像维护软件一样维护任务；语义化版本 x.y.z 对应 rerun（环境）/regrade（verifier）/reuse（元数据）； 最终交付「full receipts」——每行结果都有 trial 级的轨迹、日志、产物与奖励（Slide 55–63）。
