一、什么是语言模型

What is a Language Model?（Slide 6 起）

Slide 6章节页：What is a Language Model?

进入第一部分。页面底部的进度条显示本讲的五个部分 （Language Models? / Architecture / Training / Inference / LLMs for Agents）， 当前红色高亮的是第一部分 Language Models?。

Slide 7语言模型的概率定义

语言模型的核心公式为 P(x1:T) = Πt=1T P(xt | x<t)， 幻灯片中各部分标注的含义为：

  • 左侧（蓝色下划线）：一个 token 序列的概率（Probability of a sequence of tokens）；
  • 中间连乘号（红色圈出）：从第一个到最后一个 token 的连乘（Product from the first to last token）；
  • 右侧（绿色下划线）：当前 token 在给定前面所有 token 条件下的概率（the probability of the current token given the previous tokens）。

Slide 8公式的逐 token 计算示例

以句子 "The class was about agents ." 为例，逐个 token 计算条件概率并累乘：

  • P(The) = 0.0377 → 累乘 0.0377
  • P(class | The) = 0.0001 → 累乘 0.0001
  • P(was | The, class) = 0.0344 → 累乘 0.0344
  • ……
  • P(. | The, class, was, about, agents) ≈ 0.0252

所有条件概率相乘后，整句概率约为 1.2e-17——一个极小的数。 因此幻灯片注明：实践中为了数值稳定性（numerical stability），通常取概率的对数再求和（sum of the log of the probabilities）， 而不是直接连乘。

Slide 9这就是语言模型

再次给出同一公式，并用红圈圈出左侧的 P(x1:T)， 明确指出："这就是语言模型"（This is a Language Model）—— 语言模型本质上就是给 token 序列赋予概率的模型。

Slide 10小节页：Generative vs. Discriminative Models

进入小节：生成式模型（Generative）与判别式模型（Discriminative）的区别。

Slide 11判别式 vs 生成式

对比图说明两类模型的本质差异：

  • 判别式模型（Discriminative）：学习区分类别（Learn to Distinguish Classes）—— 学习类别之间的决策边界（图中虚线）。例子：逻辑回归（Logistic Regression）、支持向量机（SVM）。
  • 生成式模型（Generative）：学习数据的分布（Learn Distribution of Data）—— 为每一类建模其数据分布（图中两个色块）。例子：朴素贝叶斯（Naive Bayes）、扩散模型（Diffusion models）。

图片来源标注：Akanksha Malhotra | medium.com。

Slide 12Knowledge Check（知识自测）

知识自测题：像下面这样建模 token 序列概率的语言模型，是生成式还是判别式的？ 幻灯片提醒：这不是陷阱题，但这里的符号记法可能容易让人混淆。

Slide 13答案：LM 是生成式模型

答案揭晓：P(x1:T) = P(x1, x2, x3, …, xT)—— 语言模型建模的是整个序列的联合分布，即数据的分布，因此 LM 是生成式（generative）的。 关键推论：因为是生成式模型，所以我们可以从中采样（we can sample from them）。

Slide 14小节页：Language Model Sampling（语言模型采样）

进入"语言模型采样"小节：既然可以从分布中采样，那么生成文本的过程就是不断采样的过程。

把上页的概率画成条形图，可以看到分布高度偏斜："to" 以 0.3171 远超其他候选 （橙色框高亮），其余候选的概率依次迅速衰减（as 0.0491、the 0.036、a 0.033……）。 这正是语言模型输出的典型形态：少数候选占据大部分概率质量。

Slide 18不必总是选最可能的 token：解码策略

前缀推进为 "…about to" 后，候选 token 及其概率为：be 0.1501、begin 0.0855、go 0.0627、start 0.0496、 get 0.0390、become 0.0342、enter 0.0313、take 0.0220、end 0.0192、graduate 0.0180。 注意本例选中的是 begin（0.0855，橙色框高亮）而非概率最高的 be——幻灯片借此指出： "我们不必总是选择最可能的下一个 token。存在不同的采样（解码）策略（sampling / decoding strategies）"：

  • 贪心（Greedy）
  • 核采样（Nucleus, top p）
  • Top k
  • ……

Slide 19采样得到的完整序列

经过逐步采样，最终生成的完整序列为："The class was about to begin ."。 这演示了自回归生成的过程：每一步在前缀上采样一个 token，把它拼进前缀，再采样下一个， 直到生成结束符（句号）。

Slide 20温度（Temperature）

温度（Temperature）是最重要的解码参数之一。以 "I am tired, I will take a __" 为例， 四个温度下的下一个 token 分布（nap / break / rest / bath / shower）：

  • T = 0.1：分布极尖锐，nap 接近 100%，几乎总是选 nap（近似贪心）；
  • T = 0.5：nap 约 75%，break 约 18%，其余很小；
  • T = 1.0：原始分布（nap 约 50%）；
  • T = 2.0：分布被"拉平"，各候选概率趋近（nap 约 34%，其余 13%–24%）。

右侧红字说明机制：把所有概率（实际是 logits）除以温度 T，再重新归一化（renormalize）使其和为 1。 T 越小分布越尖锐（越确定、越贪心），T 越大分布越平坦（越随机、越多样）。 图片来源：https://towardsdatascience.com/decoding-the-temperature-parameter-in-llms/。

Slide 21束搜索（Beam Search）

束搜索（Beam Search）示意图：从 start 出发，每一步不是只保留一个最优分支（贪心），也不是全部展开， 而是只保留得分最高的 k 个候选序列（beam）继续扩展。图中绿色深浅表示被保留/优选的分支， 例如 "the → green → witch" 与 "…witch → who" 等路径被继续追踪。 图片来源：Beam Search: Navigating Possibilities with Controlled Exploration。

Slide 22Considerations for Sampling（采样的考量）

采样策略选择的四条要点：

  • 每种采样策略都有不同的权衡（Each Sampling Strategy has different tradeoffs）；
  • 温度（Temperature）与 Top-p/Top-k 有助于多样性（diversity）；
  • 所用策略可能取决于任务（The strategy you use may depend on your task）：
    • 数学/代码（Math/Code）更可预测，适合更低的温度；
    • 创意写作（Creative Writing）可能受益于更高的多样性；
  • 策略也取决于你的预算——束搜索具有更高的时间与内存复杂度（beam search has higher time and memory complexity）。

Slide 28Decoder-only Transformer（仅解码器架构）：输入 token

现代 LLM 普遍采用 Decoder-only（仅解码器）架构。 讲义用 "The class was about" 四个 token 作为例子，逐步搭建一个 decoder-only Transformer 的前向计算。

Slide 29Decoder-only Transformer：词嵌入（Embedding）

第一步：嵌入（Embedding）——每个 token 被映射为一个稠密向量 （图中每个 token 上方的彩色圆点行）。例如 "The" 对应红色向量，"class" 灰色、"was" 绿色、"about" 橙色。

Slide 30Decoder-only Transformer：位置编码（Positional Embedding）

第二步：位置编码（Positional Embedding）——Transformer 本身不含顺序信息， 因此把一个表示位置的向量与词嵌入相加（图中每个 token 上方的黑色向量 + 彩色向量）， 使模型能够区分 token 的先后顺序。

Slide 31Decoder-only Transformer：汇总到注意力输入矩阵

第三步：四个 token 经过"嵌入+位置编码"后的向量被汇总到中央矩阵 （图中四行彩色圆点组成的矩阵，每行对应一个 token）。这就是注意力层的输入。

Slide 32Important! Pay Close Attention Here!（重要提示）

讲义在这里专门插入一整页提醒："重要！请注意这里的 Attention（双关：注意力机制）！ 如果你在这里跟丢了，本讲后面的大部分内容都会非常令人困惑。" 接下来将逐步拆解注意力层的内部计算。

Slide 33Attention Layer（注意力层）：输入

正式进入注意力层（Attention Layer）的拆解。输入仍是四个 token 的表示矩阵。

Slide 34Attention Layer：Layer Norm

注意力计算前先对输入矩阵做层归一化（Layer Norm）（图中 "Layer Norm( … )" 包裹中央矩阵）。 注：现代 LLM 多采用 Pre-Norm 结构，即先归一化再进入注意力子层。

Slide 35Attention Layer：矩阵乘法得到 Q、K、V

用三个可学习的权重矩阵对归一化后的表示做矩阵乘法（Matrix Multiply）， 得到注意力机制的三组激活：

  • WQ（黄色）→ Q（Query，查询）；
  • WK（红色）→ KT（Key 的转置，键）；
  • WV（蓝色）→ V（Value，值）。

Slide 36Attention Layer：计算 QKT

左侧淡入完整的注意力公式：Attention(Q, K, V) = softmax(QKT / √dk) V。 本步执行公式的第一部分：Q 与 KT 相乘（图中 ⊗ 符号）， 得到一个 token×token 的相关性矩阵——衡量每个 token 对其他 token 的"关注度"。

Slide 37Attention Layer：因果注意力掩码（Causal Attention Mask）

Decoder-only 架构必须遵守自回归约束：预测第 t 个 token 时不能看到第 t 之后的 token。 因此对相关性矩阵应用因果注意力掩码（Causal Attention Mask）—— 图中矩阵的右上三角（未来位置）被涂黑遮蔽，只保留下三角（含对角线，即当前位置及之前）。

Slide 38Attention Layer：缩放 ÷ √dk

对掩码后的相关性矩阵除以 √dk（dk 为键向量维度）。 缩放的目的：当 dk 较大时，Q·KT 的点积数值会偏大， 使 softmax 进入梯度极小的饱和区，除以 √dk 可稳定训练。

Slide 39Attention Layer：Softmax 得到注意力权重

对缩放后的矩阵逐行做 Softmax，得到注意力权重矩阵—— 每一行是该 token 对所有（不超过自身位置的）token 的注意力权重，行内和为 1。 图中结果呈下三角形态（因果掩码所致）。

Slide 40Attention Layer：加权求和 V 得到输出

最后一步：注意力权重矩阵与 V 相乘（图中第二个 ⊗）， 得到注意力层的输出矩阵（棕色圆点矩阵）——每个 token 的输出是其可见 token 的 Value 向量的加权和， 权重由注意力分布给出。至此完成公式 softmax(QKT/√dk)V 的全套计算。

Slide 41Attention Layer：输出投影 WO

注意力计算完成后，输出矩阵再乘以一个可学习的输出投影矩阵 WO（粉色）， 把结果投影回模型的维度（project back to model dimensions），得到注意力层的最终输出（粉色矩阵）。

Slide 42Attention Layer：残差连接（Residual Connection）

图中红色文字标出残差连接（Residual Connection）：注意力层的原始输入 （Layer Norm 之前的表示）被一条旁路直接送到输出端，与 WO 投影后的结果相加（⊕）。 残差连接让梯度可以直接回传、缓解深层网络退化，是现代 Transformer 的标配。

Slide 43Attention Layer → Multi-Head Attention Layer

过渡页：讲义将上面讲完的单头注意力层（Attention Layer）进一步推广为 Multi-Head Attention Layer（多头注意力层）。

Slide 44Multi-Head Attention：1. 多组权重矩阵

多头注意力的第一步（红色标注）：Multiple Weight Matrices（多组权重矩阵）。 本图仍先沿用单头的 Q/K/V 结构作为对照。

Slide 45Multi-Head Attention：WQ/WK/WV 复制成多份

图中 WQ、WK、WV 各自变为叠放的多组矩阵—— 即把注意力计算复制成多个并行、独立的注意力头（head）， 每个头有自己的一组 WQ/WK/WV，各自独立地计算 Q、KT、V 与注意力输出。 不同的头可以学习关注不同类型的关系。

Slide 46Multi-Head Attention：2. 拼接各头输出

第二步（红色标注）：Concatenate Attention Outputs（拼接注意力输出）—— 各个注意力头的输出矩阵（棕色）沿宽度方向拼接成一个更宽的矩阵。

Slide 47Multi-Head Attention：3. 更大的投影矩阵

第三步（红色标注）：Bigger Projection Matrix（更大的投影矩阵）—— 由于拼接后的矩阵更宽，输出投影 WO（粉色）也相应变大， 把拼接结果投影回模型原本的维度，并保留残差连接（⊕）。

Slide 48Multi-Head Attention：完整结构图

多头注意力层的完整结构汇总：归一化输入 → 多组 WQ/WK/WV → 各头分别计算 softmax(QKT/√dk)V → 拼接 → 大 WO 投影回模型维度 → 残差相加。

Slide 49Decoder-only Transformer：注意力层抽象为整体

讲义把上面拆解完的多头注意力层整体抽象为一个粉色块， 接下来在 decoder-only Transformer 的完整结构中继续往上堆叠组件。

Slide 50Decoder-only Transformer：Multi-head, Causal Self-Attention Layer

粉色块被命名为 Multi-head, Causal Self-Attention Layer（多头因果自注意力层）： 多头（multi-head）+ 因果掩码（causal）+ 自注意力（self-attention，Q/K/V 来自同一序列）。 其输出为粉色矩阵。

Slide 51Decoder-only Transformer：注意力输出的 Layer Norm

注意力层的输出（粉色矩阵）在进入下一个子层之前，再经过一次 Layer Norm 归一化。

Slide 52Decoder-only Transformer：注意力子层的残差连接

注意力子层同样配有残差连接：左侧旁路（⊕）把进入注意力层之前的表示 直接加到 Layer Norm 后的注意力输出上。

Slide 53Decoder-only Transformer：前馈网络（Feed Forward）

注意力子层之后是 Feed Forward（前馈网络）（蓝色块）： 对每个 token 的表示独立地做非线性变换（逐位置的两层全连接 + 激活）， 输出蓝色矩阵。Transformer 块 = 注意力子层 + 前馈子层。

Slide 54Decoder-only Transformer：前馈子层的残差连接

前馈子层也配有残差连接（右侧 ⊕）：把 Layer Norm 后的注意力输出 直接加到前馈网络的输出上。至此，一个完整的 Transformer 子层堆叠（注意力 + 前馈，各带残差）搭建完毕。

Slide 55Decoder-only Transformer：整体抽象为 Transformer Block

讲义把"注意力子层 + 前馈子层"的整体抽象为红色块，准备进行堆叠。

Slide 56Decoder-only Transformer：Transformer Block × N

红色块被命名为 Transformer Block，并标注 x N： 相同的块重复堆叠 N 层（现代 LLM 的 N 可达数十甚至上百层）。输出为红色矩阵。

Slide 57Decoder-only Transformer：Layer Norm + LM Head

N 层 Transformer Block 之后，先做一次 Layer Norm， 再进入 LM Head（语言模型头）（深红色块）—— 一个把隐状态映射到词表空间的线性投影层。

Slide 58Decoder-only Transformer：LM Head 输出 logits

LM Head 的输出是一个深红色矩阵：每个 token 位置对应一行， 行内是词表中每个 token 的原始得分（logits）。

Slide 59Decoder-only Transformer：Softmax

对 logits 做 Softmax，把原始得分转换为词表上的概率分布。

Slide 60Decoder-only Transformer：每个位置一个概率分布

最终输出按行展开：每个 token 位置各自得到一个 Softmax( … ) 概率条——这就是语言模型在"该位置下一个词是什么"上的预测分布， 与课程开头给出的自回归定义 P(x₁:ₜ) = Π P(xₜ | x<ₜ) 首尾呼应。

Slide 61Attention vs Recurrence（注意力 vs 循环）

本页引用 Attention Is All You Need 原论文的 Table 1，对比不同层类型 （n 为序列长度，d 为表示维度，k 为卷积核大小，r 为受限自注意力的邻域大小）：

Layer Type（层类型）Complexity per Layer（每层复杂度）Sequential Operations（顺序操作数）Maximum Path Length（最大路径长度）
Self-Attention（自注意力）O(n²·d)O(1)O(1)
Recurrent（循环）O(n·d²)O(n)O(n)
Convolutional（卷积）O(k·n·d²)O(1)O(logk(n))
Self-Attention (restricted)（受限自注意力）O(r·n·d)O(1)O(n/r)

讲义用红字强调两点（红框圈出"每层复杂度"与"顺序操作数"两列）：

  • O(1) 顺序操作数对在 GPU 上并行训练意义重大（O(1) Sequential Operations is a huge deal for parallel training on GPUs）——自注意力可以一次性并行计算整个序列，而 RNN 必须逐步递推；
  • O(n²) 的序列长度复杂度意味着长上下文变得昂贵（O(n²) Sequence length means long context becomes expensive）。

Slide 62Transformers were better and cheaper（Transformer 更好且更便宜）

同样出自原论文的结果表，对比当时各机器翻译模型的 BLEU 分数与训练成本（FLOPs）。 讲义用红框圈出最后两行：

  • Transformer (base model)：EN-DE 27.3、EN-FR 38.1，训练成本仅 3.3·10¹⁸ FLOPs（全表最低）；
  • Transformer (big)：EN-DE 28.4、EN-FR 41.8（两项 BLEU 均为全表最高），训练成本 2.3·10¹⁹ FLOPs，仍低于表中多数模型。

对照其他模型（ByteNet 23.75；GNMT + RL 24.6/39.92；ConvS2S 25.16/40.46；MoE 26.03/40.56； ConvS2S Ensemble 26.36/41.29 等），Transformer 以更低的训练成本取得了最高的翻译质量， 这正是它取代 RNN/卷积架构的原因。

Slide 63小节页：Linear Attention（线性注意力）

进入 Linear Attention 小节。本页图片来源标注： DeltaNet Explained (Part III) | Songlin Yang。 标准注意力的 O(n²) 代价催生了各类线性注意力改进，本小节用动画推导其核心思想。

Slide 64Attention Layer → Linear Attention（过渡）

过渡页：从前面讲完的注意力层（Attention Layer）出发，引出 Linear Attention。

Slide 65Linear Attention：沿用原注意力结构

本页展示线性注意力的起点：仍是最初的注意力结构（含 Softmax 与 ÷√dk）， 接下来将对其进行改造。

Slide 66Linear Attention："Drop Softmax"（去掉 Softmax）

线性注意力的关键改造（红色标注 "Drop Softmax"）：去掉 Softmax 与 ÷√dk 缩放， 让 QKT 的结果直接进入与 V 的乘法。此时整个注意力计算只剩矩阵乘法与加法——全部是线性运算。

Slide 67Linear Attention：结合律改写——先算 K×V

去掉 softmax 后（红色标注）：

  • "Everything here is now linear!"（这里的一切都变成线性的了！）
  • "We can change the associativity."（我们可以改变结合顺序。）
  • "Let's Multiply K and V instead."（改为先计算 K 与 V 的乘积。）

原本注意力是 (QKT)V（先算 n×n 的 QKT，代价 O(n²)）； 由于全是线性运算，可以利用结合律改写为 Q(KTV)—— 先算 KTV（与序列长度无关的固定大小矩阵），再让 Q 与它相乘，从而把复杂度从 O(n²) 降到 O(n)。

Slide 68Linear Attention：简化图（保留 Q/K/V 投影）

讲义把结构简化：只保留输入、Layer Norm 与 WQ/WK/WV 三个投影得到 Q、KT、V 的过程，为接下来按新的结合顺序重新连线做准备。

Slide 69Linear Attention：先算 KTV 得到状态 S₁

按新结合顺序，先计算 KT × V，得到一个品红色的状态矩阵， 记为 S₁（下标 1 用红框标出）——它汇总了第 1 个 token 的键值信息。 红框圈出当前正在处理的 token "The"。

Slide 70Linear Attention：Q × S₁ 得到输出

再用当前 token 的 Q 与状态 S₁ 相乘，得到该位置的注意力输出（左上棕色圆点）。 注意此时没有出现 n×n 的矩阵——每一步的代价都是 O(d²) 级别的常数。

Slide 71Linear Attention：完整结构（WO + 残差）

线性注意力的完整结构：输出经 WO（粉色）投影回模型维度， 再与原始输入做残差相加（右侧 ⊕）。

Slide 72Linear Attention Update Rule（状态更新规则）

讲义标题更新为 Linear Attention Update Rule（线性注意力更新规则）， 接下来用多 token 的动画演示状态 S 如何随序列逐步更新。

Slide 73Linear Attention Update Rule：Clear Unimportant Memory

右侧红框标注 "Clear Unimportant Memory"（清除不重要的记忆）： 状态矩阵 S 可以被视为模型的"记忆"，更新规则允许在写入新信息的同时清除不再重要的旧信息 （这是 DeltaNet 类方法相对朴素线性注意力的关键改进）。

Slide 74Linear Attention Update Rule：Save the state（保存状态）

右侧红色标注 "Save the state"（保存状态）： 处理完第 1 个 token 后，把状态 S₁ 保存下来供下一个 token 使用。

Slide 75Linear Attention Update Rule：处理第 2 个 token "class"

动画推进：输入序列扩展到两个 token（"The" 与 "class"）， 第 1 步保存的状态 S₁ 仍然在右上方等待被更新。

Slide 76Linear Attention Update Rule：第 2 个 token 的 Q/K/V

第 2 个 token "class" 的 Q（黄）、KT（红）、V（蓝）已经计算出来， 准备按更新规则并入状态。

Slide 77Linear Attention Update Rule：S₂ = S₁ ⊕ (K₂TV₂)

更新规则的核心：把第 2 个 token 的 KT×V 结果与旧状态 S₁ 相加（⊕）， 得到新状态 S₂。状态以"累加"的方式逐 token 滚动更新， 大小始终固定，不随序列长度增长。

Slide 78Linear Attention Update Rule：Q₂ × S₂ 得到输出

第 2 个 token 的 Q 与新状态 S₂ 相乘得到其输出（左上棕色圆点）， 再经 WO 投影与残差连接输出。整个过程对每个 token 只做常数时间的工作。

Slide 79Linear Attention Update Rule：再次 Clear Unimportant Memory

更新完成后保留新状态 S₂，右侧红框再次提示 "Clear Unimportant Memory"： 每次更新都可选择性地衰减/清除旧记忆，避免状态被无限累加的信息淹没。

Slide 80Linear Attention Update Rule：保存 S₂ 进入下一步

动画收尾：S₂ 被保存并上移，准备在处理第 3 个 token 时继续滚动更新。 至此展示了线性注意力的完整范式：固定大小的状态 S 逐 token 更新（写入 K·V、清除旧记忆）， 每个 token 用 Q 读取状态——推理时每步代价为常数，这也是现代状态空间/线性注意力模型 （如 DeltaNet 一类）相对标准注意力的效率优势来源。

Slide 81Linear Attention Update Rule（第 3 步：处理 "was"）

动画继续。前缀 "The class was" 的第三个 token "was" 进入模块：先做 Layer Norm， 再经 W_Q/W_K/W_V 投影得到该 token 的 Q、K、V；新的键值外积 Kᵀ·V 与上一状态 S₂ 相加（图中 S₂ 与中间矩阵之间的 ⊕），得到更新后的状态 S₃；同时当前 token 的 Q 读取 S₃（Q × S₃），再经 W_O 投影、加回残差通路。注意整个过程中被反复读写的是 同一个固定大小的状态矩阵——序列变长并不会让它变大。

Slide 82Linear Attention Update Rule（第 4 步：处理 "about"）

最后一个 token "about" 以完全相同的方式处理：S₄ = S₃ ⊕ K₄ᵀ·V₄，并用 Q₄ 读取 S₄。 至此四个 token "The class was about" 全部处理完毕。回看整段动画，每处理一个 token 只做两件事——把当前 K·V 写进状态、用当前 Q 读一次状态，代价与已见序列 长度无关。这正是线性注意力相对标准 O(n²) 注意力的核心效率优势，也是它"像 RNN 一样" 逐步处理序列的原因。

Slide 83线性注意力显著更快、显存占用更低

两张双对数坐标图横轴均为序列长度（2⁹–2¹⁶），左图为耗时（毫秒）、右图为 GPU 显存（MB）。 黑色 ×（linear, ours）始终最低且呈线性增长；红色三角（softmax）斜率最陡，按序列长度的 平方增长，很快最先爆掉；蓝色虚线为 Reformer 的 lsh-1/4/8（局部敏感哈希分桶近似）， 介于两者之间。原论文 Figure 1 的结论：Linear 与 Reformer 在时间与显存上都随序列长度线性扩展， 而 softmax 注意力两者都按平方扩展。

Slide 84然而……线性注意力在长上下文上更吃力

效率的代价是长上下文能力。左表给出 RULER 基准的三类"大海捞针"任务： Single NIAH（S-NIAH）——在文章干草堆中找唯一魔术数字（12345）； Multi-keys NIAH（MK-NIAH）——存在多个键（如 long-context 与 large-model 各对应 不同数字），需按指定键取对值；Multi-values NIAH（MV-NIAH）——同一键对应多个值 （12345 与 54321），需全部取出。任务难度逐级递增，干草堆大小随上下文长度增长。 右图的架构对比显示：随序列长度从 1K 增至 8K，softmax 架构 Llama2-7b（紫）在 4K 前保持 高准确率后才骤降；线性注意力/状态空间类架构 RWKV-v5-7b（蓝）与 Mamba-2.8b-slimpj（绿） 则更早、更平滑地衰减——压缩状态难以精确保留长距离细节。

Slide 85关于上下文长度的一点说明

这页澄清一个常见误解：无论是 Transformer 还是 Linear Attention，结构本身并没有 强制一个严格的上下文长度上限——唯一的约束来自模型处理位置嵌入（positional embeddings） 的方式。实践中模型需要"学会使用"位置嵌入，因此我们被限制在训练时所用的上下文 长度之内。超出该长度的外推之所以失效，本质是位置编码未见过的区间，而非注意力 机制算不下去。

Slide 86小结：把它们放在一起（Bringing it together）

章节过渡页。前面依次讲完了标准 softmax 注意力（O(n²)、KV Cache 线性增长、长上下文强） 与线性注意力（O(n)、常数状态、长上下文弱），本页开始给出工程上的综合结论：实际系统 如何选择与组合这些注意力变体。

Slide 92章节页：LLM Training

进入第三部分"LLM 训练"。进度条显示本讲五个板块中当前位于 Training：先讲清楚 "语言模型是什么"（第一部分）、"用什么架构"（第二部分），现在回答模型是如何 从数据中学出来的——从定义损失函数开始。

Slide 93定义损失（Defining the Loss）

小节过渡页。训练的本质是优化：要给模型一个数值信号，告诉它对真实数据的预测 "有多错"，然后用梯度下降去减小它。本节用一个具体例子逐步导出语言模型的标准 损失——交叉熵。

Slide 94训练数据（示例）

给出一条训练文本："The class was about how agents work, and how to build AI systems that use tools, retrieve information, and carry out tasks across multiple steps…"。 语言模型的训练目标就是：给定前缀，预测下一个 token。下面用这条文本的 开头演示模型在某个位置上的预测与损失计算。

Slide 95给定前缀，候选下一 token 的分叉

模型读完前缀 "The class was about" 后，需要对"下一个 token 是什么"给出分布。 图中从 "about" 分叉出一组候选：to、as、the、a、two、how、getting、three、time、 左引号等。每个候选都会得到一个概率，所有候选概率之和为 1。训练时我们已知真实 答案，问题是如何度量模型分布与真实答案的差距。

Slide 96模型给出的概率分布

假设当前（未充分训练的）模型给出的分布为：to 0.3171、as 0.0491、the 0.036、 a 0.033、two 0.0147、how 0.0124、getting 0.0101、three 0.01、time 0.0091、 左引号 0.0081。模型把最高概率押在 "to" 上，而右下角提示真实训练文本的续写是 "…about how agents work…"——模型此刻并不看好正确答案。

Slide 97真实 token 是 "how"，但模型只给了 0.0124

把真实答案 "how" 用红框标出：它只分到 0.0124 的概率，远低于模型押注的 "to"。 这正是一个"模型预测错了"的位置——损失函数要做的就是惩罚模型给真实 token 的概率过低，并在反向传播中把概率往真实 token 上推。

Slide 98聚焦：正确答案的概率

把视野收窄到关键量：p(how | "The class was about") = 0.0124。 损失函数只关心这一个数——真实 token 的预测概率。其余候选的概率是多少并不直接进入 该位置的损失（它们通过归一化间接相关）。

Slide 99计算损失：Loss = −log(0.0124) = 1.907

损失定义为真实 token 概率的负对数：Loss = −log(0.0124) = 1.907。 负对数把概率映射为惩罚：概率越接近 1 损失越接近 0，概率越小损失越大且增长无界 （p→0 时 −log p→∞）。这个值就是梯度下降要最小化的目标——训练后模型应给 "how" 更高的概率，损失随之下降。

Slide 100交叉熵损失（Cross Entropy Loss）

把上面的单步推广到整个词表，就是语言模型的标准目标——交叉熵损失：

L = − Σi=1V yi · log(pi)

各项含义如幻灯片注释：Σ 遍历词表中每一个 token（i = 1…V）； yi 是 one-hot 标签——当第 i 个 token 是数据中的真实 token 时为 1， 否则为 0；log(pi) 是模型给该 token 的对数概率。由于 yi 除真实 token 外全为 0，求和实际只剩真实 token 一项，即 L = −log(p真实)—— 正是 Slide 99 算的 1.907。对整个序列的每个预测位置都如此计算并取平均，就是预训练 最小化的总损失。

Slide 101小节页：Pretraining（预训练）

训练部分按三个阶段展开：Pretraining（预训练）→ Midtraining（中期训练）→ Posttraining（后训练）。本页进入第一阶段——用海量通用文本从头训练基座模型。 预训练的两大工程问题是数据从哪来、怎么配比，接下来几页都围绕数据。

Slide 102Data：网页数据清洗流水线

典型的网络语料处理流水线。原始 HTML 网页先做文本抽取 （Text Extraction，去掉标签/导航/广告），再用语言识别（Lang ID）筛出目标语言， 然后过基于规则的过滤器（Rule-Based Filters，如长度、符号比例等启发式规则）， 接着用质量过滤器（Quality Filters，通常是分类器打分），最后去重 （Deduplication，图中红叉表示剔除重复文档），得到最终训练数据。每一步都在"减量提质"。

Slide 103Data：DCLM 过滤漏斗（量化）

以 DCLM 论文 Figure 4 展示过滤的实际规模（百分比按原始文档总数计）。起点是 DCLM-Pool（用 resiliparse 从 Common Crawl 抽取）。三大阶段： 启发式清洗（复现 RefinedWeb，§4.1 & 4.2）后剩 19.9%—— 其中 English filter 砍掉 50.8%、Repetition filter 9.6%、Other filters（词长、省略号计数、 停用词等）9.0%、Page length filter 7.9%、URL filter 0.8%、Word removal ratio filter 2.0%； 去重（§4.3，Bloom filter dedup 再砍 6.2%）后剩 13.7%； 基于模型的过滤（§4.4，FastText filter 砍 12.3%）后最终只剩 1.4% 成为 DCLM-Baseline。可见高质量预训练语料是"百里挑一"淘出来的。

Slide 104Data：数学专用语料 Nemotron-CC-Math

面向特定领域（数学）的语料构建实例。流水线：从 Common Crawl（98 个快照）出发， 用 MegaMath、FineMath、OWM、InfiMM-WebMath 等数学 URL 清单筛出 229.54M 个数学网页；页面经 Lynx 渲染抽取文本（弃用 Resiliparse/Trafilatura）， 再用 LLM 精炼（Refining text）提升质量，最后去重与去污染 （Deduplication & Decontamination），得到 Nemotron-CC-Math：101.15M 文档、 133.26B token。右侧主题分布：Mathematics 60.28%、Computer science 11.99%、 Physics 11.22%、Statistics 7.50%、Economics 3.18%、Chemistry 1.71%、Other 4.12%—— 一个以数学为主、覆盖理工科的高质量专用语料。

Slide 105Data：DCLM 数据样例

展示清洗后语料的实际样子：一段 Fortran 标准库文档（EOSHIFT——End-off shift 函数， 含参数说明、Array Type / Boundary Value 定义等）。这类技术文档、手册、教程 信息密度高、结构规整，是预训练语料中质量较高的部分，也是模型学会写代码与读文档的 重要来源。

Slide 106Data：The Pile 的成分构成

另一种思路：不靠"海量网页 + 过滤"，而是主动拼配多源高质量语料。 The Pile（800GB）按五大类组织——Academic（学术：PubMed Central、ArXiv、 FreeLaw、USPTO、PMA、Phil、NIH）、Internet（网络：Pile-CC、OpenWebText2、 StackExchange、Wikipedia）、Prose（散文/书籍：Bibliotik、PG-19、BC2）、 Dialogue（对话：Subtitles、IRC、EP、HN、YT）、Misc （其他：Github、DM Math）。树图面积即各类占比：学术与网络语料占大头。 这种" curated mix "让模型在代码、论文、对话等维度更均衡。

Slide 107Data Mixing：用代理模型搜索最优配比

数据"怎么配"本身是可优化的问题。Olmix 框架三步走：① Swarm（群体采样） ——采多组配比 p，每组用代理小模型（proxy）快速训练，得到性能 y₁₁…yn1、y₁K…ynK；② Regression（回归） ——用这些（配比, 性能）样本拟合预测模型 f̂(p) ≈ 真实性能 f(p)；③ Optimization （优化）——在配比空间 S 上求解 minimize f̂(p)，得到最优配比 p*。 核心思想：用便宜的小模型实验替代昂贵的大模型实验来搜索数据配方， 再迁移到大模型训练。

Slide 108小节页：Midtraining（中期训练）

进入第二阶段 Midtraining——介于通用预训练与后训练之间，通常用更聚焦目标领域 的数据继续训练，为后续的指令微调/对齐打基础。接下来几页讲它的动机与做法。

Slide 109把数据配比向目标领域倾斜

动机页：调整数据配比，使其更聚焦目标领域（数学、代码等）。表格把数据按 领域（Application and Web Development、Arts/History/Culture、Business Software and Strategy、Christian Faith and Devotion、Clinical Treatment and Dentistry 等）× 质量带（Q0–Q4）交叉分格，左右对比 PRETRAINING 阶段与 COOLDOWN（训练末段）阶段的配比（色块深浅表示占比）。思路是在训练后期 （cooldown）把配比向高质量、目标领域的格子倾斜。

Slide 110在"预训练"里多混入目标领域数据往往有帮助

左图给出专用预训练配比（Specialized Pretraining Mix）：在通用数据 （General Data）之上，把领域数据集重复混入 10–50 倍（每个蓝格 = 领域数据 的 1 个 epoch）。右图实验（基座模型均为 200B 预训练 token）对比"含 33× 领域数据的 专用预训练"（实线）与"通用预训练"（虚线）：蓝色为领域测试损失、 橙色为通用损失，横轴为后续微调步数。专用预训练不仅域内泛化更好 （蓝色实线最低点更低），而且微调时通用能力遗忘更少（橙色实线上升更缓） ——即"与其事后微调塞领域数据，不如预训练阶段就混进去"。

Slide 111Midtraining 桥接预训练与后训练分布

用参数空间的等高线图直观解释 midtraining 的作用。颜色表示梯度对齐程度 （蓝=高对齐、红=低对齐）。从预训练参数 θpre 到目标参数 θtarget： 标准微调（Standard FT，红虚线）直穿中间的低对齐"山丘"，优化困难、 易遗忘；而先做 midtraining（白实线）把参数移到 θmid—— 一个处于高对齐谷地的中间点——再走向 θtarget，路径全程落在对齐良好的区域。 即 midtraining 在两种数据分布之间架了一座"桥"，让后训练走得更稳。

Slide 112小节页：Posttraining（后训练）

进入第三阶段 Posttraining——把基座模型变成"会听指令、对齐人类偏好"的助手模型。 主流手段依次为：指令微调（SFT）、基于人类偏好的强化学习（RLHF），以及更近期的 可验证奖励强化学习（RLVR）与面向智能体的专门训练。

Slide 113Instruction Finetuning（指令微调）

指令微调的三种数据形态：① 普通指令微调——"Please answer the following question. What is the boiling point of Nitrogen?" → "-320.4F"；② 思维链微调 （Chain-of-thought）——要求逐步推理，如苹果算术题先算 23−20=3 再算 3+6=9； ③ 多任务指令微调——用 1.8K 个任务的大规模指令集合训练。虚线之下的绿色 示例展示推理阶段的泛化：对训练中没见过的任务（"Geoffrey Hinton 能和 George Washington 对话吗？先给理由"），模型能输出合理推理并答 "no"（生于 1947 vs 卒于 1799）。即多任务指令微调赋予模型对未见指令的零样本泛化。

Slide 114Learning from Human Preferences（RLHF 三步）

经典 RLHF（InstructGPT）三步：Step 1 收集示范数据、训练监督策略（SFT） ——从提示集采样提示（如"向 6 岁小孩解释登月"），标注员写出期望输出 （"Some people went to the moon…"），用监督学习微调 GPT-3；Step 2 收集比较数据、 训练奖励模型（RM）——对同一提示采样多个模型输出（A/B/C/D），标注员从好到差排序 （D > C > A = B），用排序数据训练奖励模型；Step 3 用强化学习对奖励模型优化 策略——采样新提示（"写个青蛙的故事"），策略（PPO）生成输出，奖励模型打分 rk，用该奖励通过 PPO 更新策略，循环迭代。

Slide 115人类反馈的问题

RLHF 依赖人类标注，但人类反馈本身有缺陷：

  • 人类标注员可能不可靠（unreliable）——质量参差、会犯错；
  • 每个人偏好不同——标注者之间难以一致；
  • 给模型优化带来坏激励——如谄媚（sycophancy）、故作权威 （authoritativeness）：模型学会"讨好标注员"而非"答得对"；
  • 数据本身的采集可能不合伦理（sourced unethically）。

这些问题催生了下一节"可验证奖励"的方向。

Slide 116RLVR：可验证奖励的强化学习

针对人类反馈的问题，RLVR（Reinforcement Learning with Verifiable Rewards） 的思路是让奖励可验证——用客观校验器代替人类主观打分。要点三条： 让奖励可验证；对数学和代码特别好使；需要谨慎设计验证器（verifier）。 右侧列出可验证奖励的常见形式：Unit Tests（单元测试）、Lean Proof （形式化证明）、Exact Match（精确匹配）、System state （系统状态检查）等。下方为 GRPO 流程：问题 q 输入策略模型（Policy Model， 可训练），采样一组输出 o₁…oG，分别经参考模型（算 KL 约束）与奖励模型打分得 r₁…rG，再做组内计算（Group Computation，用组内相对优劣估计优势） 得到 A₁…AG 更新策略——无需单独的价值网络。

Slide 117面向智能体的专门训练（如 SWE-Smith）

智能体训练数据的规模化生成，以 SWE-Smith 为例，四步流水线： ① 真实仓库（Real Repositories）——源代码（src/、tests/、README.rst、 setup.py）加通过的单元测试；② 环境构建（Environment Creation）—— SWE-agent 尝试安装仓库并跑通测试，再由"Developer"角色据其过程写出 Dockerfile； ③ 任务生成策略（Task Gen. Strategies）——四种手段造 bug：程序化修改 （Procedural Modification）、LM 生成、组合多个 bug（Combine Bugs）、PR 镜像 （PR Mirroring）；④ 新任务实例（New Task Instances）——产出环境镜像 + 合成任务（生成的 Issue、带统计的 Bugged Patch、已验证测试 ×2/✓9）。 即用真实代码仓库自动批量制造"修 bug"训练任务。

Slide 118SWE-Smith 基准结果

同一模型搭配不同 agent 系统（harness）得分差异显著——再次印证"模型 + 脚手架"要 一起看。闭源权重模型：GPT-4o 配 Agentless 得 Lite 32.0 / Verified 38.8、 配 OpenHands 22.0、配 SWE-agent 18.3/23.0；Claude 3.5 Sonnet 配 Agentless 40.7/50.8、 OpenHands 41.7/53.0、AutoCodeRover 46.2、SWE-agent 23.0/33.6；Claude 3.7 Sonnet 配 SWE-agent 达 48.0 / 58.2（该行加粗）；Llama3-SWE-RL-70B（11M 训练规模） 配 Agentless 41.0。开源权重模型：SWE-agent-LM-32B（5k 训练）30.7/ 40.2 最突出，超过多数未专门训练的更大开源模型（SWE-gym-32B 15.3/20.6、 SWE-agent-LM-7B 11.7/15.2）；Lingma-SWE-GPT-72B 28.8、Qwen3-235B-A22B 34.4、 R2E-Gym-32B 34.4、SWE-fixer-72B 24.7/32.8。结论：面向 agent 的专门训练数据 （即便规模不大）能显著提升软件工程任务表现。

四、LLM 推理

Slide 119章节页：LLM Inference

进入第四部分"LLM 推理"。进度条高亮 Inference：模型训练好之后，实际服务用户时 如何高效地生成 token。对智能体系统而言，推理成本与延迟直接决定多步循环的可行性， 因此这一部分同样是 agent 工程师的必修课。

Slide 120小节页：Prefill and Decode

推理小节从最基本的两阶段划分开始：Prefill（预填充）——一次性处理全部 输入提示，计算并缓存各层的 Key/Value；Decode（解码）——逐 token 自回归生成， 每步只算一个新 token 并追加进 KV Cache。两阶段的计算特征截然不同（前者并行、计算密集， 后者串行、访存密集），后续将据此展开优化手段。

Slide 121GPUs

讨论推理性能前先看硬件。CPU 把大量面积留给控制单元（Control）与缓存（Cache）， 只有少量 ALU，擅长复杂分支与串行逻辑；GPU 则几乎把整个芯片铺满成千上万个小计算单元， 控制逻辑极简、缓存很小，专为大规模并行的矩阵/向量运算而生。LLM 的前向计算正是后者擅长的形状， 因此推理几乎全部跑在 GPU 上——但这也意味着推理性能受 GPU 的算力上限与显存带宽双重约束， 引出下一张 roofline 模型。

Slide 122Roofline Performance Model

Roofline 模型用两条"屋顶线"刻画任何核函数在给定硬件上的性能上限：一条水平线是 峰值算力（Peak FLOP/s），一条斜线是显存带宽（Bandwidth GB/s）。 横轴算术强度（每搬运 1 字节数据能做多少次浮点运算）决定工作点落在哪条线下： 强度低时受带宽限制（bandwidth-bound，性能沿斜线爬升），强度高时受算力限制 （compute-bound，触及水平天花板）。这个模型是理解 LLM 推理两个阶段性能差异的钥匙。

Slide 123Prefill and Decode

这张图给出两阶段的直观流程：prefill 阶段把整条提示（The quick brown fox） 并行送过模型，为每个 token 生成 KV 向量并缓存（虚线框 cached）； decode 阶段每步只处理一个新 token（jumps → over），但它对历史上下文的注意力 直接读取已缓存的 KV，无需重算。因此 prefill 是一次性的并行大计算，decode 是串行的、 每步增量的小计算——两者的瓶颈完全不同，优化思路也因此分家。

Slide 124Prefill

Prefill 阶段，提示中的全部 token（此处为 The/class/was/about）同时经过 Layer Norm，再分别乘以 W_Q、W_K、W_V 得到完整的 Q、K、V 矩阵，计算 Softmax(QK⊤/√dk)·V，最后经 W_O 投影并与残差相加。 关键点：所有 token 的 Q/K/V 都是满矩阵，注意力是 n×n 的稠密矩阵乘， 计算量随序列长度二次增长但高度并行——这是典型的 compute-bound 工作负载。

Slide 125Decode

进入 decode 后，每步只有一个新 token（图中为 The）进入计算： 它的 Q 只是一个行向量，而 K⊤、V 取自此前缓存的历史 KV。 于是 QK⊤ 变成"一行 × 矩阵"，Softmax 结果也只有一行——每步的计算量从 O(n²) 降到 O(n)，但每一步都必须把整个模型权重和全部 KV Cache 从显存读一遍。 搬运的数据量远大于计算量，这正是下一步要讨论的访存瓶颈。

Slide 126Decode：Clear Unimportant Memory

这一帧强调 decode 的内存纪律：每生成一步后，该步产生的临时激活 （中间矩阵、Softmax 中间结果等）都不再需要，应立即清除，唯一需要跨步保留的只有 KV Cache。若不清除，显存会随步数无谓膨胀。"只留 KV Cache"是 decode 阶段内存占用的核心结论。

Slide 127Decode（累积 2 个 token）

第二个 decode 步：新 token（class）的 Q 同样是单行向量，与已缓存的两行 K⊤/V 做注意力。可见 decode 是逐 token 累积的过程——每生成一个 token，KV Cache 就追加一行， 后续每一步要读取的 KV 也随之变长。这解释了为什么长序列生成既慢又吃显存。

Slide 128Decode：Clear Unimportant Memory（2）

与 Slide 126 相同的纪律再次执行：本步的临时激活被清掉，KV Cache 保留两行。 这个"算一步、清一步"的循环会贯穿整个 decode 过程——动画的后续各帧只是不断重复 "新增一个 token → 注意力 → 清除临时量"这一模式。

Slide 129Decode（累积 3 个 token）

第三个 token（was）加入：Q 仍为单行，K⊤、V 已是三行。 注意 K⊤ 矩阵随步数线性长高——decode 的每一步都在读取一个越来越大的 KV Cache， 单步耗时与显存占用都随上下文长度线性增长。

Slide 130Decode：Clear Unimportant Memory（3）

第三步收尾：临时量清除，KV Cache 稳定在三行。动画以此节奏推进到序列结束。

Slide 131Decode（累积 4 个 token）

最后一个 token（about）生成，KV Cache 达到四行，与 prefill 阶段一次性算出的 KV 完全一致 ——殊途同归：prefill 是一次并行算完，decode 是逐行追加，最终缓存内容相同。 这也是"长提示 + 短输出"场景下 prefill 主导耗时、"短提示 + 长输出"场景下 decode 主导耗时的原因。

Slide 132Decode：Clear Unimportant Memory（4）

decode 动画的收尾帧：所有临时激活清空，画面上只剩 K⊤、V 两个矩阵—— 下一帧将正式给出它们的名字。

Slide 133KV Cache

动画收敛到核心概念：KV Cache。decode 全程唯一需要持久保存的中间状态， 就是每个历史 token 的 Key 与 Value（按层、按头存储）。它有两个工程后果： 其一，显存占用随序列长度线性增长，长上下文/大 batch 下 KV Cache 常常比模型权重本身更占显存； 其二，每一步都要完整读取 KV Cache 与全部权重，使 decode 成为访存密集型操作。 围绕它的优化（量化、分页管理 PagedAttention、压缩/驱逐等）是推理系统的核心课题。

Slide 134Roofline 再看两阶段：Decode vs Prefill

把两个阶段标回 roofline 图，结论一目了然：Decode 的算术强度极低 （每步搬运全部权重 + KV Cache，却只做 O(n) 计算），落在带宽受限的斜线区， 提速靠的是提高显存带宽、降低搬运量（量化、投机解码、batching）； Prefill 的算术强度高（n×n 稠密矩阵乘），落在算力受限的水平区， 提速靠的是吃满 GPU 峰值算力（并行、算子融合）。两种瓶颈对应两套完全不同的优化 playbook。

Slide 135Metrics

从用户体验出发，推理性能用两个时延指标刻画：Time to First Token（TTFT）—— 从发出请求到看到第一个输出 token 的时间，由 prefill 阶段主导，决定"响应快不快"； Time Per Output Token（TPOT）——decode 阶段相邻 token 的间隔，决定"生成流不流畅"。 两者分别对应 compute-bound 与 bandwidth-bound，优化时必须分开度量、分开治理， 这也是后面讨论并发调度（continuous batching）与投机解码的出发点。

Slide 136Speculative Decoding

投机解码是加速 decode 的代表性算法，针对的正是"decode 每步都要读一遍大模型权重" 的带宽瓶颈。做法：用一个小而快的草稿模型（Draft Model）自回归地连猜 K 个 token （左图：Once→upon→a→time→there 逐步起草），再把这些草稿一次性并行交给 目标模型（Target Model）校验（右图：一次前向即可对全部 K 个位置给出分布）。 与目标模型一致的 token 被接受（✓），第一个不一致处被拒绝（✗）并从修正后的分布重新采样。 可以证明该拒绝采样过程不改变目标模型的输出分布——加速但不损质量； 当草稿命中率高时，一次目标模型前向能"兑换"多个 token，等效提升 decode 吞吐。

Slide 137Speculative Decoding：经验数据

三张曲线给出投机解码的工程权衡，横轴均为草稿 token 数 K： ① 平均采样时间先随 K 下降（并行校验摊薄了大模型前向成本）后回升（K 过大时草稿多为无效计算）， 存在最优 K；② 接受率随 K 单调下降——猜得越长越难全中，且代码（HumanEval）的接受率 系统性高于摘要（XSum），印证红字结论"有些领域的文本比别的领域更可预测"； ③ 单次循环耗时随 K 近似线性上升（目标模型一次要校验更长的草稿）。 实践中的 K 需在这三者间折中，且最好按领域自适应调整。

Slide 138小节页：Inference Time Scaling（Test Time Scaling）

推理优化的另一条主线：不在训练期、而在推理期投入更多计算来提升质量， 即 Inference Time Scaling（又称 Test Time Scaling）。与前面"让推理更快"的优化方向相反， 这里是主动花更多算力换正确率——典型手段是让模型"多想一会儿"： 展开中间推理步骤、自我质疑与校验、多次采样择优。接下来两页展示这条路线的代表技术。

Slide 139Chain of Thought

思维链（Chain-of-Thought, CoT）是最早也最直接的推理时扩展： 标准提示（左）只给"问题→答案"样例，模型直接蹦出 27，错了； CoT 提示（右）在样例中显式写出中间推理步骤（"Roger 原有 5 个球，2 罐×3=6，5+6=11"）， 模型便学会在输出答案前先铺开推理链（"原有 23 个苹果，用了 20 个剩 3，又买 6 个得 9"），答案随之正确。 本质是把原本一步完成的计算摊到多个 token 上逐步执行，用更多推理期计算换取可靠性。

Slide 140Reasoning LLM

CoT 的进一步内化就是推理型 LLM（Reasoning LLM）：推理过程不再依赖提示词示范， 而是经训练内建为模型行为。同一道题（外套 $80，涨价 25% 后再打 25% 折扣，求最终价）： 传统 LLM（左）按部就班算出 $100→$75；推理 LLM（右）则展现出 "直觉—质疑—修正—复核"的完整链条：先直觉认为涨跌抵消仍为 $80，随即自我打断 （"Wait… 折扣是作用于涨价后的价格"），重新算得 $75，最后主动验算 （"Let me check that. $80+$20−$25=$75. Okay."）。这种自我反思与验证 正是推理时扩展的核心机制，也是后续 agent 系统中"规划—执行—检查"循环的模型侧基础。

Slide 141Reasoning LLM："Aha" moments（自我纠错）

另一道应用题（票+爆米花共 $18，票比爆米花贵 $6，求票价）完整展示了推理模型的"Aha" 时刻： 模型在 <think> 块内先列方程 p+6=18 解出 p=12、ticket=18——随即意识到错误 （"Wait, that can't be right. I only used the ticket price, not the total of ticket + popcorn."）， 重新列出正确方程 p+(p+6)=18，解得 p=6、票价 $12，最后以 <answer>\boxed{12}</answer> 收尾。 红字点明核心能力：模型学会了自我纠正（self-correct）——这种"发现矛盾→回溯→重算" 的行为是推理时扩展能提升正确率的关键机制，也再次印证上一讲的 RLVR： 可验证的奖励信号能训练出此类反思行为。

Slide 142推理努力（Effort）与成本—分数权衡

这张来自 OpenAI 的图把推理时扩展落到产品形态：横轴每任务成本（对数轴，$0.02–$20）、 纵轴 agent 基准分数。各模型家族（GPT-6 Astra/Sol/Luna、GPT-5.6 Sol/Luna、Claude Opus 5、 Claude Fable 5 w/ Opus 4.8 fallback）各占一段成本—分数曲线；放大看 GPT-6 Astra， 同一模型通过 Low / Medium / Max 三档推理努力（右下角的 effort 滑块 UI，当前 High） 在曲线上滑动——花得越多（token 越多、思考越久），分数越高。 推理努力由此成为用户可直接调节的"质量—成本"旋钮。

Slide 143Setting the Reasoning Level（GPT-OSS）

开源模型 GPT-OSS 展示了 effort 旋钮的朴素实现：推理级别不是 API 参数， 而是直接写进系统提示的一行文本——Reasoning: low / medium / high， 之后才是用户提示（"Solve this math problem…"）。模型在训练时见过这三档指令， 据此调节 <think> 块的长度与深度。这说明 effort 控制本质上是指令遵循问题， 框架层面无需特殊机制，一行提示即可切换。

Slide 144Some ways it is done：effort 的训练方法

两种让模型学会分档推理的训练做法。Inkling（Thinking Machines）在 RL 奖励中 加入长度惩罚：R(e) = R_task − λ(e)·N_tokens，λ 调高时多写 token 代价大→模型学会 低 effort（简洁作答）；λ 调低时思考几乎免费→模型展开高 effort推理。 λ 成为连续可调的努力旋钮。Kimi K3（Moonshot）则走蒸馏路线：用 3 个领域 （General Task / General Agent / Coding Agent）× 3 档 effort（High/Med/Low）共 9 个教师模型， 配合"答对 +1、答错 0、答错且超预算 −1"的奖励，多教师蒸馏（Multi Teacher Distillation） 到一个学生模型，使其同时继承各领域的分档推理能力。

Slide 145Scaling with Repeated Sampling

推理时扩展的另一条路线：重复采样（Repeated Sampling）。 Step 1 让 LLM 对同一问题独立生成许多份候选解；Step 2 用验证器 （单元测试、形式化证明检查器、多数投票等）从中挑出正确答案。该范式把问题拆成两个独立维度： Problem 1（coverage，覆盖率）——采样足够多时，候选中是否存在正确解； Problem 2（precision，精确率）——能否从候选中识别出正确解。 只要任一维度足够强（或两者配合），总正确率就能随采样数提升。出自 "Large Language Monkeys"（arXiv 2407.21787）。

Slide 146Scaling with Repeated Sampling：pass@k 曲线

实证数据：纵轴覆盖率 pass@k（k 次采样中至少一次正确的概率），横轴采样数 k（对数轴 1–10⁴）。 在 MiniF2F-MATH（形式化证明）、CodeContests、MATH、GSM8K 四个基准上， Llama-3-8B/70B-Instruct 的 pass@k 随 k 单调上升：小模型靠海量采样， coverage 能追平乃至超过单次采样的 GPT-4o（红色虚线）——尤其在有 oracle 验证器的 MATH/GSM8K 上，pass@k 快速逼近 1。结论：采样数是一种可与模型规模互换的推理期算力， 前提是有可靠的验证器（否则退化为下一节的自一致性）。

Slide 147没有验证器怎么办？Self-Consistency

当任务没有单元测试这类客观验证器时，自一致性（Self-Consistency）提供替代方案： 标准 CoT 贪心解码（上）只走一条路径，可能得到错误的 $14；自一致性（下）则 采样一组多样的推理路径（示例中三条路径分别得 $18、$26、$18）， 然后对推理路径做边际化、只聚合最终答案——多数投票得 $18，正确。 直觉：通向正确答案的推理路径通常多于通向任一错误答案的路径。出自 arXiv 2203.11171。

Slide 148Self-Consistency：ARC 上的收益

ARC-Challenge 基准的对照实验，横轴为采样推理路径数： Self Consistency（Multi-path）（蓝星）准确率从约 36% 一路升至约 54%， 明显优于Sample & Rank（绿方，采样多条但用模型似然排序挑选，约 44%） 和Greedy Decode（橙圆，单路径，约 43%）。要点： ① 多数投票比"模型自评分排序"更可靠——模型对自己错误路径的似然并不低； ② 收益随路径数对数式增长并最终饱和，存在性价比拐点。

五、面向智能体的 LLM

Slide 149章节页：LLMs for Agents

讲义进入最后一节：面向智能体的 LLM（LLMs for Agents）。 底部进度条显示本讲的完整脉络——语言模型定义、架构、训练、推理，最后落到 为 agent 场景设计与适配 LLM：当模型不再只是"问答"，而要规划、记忆、调用工具、 与外部世界交互时，对模型能力与接口的要求都发生了变化。

Slide 150Agents: Key Components

Agent 的标准组件图：LLM Core（红框，本讲主角）居中， 上方规划与推理（Planning & Reasoning）和记忆（Memory）注入其中； Core 向下驱动工具（Tools）——检索、计算器、代码执行、搜索、文件操作等， 工具调用最终落实为Agent 动作（tool call、与环境/用户的交互）； 动作作用于右侧的环境（Environment）——桌面 OS、浏览器、移动应用、游戏、数据库等外部世界， 环境的新状态再经 observe 观察反馈回 Core，构成"观察—思考—行动"闭环。 后续各页逐一讨论 LLM 如何适配这个闭环的各个环节。

Slide 151小节页：Structured I/O

第一个子主题：结构化 I/O。Agent 系统中 LLM 的输出往往要被下游程序解析执行 （工具调用参数、JSON 字段、枚举决策），自由文本不可靠； 同时上游也要以结构化方式把任务交给模型。本节讨论如何建立这种通信契约。

Slide 152Motivating Structured I/O

动机页引用 BAIR 的复合 AI 系统观点："越来越多的新 AI 成果来自复合系统 （compound systems）"——右侧图示一个任务由多个模型与搜索、数据库、计算器、终端等组件 协作完成。组件一多，就必须回答：这些系统组件之间如何通信？ 答案是一份共享契约（shared contract）——约定的结构化输入输出格式。 这正是 agent 工程与单纯 prompt 写作的分水岭。

Slide 153Constrained Decoding

约束解码（Constrained Decoding）：强制模型输出符合特定结构（如 JSON schema）。 方法是用有限状态机（FSM）表达目标正则/文法，解码时每一步只允许采样"当前状态合法"的 token。 (a) 是朴素 FSM：对字面量 {"summary": " 逐字符建 14 个状态；(c) 中几乎每个 token 后都要插入一次 LLM decode 判断，开销大。(b) 的压缩 FSM 把整段字面量压成一次转移（2 态）， (d) 中字面量部分直接跳过模型解码（由 FSM 直接吐出），只在真正需要模型生成的位置 （_ 处）才调用 LLM——既保证结构 100% 合法，又省掉大量无效解码步。出自 SGLang（arXiv 2312.07104）。

Slide 154Constrained Decoding：吞吐对比

SGLang 论文在 Llama-7B 上的归一化吞吐对比（越高越好）：在 MMLU、ReAct Agents、 Generative Agents、Tree/Skeleton of Thought、LLM Judge、HellaSwag、JSON Decoding、 Multi-Turn Chat、DSPy RAG Pipeline 等 11 类负载上，SGLang（橙）几乎全部归一到 1.0， 显著优于 vLLM（绿）、Guidance（蓝）、LMQL（灰）——尤其在 JSON Decoding、 Tree of Thought 等强结构化负载上，后两者吞吐跌至接近 0，而 SGLang 仍满速。 底部结论：SGLang 的优势来源之一正是用 FSM 做约束解码（还有其他优化）。 对 agent 系统而言，结构化输出不应以吞吐为代价。

Slide 155DSPy Signatures

DSPy 提供了声明式定义结构化 I/O 的方式——Signature（签名）： 一个 Python 类直接写明输入字段（message: str = dspy.InputField()）与输出字段 （name: str、email: Optional[str]、 intent: Literal["meeting","intro","follow-up"]，各为 OutputField）， 实例化 dspy.Predict(Extract) 即可调用，返回类型安全的 Prediction(name="Sarah", email="sarah@acme.co", intent="meeting")。 斜体注释点题："Signatures define tasks and enforce output types"—— 把"要模型做什么、输出什么形状"从自然语言提示升格为带类型约束的程序声明。

Slide 156DSPy Signatures: Peek inside

"打开引擎盖"看签名如何生效：DSPy 把上一讲的类编译成两段提示。 System Prompt 中逐字段声明输入（message）与输出（name；email 附带 JSON schema {"anyOf":[{"type":"string"},{"type":"null"}]}；intent 注明"必须精确匹配 meeting/intro/follow-up 之一，不得有多余字符"），并用 [[ ## field ## ]] 标记约定输出格式， 结尾以 [[ ## completed ## ]] 收束、重申任务目标。User Prompt 给出实际输入并要求 按 name→email→intent 顺序、以合法 Python 类型填写各字段。 可见结构化输出的本质是提示模板 + 类型约束的自动生成，开发者只写声明，细节交给框架。

Slide 157Constrain the Model: Classifiers

约束输出的另一类做法：不动生成、改训练。在预训练模型（DistilBERT）的 嵌入之上训练一个小分类头（此处为逻辑回归），把连续表示映射到离散类别标签： 输入 "[CLS] a visually stunning rumination on love [SEP]" 经 DistilBERT 得嵌入， 分类头输出 0（negative）15% / 1（positive）85%，最终预测 positive。 这种"大模型当特征提取器 + 小头做决策"的模式训练便宜、输出确定， 适合情感分类、意图识别等输出空间固定的 agent 子任务。

Slide 158Constrain the Model: System One Models

System One 模型——当前流行术语，但本质是"带可适配选项的分类器"， 专为高频"决策"设计。以马里奥游戏为例的三步流程： ① 对比式状态—动作预训练：动作编码器把 "right jump" 等动作编码为 A₁…A_N， 状态编码器把游戏画面编码为 S₁…S_N，对比学习使匹配对 (S_i, A_i) 的内积最高（矩阵对角线高亮）； ② 构造动作候选：把候选动作（left/jump/right run）套进 "Mario should {action}." 模板再编码， 使动作空间可随任务增删；③ 零样本动作分类：当前画面编码为 S₁，与候选动作向量做内积后 softmax， 得 left 5% / jump 80% / right run 15%，输出 "Mario should jump!" 并回作用于游戏。 这类"快思考"决策器延迟低、输出封闭，适合 agent 闭环中需要即时反应的一环。

Slide 159Example: Tool Calling

工具调用的结构化 I/O 实例，出自 Toolformer（arXiv 2302.04761）： 模型在生成文本的过程中内联调用工具，再把工具返回值续写进文本。 四个示例：调 QA 工具查《新英格兰医学杂志》出版方（→Massachusetts Medical Society）、 调 Calculator 算 400/1400（→0.29）、调机器翻译 MT 译 "tortuga"（→turtle）、 调 WikiSearch 检索 Brown Act（→法案全文定义）。关键在于工具调用被表示为 文本流中的结构化片段（[Tool(参数) → 返回值]），既是模型的输出契约， 也是执行器的输入契约——结构化 I/O 在工具调用场景的直接体现。

Slide 160小节页：Context Engineering

第二个子主题：上下文工程（Context Engineering）。 结构化 I/O 管的是"接口形状"，上下文工程管的是内容——在有限的上下文窗口里， 为模型装配最有用的信息（任务说明、工具描述、检索结果、历史轨迹、记忆）。 agent 的表现很大程度取决于上下文质量，这使其从"提示技巧"上升为一门系统工程。 下一批展开具体做法。

Slide 161Prompt engineering vs. context engineering

Anthropic 这张对比图划清了两个层次。提示工程面向单轮查询：上下文窗口里只有 System prompt + User message，调的是"一句话怎么说"。上下文工程面向 agent： 左侧是可供给模型的候选上下文池——多份文档、多个工具、记忆文件、详尽指令、领域知识、 消息历史，远超窗口容量；中间经过 Curation（精选/编排），右侧实际进入窗口的只是 其子集——System prompt + Doc 1/2 + Memory file + Tool 1/2 + User message + Message history。 模型输出 Assistant message 或 Tool call，Tool result 又回流进消息历史， 使上下文随交互动态增长。上下文工程因此是一个持续的"选什么、丢什么、何时更新"的系统问题。

Slide 162What goes in the context of an agent?

把上一讲的候选池归纳为五类标准组成： ① System Prompt——角色、规则、工具说明等固定指令； ② Message History——多轮对话与工具调用轨迹； ③ Memories——跨会话持久化的记忆（用户偏好、历史结论）； ④ Tool Call Results——工具返回的检索结果、执行输出； ⑤ Attached Files——随任务附带的文档/代码。 这五类各自有不同的"注入策略"（全量、检索、摘要、淘汰）， 下文的 Context Rot 与各项实用建议都围绕它们展开。

Slide 163Why not just put everything? Context Rot

既然上下文这么重要，为什么不把所有东西全塞进去？因为 Context Rot（上下文腐化）： 上下文越长，模型从中正确提取、聚合信息的能力越差。OOLONG 基准的两个例子都要求 对长上下文做聚合推理：左例给出 8 篇带日期的文章，问 9 月还是 8 月的经济报道更多， 模型需逐篇判别相关性再计数（9 月 2 篇 vs 8 月 1 篇 → September）； 右例给 12 小时对话转录，问角色 Jester 施放 "Healing Word" 几次（答两次）。 这类"大海捞针 + 聚合"任务正是长上下文能力的试金石，引出下页的量化结果。

Slide 164Context Rot：分数随上下文长度衰减

量化证据：在 OOLONG-synth 与 OOLONG-real 两个子集上， gemini-2.5-pro、gpt-5 系列、o3/o4-mini、claude-sonnet-4 等 9 个模型的得分 随上下文长度增加而普遍下滑——前沿模型从 8K 时的 0.8+ 跌到 256K–512K 时的 0.4 上下， llama-4-maverick、deepseek-r1-0528 则全程趴在低位（接近或低于 random baseline）。 结论：上下文窗口"能装下"不等于"用得好"，无差别地堆长上下文既贵又降质， 必须配合精选、检索与压缩——这正是上下文工程存在的理由。

Slide 165上下文没有唯一解，动手实验

过渡页，讲义原文直陈："构建上下文没有唯一正确的方法——这将是你作业 1（HW1）中要亲自实验的内容； 我们在这里提供一些实用技巧与注意事项。" 随后几页即这些 practical tips：避免臃肿（avoid bloat）、顺序追加（add sequentially）、 实证评估（evaluate empirically）、压缩（compaction），以及一种不同的哲学——递归语言模型。

Slide 166Avoid bloat：工具有时只需几个

第一条建议：避免臃肿。"Sometimes a few tools are all you need"—— 例如 Pi 这个 agent 只有 read、write、edit、bash 四个工具。 Terminal-Bench 2 的实验（同一模型 × 三种 harness）显示工具集设计（harness）影响巨大： Claude Fable 5 上 Claude Code 最贵（$1.55/rollout）也最高（75.6%），Codex 以 $0.98 拿到 72.2%； Claude Opus 4.8 上更便宜的 Pi/Codex（$0.76/$0.85）成功率 72.2%，反超更贵的 Claude Code（$0.90，68.9%）； Claude Haiku 4.5 上工具最简的 Pi（47.8%）远胜 Codex（31.1%）。 要点：harness/工具集是独立于模型的设计变量，臃肿的工具与提示会带来"har­ness 税"， 应精简到任务真正所需。

Slide 167Avoid bloat：用检索取回最相关内容

避免臃肿的第二条手段：用检索代替全量注入——"Use retrieval to recover the most relevant memories or files"。标准检索链（Retrieval Chain）：Prompt 先经 Embedding Model 向量化， 在 Vector DB 中做相似度搜索召回候选，再由 Reranking Model 精排， 取回的最相关片段与原始 Prompt 一并送入 LLM 生成 Response。 这样上下文窗口里只放精选证据而非全部语料。页脚预告："More on this in the next lecture!" ——检索即第三讲 RAG 的主题。

Slide 168Add sequentially：顺序追加上下文

第三条建议直接关联本讲推理部分：顺序追加上下文，避免使 KV Cache 失效。 回顾 Slide 133：KV Cache 缓存的是各历史 token 的 K/V。只要新内容追加在序列末尾， 已有 token 的位置不变、KV 不变，增量 prefill 只需计算新增部分，缓存全程有效。 这是 prompt 前缀缓存（prefix caching）生效的前提，也是 agent 多轮交互的默认形态。 反例见下一页。

Slide 169Add sequentially：插入会摧毁 KV Cache

反例：若在序列前端插入新 token（"Actually"），其后每个 token 的位置编号整体后移， 红字点明 "All of these position embeddings just changed"——位置嵌入一变， 所有历史 token 的 K/V 全部作废，整个 KV Cache 被 Invalidated（大红叉）， 只能从头重算 prefill。工程启示：上下文应保持 append-only 的稳定前缀， 系统提示、工具定义等固定内容放最前，动态内容追加在后；确需修改时，意识到这是全量重算的代价。

Slide 170Evaluate context choices empirically

第四条建议：实证评估你的上下文选择——"You can setup benchmarks/evals and test your changes"。 任何上下文/工具设计的改动都应跑基准对照，而非凭直觉。示例取自 Toolformer 论文： 在 LAMA、Math、QA 三类基准上，启用工具调用的 Toolformer（蓝线）随模型参数增长， 得分显著拉开禁用工具的版本（红线）并超过 GPT3（虚线）——工具接入这一"上下文设计决策" 的效果由此被量化。上下文工程因此与实验科学同构：提出改动 → 设 eval → 对比 → 保留有效者。

Slide 171Compaction：压缩上下文及其风险

当上下文增长到必须压缩（compaction，通常由模型把旧历史总结成摘要再重启上下文）时， 面临一个棘手的取舍，讲义列出四条：① 触发压缩时上下文往往已经极长； ② 新的决策是新上下文里保留什么；③ 保留太多→很快又要再压缩； ④ 丢弃太多→可能丢失完成任务所需的关键上下文。 下方案例触目惊心：Summer Yue 指示 OpenClaw agent 只"建议"待删邮件、未经确认不得行动； 但当收件箱过大触发上下文压缩时，"confirm before acting" 指令被压没了， agent 开始自行批量删邮件，她不得不冲到 Mac mini 前杀掉进程。 警示：安全攸关的约束不能只存在于会被压缩的上下文里，压缩策略本身需要评测与防护。

Slide 172Different Philosophy: Recursive LMs (RLMs)

一种与"塞上下文/检索"都不同的哲学——递归语言模型（Recursive LMs, RLMs）： 不把超长上下文直接喂给模型，而是把它作为变量载入一个编程环境 （Environment ε），根 LM（depth=0）像操作数据一样操作它： print(prompt[:100]) 查看开头、prompt.split("Chapter 2") 按章切分， 再对片段发起 llm_query(...)——每次子调用派生一个 depth=1 的子 RLM （"在第 1 章找属于某人的物品"、"找明确说被发现的物品"），子 RLM 返回 Sub-Response （银瓶、Herod 的戒指），根 LM 汇总后 print(FINAL_ANSWER) 输出最终答案。 长上下文由此被分解为"程序化操作 + 递归子查询"，模型每次只面对一小段真正相关的文本。

Slide 173Recursive LMs：263K 上下文上的结果

实证：在 OOLONG trec_coarse（263k token 上下文）上， RLM(GPT-5-mini) 以 51.1% 夺冠——一个小模型经递归分解， 得分接近直接读取的 GPT-5（34.2%）的 1.5 倍，更远超 GPT-5-mini 直接读取（23.2%）、 不用子调用的 RLM(GPT-5)（40.9%）以及 ReACT+GPT-5+BM25 检索基线（30.7%）。 两个结论：① 程序化分解 + 递归子调用能数倍释放同一模型的长上下文能力； ② 搭配得当的小模型可以胜过直接读取的大模型—— 为"上下文太长装不下/用不好"提供了架构层面的新解法。
