Effective Context Engineering for AI Agents

面向 AI 智能体的有效上下文工程
作者：Anthropic Engineering（Rajasekaran et al.）　|　出处：Anthropic Engineering Blog（2025）

TL;DR 背景 上下文工程 vs 提示工程 为什么重要：context rot 上下文的构成 按需检索 长程任务三策略 结论 影响与关联 术语对照
一句话总结（TL;DR）：上下文是智能体关键且有限的资源—— 上下文工程（context engineering）就是在每一次推理时，精心筛选并维护进入模型的最优 token 集合： 系统提示要找到「合适的高度」，工具与示例要少而典型，信息尽量「按需检索」而非预先塞满， 长程任务则依靠压缩（compaction）、结构化笔记（note-taking）、子代理（sub-agents）三种策略延续。

一、背景与要解决的问题

大模型的上下文窗口越来越大（数十万 token），一个直觉是「把所有可能相关的信息都塞进去」。 但 Anthropic 团队在构建 Claude Code 等长时运行智能体的实践中发现：塞得多 ≠ 表现好。 本文回答的问题是：智能体在多轮、长程任务中，应该如何筛选（curate）和维护（maintain）模型可见的信息， 才能持续保持高质量的表现。

"Context is a critical but finite resource for AI agents." 上下文是 AI 智能体的关键且有限的资源。

二、上下文工程 vs 提示工程

提示工程（prompt engineering）关注的是如何撰写和组织一次性的指令； 上下文工程（context engineering）则是更大的概念：管理推理时刻进入模型的整套内容—— 系统指令、工具定义、对话历史、检索到的外部数据、协议信息等，并把它视为一个随每一步推理不断更新的动态过程， 而不是一次写好的静态文本。

"Context engineering refers to the set of strategies for curating and maintaining the optimal set of tokens…" 上下文工程指的是一组策略，用于筛选并维护（进入模型的）最优 token 集合……

三、为什么重要：context rot（上下文腐化）

文章给出的核心依据是长上下文下的性能退化现象，业界称为 context rot：

  • 随着输入 token 增多，模型准确回忆信息、进行长距离推理的能力会下降；
  • 模型之间的注意力预算（attention budget）有限，token 越多，每个 token 分到的「有效注意力」越少；
  • transformer 架构与训练数据分布都使长序列更容易出现精度损失。
"models remain highly capable at longer contexts" ——模型在更长上下文下依然很有能力（但并非没有精度代价）。

因此结论是：应把上下文视为有递减回报的有限资源，精心减少低价值信息、最大化高价值信息的密度。

四、有效上下文的构成（The anatomy of effective context）

原文围绕三类组件给出设计准则：系统提示、工具、示例。

1. 系统提示：找到「合适的高度」（right altitude）

系统提示有两个失败极端：

  • 过度硬编码：写满脆弱的 if-else 式规则，环境稍变就失效；
  • 过度抽象：只给「要有帮助」「要好好干」这类空泛原则，等于没给。

正确做法是校准到中间的「合适高度」：给出明确但可泛化的行为启发（heuristics）。 实践上：从最小可行的系统提示开始测试，观察失败模式，再针对性补充规则——而不是一上来就写几千行。

2. 工具：像设计高质量函数一样设计

工具是智能体与环境之间的「约定」。准则：

  • 工具应自包含、对错误稳健、极其清晰（self-contained, robust to error, and extremely clear）；
  • 职责单一、彼此少重叠——工具集过大或功能雷同会让模型难以选择，也浪费上下文；
  • 参数命名与描述无歧义，返回省 token 且信息完整的结果；
  • 为常见错误提供有意义的报错信息，让模型能够自行恢复。
"tools should be self-contained, robust to error, and extremely clear" 工具应当自包含、对错误稳健、并且极其清晰。

3. 示例：典型而非穷举（canonical examples）

少样本示例（few-shot）依然重要，但要少而精：

  • 选择多样且典型的例子，代表目标行为；
  • 不要试图用示例覆盖所有边缘情况——堆砌大量边缘规则反而稀释高价值信息；
  • 对模型而言，一个好例子比十条规则更有效。

五、上下文检索与智能体式搜索（just-in-time retrieval）

两种把外部信息带入上下文的策略对比：

预先加载（pre-computed retrieval）按需检索（just-in-time / agentic search）
机制推理前用 RAG 等方式把相关文档一次性塞入上下文上下文中只保留轻量引用（文件路径、查询、链接、ID），运行时由智能体自己决定加载什么
优点快灵活：渐进式发现相关信息，不被无关内容污染
缺点可能带入大量无关信息、浪费 token更慢，需要好的工具与引导
"maintain lightweight identifiers" 维护轻量标识符（路径/查询/链接），需要时再加载完整内容。

实践建议是混合策略：文中以 Claude Code 为例——CLAUDE.md 这类项目级说明预先载入上下文， 其余文件由模型通过搜索/读取工具按需获取。

六、长程任务的三种上下文管理策略

Context engineering for long-horizon tasks —— 当任务超出上下文窗口时，如何让智能体保持目标、状态与连贯性。

策略 1：压缩（Compaction）

机制：当对话接近上下文窗口上限时，先把关键内容总结成摘要，再用摘要开启一个全新的上下文继续执行。

  • 摘要要保留：关键决策、未解决的问题、当前实现状态；
  • 删掉：冗余的工具输出、已完成的中间过程；
  • 清理旧的工具结果（tool results）是相对安全的轻量做法——它们通常占据大量 token 而后续很少被用到。
"Compaction is the practice of taking a conversation nearing the context window limit, …" 压缩指的是：当对话接近上下文窗口上限时，（对其进行总结并以摘要重启上下文的做法）。

适用：连续对话型、逐步推进的任务（Claude Code 的 auto-compact 即属此类）。

策略 2：结构化笔记 / 外部记忆（Structured note-taking）

机制：让智能体把状态写到上下文之外（文件系统、记忆工具），需要时再读回—— 相当于给智能体配一本「实验笔记本」。

  • 典型形态：待办清单（to-do list）、NOTES.md、文件式记忆工具；
  • 好处：笔记持久、可跨 compaction 存活，还能让用户直接查看智能体的计划；
  • 智能体在长任务中不断「记笔记 → 读笔记」，保持对目标与进度的追踪。

适用：有明确阶段进展、里程碑式的任务。

策略 3：子代理架构（Sub-agent architectures）

机制：主代理（orchestrator）负责高层规划与结果综合；把深搜、专项分析等工作分派给 拥有独立干净上下文的子代理，子代理只把浓缩后的结果返回给主代理。

  • 关键收益：子代理消耗的探索性 token 不会污染主代理的上下文；
  • 主代理上下文始终保持高信号密度，适合做最终决策。

适用：需要并行探索、广泛检索的研究型任务。

三种策略并不互斥：原文建议按任务形态选择或组合——连续对话用压缩，阶段式任务用笔记，并行探索用子代理。

七、结论

文章的收尾论点：即使未来模型能力持续增强、窗口持续变大，上下文工程的核心原则不会过时——

  1. 最小化低价值 token，最大化高价值信息密度；
  2. 让有限的上下文始终服务于当前任务目标；
  3. 把上下文当作需要持续策展（curate）的动态资源，而非一次性输入。

八、影响与后续

  • 本文让「context engineering」一词在 2025 年取代「prompt engineering」成为智能体开发的关键词， 被 Andrej Karpathy 等人在社区广泛引用传播。
  • compaction / 笔记 / 子代理三策略已成为长程智能体产品（Claude Code、各类 coding agent）的标配设计， 也直接对应 CS329Z 第二讲「上下文工程」与后续「Memory & Multi-Agent Systems」（第 7、8 讲）的内容。
  • 与第二讲必读《Building Effective Agents》互为补充： 前者讲「模式怎么选」，本文讲「每一步给模型看什么」。
