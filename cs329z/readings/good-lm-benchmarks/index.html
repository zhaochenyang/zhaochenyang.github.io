How to Build Good Language Modeling Benchmarks

如何构建好的语言模型基准

TL;DR 背景与问题 核心观点 设计框架剖析 结论与建议 影响与课程关联 术语对照
一句话总结：好的 benchmark 与好的模型同等重要——它应当自然（Natural）、可自动评测（Automatically Evaluateable）、足够难（Challenging）；作者给出的难度标准随模型能力飙升一路收紧：从「顶级模型得分 1%–35%」到「0.1%–9%」，再到要求设计出「即使模型能力提升 3 倍仍然得 0 分」的「-200%」级任务。每个任务应显式设计为 <request, environment, stopping criteria, scorer> 四元组，并配备接近真实使用方式的基线脚手架（scaffolding）。

背景与要解决的问题

作者是 SWE-bench 等基准的合作者，长期思考「什么样的 benchmark 才能真正推动领域进步」。文章开篇即指出：社区里推动某个 benchmark 上 SOTA 的工作很多，但「构建好的 benchmark 与构建新系统同样重要」。一个设计糟糕的基准会误导整个社区的努力方向——要么太容易很快饱和，要么形式不自然导致分数与真实能力脱节。这篇博文把作者的基准设计经验浓缩为三条核心属性、一条加分属性和一组实操守则，并随 LLM 能力的快速演进多次增补修订（2025 年 1 月、2025 年 5 月、2026 年 6 月）。

核心观点

属性 1：Natural——问题必须来自真实人类的真实需求

基准中的问题应当是「某类人群经常提出的自然问题」。典型正例：SWE-bench 使用真实 GitHub 仓库中用户提交的 bug 报告；AssistantBench 使用「找一节清晨瑜伽课」这类真实网页助理查询；CiteME 要求回答真实的学术溯源问题。检验标准很朴素：如果系统在基准上得分提高，是否真的能帮人节省时间、提升生产力？

作者点名两种常见的「不自然」设计：

  • 问题形式不真实：例如把开放式任务强行改成多选题（multiple choice）。「我看医生时从不会说：医生，我手肘疼，而且肯定是这四个选项之一导致的」。
  • 问题凭空编造：而非来自真实用户。更好的做法是从真实搜索日志/用户提问中筛选——例如用户翻到搜索结果第二页、或在页面停留超过 5 分钟，往往说明已有结果不够好，这类问题就是天然的高质量样本。
"Try to build a benchmark that has natural questions that some category of humans ask on a frequent basis." 尽量构建一个由某类人群经常提出的自然问题组成的基准。

属性 2：Automatically Evaluateable——答案对错必须能自动判定

给定模型生成的答案，基准必须能自动判断正误，否则无法规模化使用。代码类任务天然占优：可以用单元测试验证（如 HumanEval、SWE-bench）。摘要（summarization）类任务虽然有用但很难自动评测，因为「正确答案」形式多样。作者明确不赞成让同一个语言模型既作答又评分——这与 CS329Z 第 13 讲对 LLM-as-judge 偏差的讨论相呼应。

属性 3：Challenging——难度标准随时代不断收紧

如果发布时最强模型就能拿到 80% 准确率，这个基准会被立刻视为「已解决」而失去价值。作者的难度建议经历了三轮演进，本身就是一部 LLM 能力飙升的编年史：

时间建议的发布时顶级模型准确率说明
2024-08（初版）1% – 35%最初的「足够难」区间
2025-01 增补0.1% – 9%「高于此区间大概率太容易」
2025-05 增补「-200%」要求任务难到即使模型能力提升 3 倍仍得 0 分，并预判 6–12 个月后的模型水平
"Find questions that are so hard that even if the models improve 3x they'll still get zero." 去找那些难到即使模型能力提升 3 倍仍然得零分的题目。

若基线已达 70% 左右，可以过滤简单样本：Bamboogle 剔除 Google 搜索能直接答对的问题；CiteME 剔除 GPT-4o 在非智能体提示下能答对的问题。但 2026 年 6 月的增补给出警告：如果必须靠过滤才能让基准变难，说明整个任务分布太容易了，应当直接转向更难的领域。

难度也要有下限——分数过低会吓退研究者。SWE-bench 首发时最强模型仅约 1.96%，直到 SWE-agent 把它提到约 13%，才带动大量后续工作涌入。「看得见进步空间」是基准被采用的关键。

加分属性：抗数据污染（contamination resistance）

尽量让基准即使泄漏进训练数据也难以刷分。正例：SciCode 由博士生编写高难度科研编程题，并刻意不公开答案，从而降低答案混入训练语料的风险。

设计框架剖析

任务的 4-tuple 结构

文章结论部分给出了与 CS329Z 第 12 讲一致的四元组任务框架：benchmark = 一组任务，每个任务 = <request, environment, stopping criteria, scorer>。

"A benchmark is a collection of tasks, where each task is made up of <request, environment, stopping criteria, scorer> 4-tuples." 基准是任务的集合，每个任务由「请求、环境、停止条件、评分器」四元组构成。
组件含义示例
Request（请求）要模型实际完成的事SWE-bench：「修复这个 issue」+ issue 正文
Environment（环境）能否联网、依赖是否可用、提供哪些工具的完整描述代码任务应允许执行代码
Stopping criteria（停止条件）轮数上限、成本上限或墙钟时间防止无限循环烧钱
Scorer（评分器）二元通过/失败、连续分数或排名式分数SWE-bench 用测试判定；AlgoTune 用运行时间比值；CodeClash 用 ELO

基线脚手架要贴近真实使用方式

评估用的 scaffolding（脚手架）应尽可能接近当下最好的真实使用方式：代码任务应允许执行代码，知识任务应允许联网，否则「不现实」。作者强调这通常并不费事：

"mini-SWE-agent is able to get very competitive scores (and sometimes even surpass) Claude Code these days, even though it is orders of magnitude simpler." mini-SWE-agent 如今能拿到非常有竞争力（有时甚至超过）Claude Code 的分数，尽管它简单了好几个数量级。

结论与建议（实操守则）

  • 单一主指标：基准对外只推广一个易懂的总分；细分维度的分析放论文里，不要同时推多个指标或多个类别。
  • 强基线：必须包含顶级闭源模型与领先开源模型；不要用 GPT-3.5 或 Llama 3 7B 这类弱/过时模型充数。
  • 任务数量：至少约 150 个任务；最好 300–500 个以获得统计分辨率；超过 500 会运行太慢、不利于采用。「50 个大任务 × 每个 10 个子任务」也可接受。
  • 接受饱和周期：基准通常在约一年内饱和，不必强求五年有效；即使部分问题的答案会随时间变化，也可以接受。
  • 现实主义的传播优势：越贴近真实使用的基准越好「卖」（越容易被社区采用）。
本文没有实验数据，属于经验总结型（guidelines）文章；其说服力来自作者参与 SWE-bench 等基准的一手经验，以及文中大量正/反例（Bamboogle、CiteME、SciCode、AlgoTune、CodeClash、mini-SWE-agent）。

影响与课程关联

  • 与课程的关联：CS329Z 第 12 讲「Evaluation Fundamentals & Benchmark Design」讲授的 4-tuple 框架（request、environment、stopping criteria、scorer）与本文的「Concluding Thoughts」完全同源；必读文章（Zhu et al. 2025《Establishing Best Practices for Building Rigorous Agentic Benchmarks》）是对本文经验法则的系统化、实证化版本。
  • 领域影响：「发布时顶级模型得分应低于 10%」与「-200%」难度哲学直接影响了后续 agentic benchmark 的设计取向（如更难的多步骤、长程任务）；SWE-bench 从 1.96% 到 13% 再到饱和的完整生命周期，成为「基准约一年饱和」论断的经典注脚。
  • 对智能体构建者的启示：为自己的智能体产品搭内部 eval 时同样适用——任务来自真实用户失败案例、能自动判分、留出能力增长空间（呼应第 13 讲 Anthropic 的 evals 路线图）。
