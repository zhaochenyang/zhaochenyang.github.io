Demystifying Evals for AI Agents

揭秘 AI 智能体的评估体系
Mikaela Grace, Jeremy Hadfield, Rodrigo Olivares, Jiri De Jonghe（Anthropic Applied AI / Engineering）· Anthropic Engineering Blog · 2026-01-09
阅读原文（Anthropic） 专栏首页
TL;DR 背景与问题 核心观点 三类评分器与路线图 结论与建议 影响与课程关联 术语对照
一句话总结：智能体的多轮、用工具、改环境等特性让评估远比单轮 LLM 困难；Anthropic 给出一套完整工程方法论——用 task / trial / grader / transcript / outcome / harness 拆解评估对象，按任务类型组合代码型、模型型、人工三类评分器，用 pass@k 与 pass^k 应对非确定性，遵循 Step 0–8 路线图从 20–50 个真实失败任务起步，并牢记两条铁律：「grade what the agent produced, not the path it took（评结果，不评路径）」与「Read the transcripts!（去读轨迹！）」。

背景与要解决的问题

智能体之所以有用，正是因为它能跨多轮调用工具、改变环境状态、并根据中间结果调整行为——但这些特性也让评估变难：错误会跨步骤传播，模型还可能给出评测设计者没预料到的有效解法。没有评估体系的团队会陷入被动修复循环：用户投诉后才发现回归（regression），修一个问题又引入新问题。

"Good evaluations help teams ship AI agents more confidently. Evals make problems and behavioral changes visible before they affect users." 好的评估让团队更有信心地发布 AI 智能体；评估让问题和行为变化在影响用户之前就可见。

评估的价值不止防回归：它还定义产品的成功标准、加速模型升级决策（新模型好不好，跑一遍 eval 就知道）、建立基线、降低团队沟通成本。

核心观点

观点 1：先把评估的「对象」拆清楚

概念含义
Task（任务）一条测试用例：输入 + 成功标准
Trial（单次尝试）同一任务的一次运行（非确定性 → 需要多次）
Grader（评分器）对表现打分的逻辑
Transcript（轨迹）完整过程记录：输出、工具调用、推理、中间结果
Outcome（结果状态）环境里实际发生了什么——而非模型「说」它做了什么
Evaluation harness运行评测的基础设施（跑 trial、打分、汇总）
Agent harness让模型成为智能体的运行框架（工具、循环、提示）
Evaluation suite一组同类任务的集合

评估按复杂度分层：简单单轮评测 → 多轮评测 → 完整智能体评测。

观点 2：非确定性要用 pass@k 与 pass^k 度量

同一任务多次运行结果可能不同，绝不能只看一次通过与否：

  • pass@k：k 次尝试中至少成功一次的概率——适合「只要有一次做对就有价值」的场景；
  • pass^k：k 次尝试全部成功的概率——适合强调稳定可靠的用户场景。

文中例子：单次成功率 75% 时，连续 3 次全部成功（pass^3）只有约 42%——「看起来还行」的单次成功率在重复使用下会迅速崩塌。

观点 3：评结果，不评路径

"Grade what the agent produced, not the path it took." 评分应针对智能体产出的结果，而不是它走过的路径。

过度检查固定执行路径（必须按某种顺序调用某些工具）会把「合理但不同」的解法判为失败；同时评分器要防绕过——不能让智能体靠钻测试漏洞（而非真正解决问题）通过评估。

观点 4：低分常常是评测坏了，不是模型坏了

  • 任务歧义：若两位领域专家不能独立得出一致的通过/失败判断，任务本身就有问题；评分器检查的所有条件都应能从任务描述中推出。
  • 0% 通过率警报：
    "0% pass rate across many trials (i.e. 0% pass@100) is most often a signal of a broken task."大量尝试下 0% 通过率（即 pass@100 = 0），多数时候是任务坏掉的信号。
  • 评分器/环境 bug：评分过严、随机性无法复现、测试环境配置错误都会造成假失败——文中引用 CORE-Bench 与 METR 的例子：修正评测缺陷后分数显著变化。
  • 环境共享状态：不同 trial 共享残留文件、缓存、历史数据会造成假失败或假成功；理想情况每个 trial 从干净隔离的环境开始。
  • 任务不平衡：只测「行为应该发生」的情况、不测「不应该发生」的情况，会导致优化偏斜（例如只奖励搜索 → 智能体过度搜索）。
  • 评估饱和（eval saturation）：接近满分的评测只剩回归检测价值，重大能力进步只会表现为小幅分数增长，需要更难、更贴近复杂现实的任务。

三类评分器与 Step 0–8 路线图

三类 grader 的分工

类型适用常见方式优缺点
代码型（code-based）明确、可程序化验证的条件字符串/正则/模糊匹配、失败转通过测试、静态分析（lint/类型/安全）、结果状态验证、工具调用验证、轨迹分析（轮数、token 用量）快、便宜、客观、可复现、易调试；但对合理变体脆弱，缺主观判断力
模型型（model-based，LLM-as-judge）开放式、主观性强、输出形式多样的任务规则化评分（rubric）、自然语言断言、成对比较（pairwise comparison）、参照答案评估、多评审共识灵活、可扩展、能捕捉细微差别；但非确定、成本更高，需与人工判断校准
人工（human）高质量判断、专家审查、校准模型评分领域专家审查、众包、抽样检查、A/B 测试、评分者一致性分析最接近真实用户/专家判断，是校准基准；但昂贵、慢、难以高频运行

单任务打分可以是加权分、二元通过或混合方式。LLM-as-judge 的设计原则：清晰结构化的评分标准（rubric）；每个维度用独立 judge，不要让一个 judge 同时判断所有方面；允许 judge 在信息不足时返回「Unknown」以减少幻觉式判断；反复与人类专家校准；支持部分得分而非全对全错。

Step 0–8 路线图（Anthropic 官方实践）

  1. Step 0 · Start early（尽早开始）：不要等有几百个任务才动手——早期用 20–50 个来自真实失败的任务就够，因为早期改动影响明显，小样本也能看出变化。
  2. Step 1 · 从已有手动测试入手：把开发中已在手动检查的行为、发布前验证、常见用户任务、bug 记录、客服问题转成测试用例，按用户影响排序。
  3. Step 2 · 写清晰任务并准备参考解：好任务的标准是两位专家独立判断结论一致；为每个任务准备一个已知可通过的参考解，用于验证任务与评分器本身没坏。
  4. Step 3 · 构建平衡的问题集：既测应该触发的行为，也测不应该触发的行为（如搜索评测同时覆盖「需要搜索」与「应直接回答」的问题）。
  5. Step 4 · 构建稳定评测环境：评测中的智能体尽量接近生产系统，但每个 trial 相互隔离，避免残留状态造成噪声或虚高分数。
  6. Step 5 · 谨慎设计评分器：优先确定性评分；必要时用模型评分换取灵活性；人工评分用于高质量校验。避免过度约束路径、支持部分得分、校准 judge、防钻空子。
  7. Step 6 · 检查轨迹：必须阅读 trial 记录，判断失败是模型真实错误还是评分器误杀合理答案。
    "Read the transcripts!"去读轨迹！
  8. Step 7 · 监控能力评测饱和：满分/近满分的评测不再提供改进信号，只能做回归防护；饱和后要换更难、更贴近复杂现实的任务。
  9. Step 8 · 长期维护评测集：评测集是持续演化的资产——专门团队维护核心评测基础设施，产品与领域专家贡献任务；评测任务可以像单元测试一样由工程师持续提交。

按智能体类型选择评估重点

类型评估重点代表基准
编码智能体确定性测试为主：代码能否运行、测试是否通过；辅以代码质量、工具调用、轨迹指标SWE-bench Verified、Terminal-Bench
对话智能体任务完成 + 交互质量；常用第二个模型模拟用户；检查状态、轮数、语气与解释质量τ-Bench、τ²-Bench
研究智能体输出开放主观，需组合评分：来源支持度、关键事实覆盖、来源权威性、答案一致性；唯一答案题用精确匹配，综合题用校准过的模型评分—
计算机操作智能体真实/沙盒 GUI 环境，检查最终环境状态而非界面显示；浏览器任务在 DOM 提取与截图间权衡 token 效率与延迟—

结论与建议

  • 能力评测 vs 回归评测：能力评测问「还能不能更好」（初始通过率低，留提升空间）；回归评测问「是否还能做到以前能做的」（应接近全通过）。能力评测通过率涨上去后，可转入持续运行的回归套件。
  • 评估之外的补充信号：自动化评测（快、可复现、每次变更前跑）+ 生产监控（真实但事后）+ A/B 测试（真实用户结果但慢）+ 用户反馈（能发现未知问题但稀疏）+ 人工读轨迹（理解失败模式但不可扩展）+ 系统化人工研究（主观任务/校准 judge 但贵）——多重防护，没有单一方法能抓住所有问题。
  • 现成框架：Harbor（容器化大规模试验）、Braintrust（离线评估 + 生产可观测 + 实验跟踪）、LangSmith（追踪/评估/数据集管理）、Langfuse（同类能力、可自托管）、Arize（Phoenix 与 AX，追踪-调试-评估-监控）。框架只是加速器，价值取决于高质量任务与评分器。
  • 核心结论：没有评估的团队陷入被动修复；尽早建立评估反而加速开发——失败转化为测试用例，测试用例防止回归，指标替代猜测。评估不是一次性工程，而是智能体开发的核心组件。

影响与课程关联

  • 与课程的关联：本文是 CS329Z 第 13 讲「LLM-as-Judge & Evaluation Infrastructure」的主干必读——讲次主题中的三类 grader、judge 提示设计、已知偏差、pairwise vs pointwise、pass@k vs pass^k、harness 设计、「Anthropic 8 步路线图」全部出自本文；与第 12 讲的 4-tuple 框架（task = request + environment + stopping criteria + scorer）直接衔接，也与本讲另两篇必读（MT-Bench 的 LLM-as-judge 学术奠基、AutoMetrics 的自动评估器生成）构成「工程实践—学术方法—自动化前沿」三角。
  • 领域影响：作为头部智能体厂商的一线工程总结，「Read the transcripts」「grade the outcome, not the path」「pass^k 衡量稳定性」等提法已成为智能体评估的通用语汇；τ-Bench、SWE-bench Verified 等基准的推荐也让本文成为选型参考。
  • 对智能体构建者的启示：从 20–50 个真实失败案例起步、为每个任务写参考解、用独立 judge 分维度打分、警惕 pass@100=0 的坏任务——这些是可以直接落地的 checklist。
