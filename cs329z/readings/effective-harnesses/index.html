Effective Harnesses for Long-Running Agents

面向长时间运行智能体的有效 Harness（工程脚手架）

一句话总结：要让智能体在跨越多个上下文窗口的长任务（如从零构建一个完整 Web 应用）中可靠工作，仅靠上下文压缩（compaction）不够——需要一套工程化的 harness（脚手架）：用「初始化智能体 + 编码智能体」双角色，把项目状态外化为文件、Git 历史、进度记录与结构化功能清单，让每个新会话都能像接手项目的工程师一样快速上手、小步推进、可验证、可回退。

背景与要解决的问题

复杂项目无法在一个上下文窗口内完成，长任务必须拆成多个离散会话，而新会话不知道之前发生了什么。作者以「让 Claude Agent SDK + Opus 4.5 从零构建一个 claude.ai 克隆」为例说明：只给高层提示时，即使模型很强，也产不出生产级应用。典型失败模式包括：

  • 智能体试图「一口吃成胖子」（one-shot 整个应用），一次做太多事；
  • 上下文耗尽后代码停留在半成品状态、没有文档，后续会话只能靠猜；
  • 后期会话看到已有进展，过早宣布项目完成；
  • 环境里留下 bug、混乱代码或未记录的进展；
  • 功能没做端到端测试就被标记为完成；
  • 新会话浪费大量时间弄清如何启动应用。

上下文压缩（compaction）能缓解但不能根治：指令与状态仍可能传递不清。文章的答案是向人类工程团队的协作方式学习——项目知识不该只存在于某个人的脑子里，而应外化为文档、版本历史与任务清单。

核心观点

观点 1：Harness 是弥补上下文断裂的关键基础设施

文中的 harness 指围绕模型运行的工程化脚手架：提示词、工具、脚本、文件、Git、测试流程与会话交接机制。Agent 是执行任务的模型循环，harness 负责给它方向、状态、工具和可恢复的工作环境。

"Relying on compaction alone is not enough to make agents work reliably over long time horizons." 仅靠上下文压缩，不足以让智能体在长时间跨度上可靠工作。

观点 2：双角色结构——Initializer Agent 与 Coding Agent

首次会话用初始化智能体（initializer agent）搭好地基，后续会话都用编码智能体（coding agent）增量推进。作者强调二者的差异主要只是不同的初始用户提示词（different initial user prompts）——角色由 harness 的 prompt 定义，而非不同的模型。

观点 3：状态外化——文件、Git、进度记录

初始化阶段建立四件套：init.sh（一键启动环境）、claude-progress.txt(进度记录)、初始 Git 提交、以及完整功能清单。此后每个新会话的启动流程固定：运行 pwd 确认环境 → 读进度文件、功能清单、Git 日志 → 检查 init.sh → 启动开发服务器做冒烟测试 → 才开始开发。先验证已有功能再叠加新功能，避免在已损坏的应用上继续施工。

观点 4：用 JSON 功能清单驱动增量开发

初始化智能体把高层需求展开成结构化功能项（claude.ai 克隆一例生成了超过 200 个功能项），全部标记为「failing」；编码智能体每轮只挑一个高优先级未完成功能（one feature at a time），充分测试后才允许把状态改为「passes」。清单用 JSON 而非 Markdown——JSON 更不容易被模型随意改写，并配合强约束提示：

"It is unacceptable to remove or edit tests." 删除或修改测试是不可接受的。

观点 5：像真实用户一样做端到端验证

明确要求智能体做端到端测试而不是只跑单元测试；在 Web 应用示例中通过 Puppeteer MCP 操作浏览器并截图验证 UI。只有充分测试后才把功能标为「passing」，直接针对「过早宣布完成」这一失败模式。

Harness 设计剖析

架构图（原文示意，文字描述）：左侧为 Initializer Agent 会话——读取高层需求后生成 init.sh、claude-progress.txt、200+ 项 JSON 功能清单（全部 failing）并做初始 Git 提交；右侧为多个 Coding Agent 会话依次接力——每个会话先读进度文件/功能清单/Git 日志恢复状态，选取一个高优先级功能，实现→端到端测试（Puppeteer 截图）→更新 passes 状态→写清晰提交信息→更新进度文件，留下「干净可交接状态」给下一个会话。
机制做法针对的失败模式
初始化脚手架init.sh + 进度文件 + 初始提交 + 完整功能清单新会话不知如何启动、不知道项目全貌
JSON 功能清单类别/描述/步骤/passes 字段；初始全部 failing；只许改 passes需求被模型改写、范围漂移、过早完成
单功能增量每轮只做一个高优先级功能（one feature at a time）一次做太多、半成品堆积
会话启动协议pwd → 读进度/清单/Git 日志 → 启动服务器 → 冒烟测试盲目开工、在损坏状态上叠加
Git 检查点频繁提交、清晰提交信息；出错可 git revert/回退到可用状态错误改动无法恢复
端到端测试Puppeteer MCP 浏览器操作 + 截图验证；测试通过才标 passes「看起来完成」但未验证
干净交接每次会话结束时保持 clean state：代码整洁、无重大 bug、进度已记录下一位「工程师」面对烂摊子

功能清单条目示例（JSON 结构）

{
  "category": "chat",
  "description": "用户可在会话中发送消息并收到流式回复",
  "steps": ["...", "..."],
  "passes": false
}

结论与建议

  • 长时间运行智能体的关键不是单次会话更强，而是多个上下文窗口之间的可靠交接：初始化阶段建立完整需求、脚本与记录机制；后续阶段小步推进、持续测试、提交 Git、留下清晰进度。
  • 该方法显著减少「迷失、回退、虚假完成」三类问题。
  • 开放问题（作者原文提出）：单一通用智能体是否最优，还是应由测试、QA、清理等专用智能体组成多智能体系统？这些经验能否推广到 Web 开发之外的领域？
  • 文中提到配套代码示例见 Claude Agent SDK quickstart。

影响与课程关联

  • 与 CS329Z 第 15 讲（Coding & Software Agents）的关系：该讲的核心论点之一是「scaffold（脚手架）即设计决策」——SWE-agent、Claude Code、OpenHands 的差异很大程度在脚手架而非模型。本文是这一论点最直接的工程实证：同一模型（Opus 4.5），有无 harness 决定能否产出生产级应用。
  • 与课程其他讲次的呼应：状态外化到文件呼应第 7 讲「文件系统作为外化记忆」（MemGPT/Letta 的思路）；单功能增量 + 清单驱动呼应第 6 讲 plan-and-execute 模式；「先验证再开发、端到端测试」呼应第 12–13 讲评估基础设施（verifier/scorer 设计）。
  • 实践影响：「progress 文件 + JSON 功能清单 + 会话启动协议」已成为社区构建 long-running coding agent 的常见模式，与 Claude Code 最佳实践中的 checklist/scratchpad 建议一脉相承。
