DSPy: Compiling Declarative Language Model Calls into Self-Improving Pipelines

DSPy：将声明式语言模型调用编译为自我改进的流水线

TL;DR 背景与问题 核心观点 编程模型与编译器 实验结果 影响与课程关联 术语对照
一句话总结：DSPy 主张把「手写提示词」换成「写程序 + 编译」：开发者用签名（signature）声明每一步文本转换「做什么」，用模块（module）像搭 PyTorch 网络一样组合流水线，再由优化器（optimizer/teleprompter）针对给定指标自动学习提示组合、few-shot 示例乃至微调权重。编译后 GPT-3.5 与 Llama2-13b-chat 相比标准 few-shot 提示分别通常提升 25% 与 65% 以上，编译到 770M 参数 T5 的小模型流水线可与依赖专家手写提示链的 GPT-3.5 方案竞争。

背景与要解决的问题

当前 LLM 应用的主流开发方式是：人肉试错拼出冗长的提示模板（prompt templates），把指令、few-shot 示例、思维链触发语等硬编码进字符串。DSPy 论文开篇指出这种做法的根本缺陷：

"...hard-coded 'prompt templates'... can be brittle and unscalable... conceptually akin to hand-tuning the weights for a classifier." 硬编码的提示模板……可能既脆弱又难以规模化……这在概念上相当于手工调一个分类器的权重。
A single prompt string "might not generalize to different pipelines or across different LMs, data domains, or even inputs." 单一提示字符串「可能无法泛化到不同的流水线、不同的语言模型、不同的数据域，甚至不同的输入」。

换句话说：提示工程把「任务逻辑」与「如何向特定模型表达任务」耦合在了一起。换个模型、换个流水线结构、换个数据域，精心调好的提示就可能失效，只能重新手调。DSPy 的答案是借鉴深度学习框架的经验——声明式编程 + 自动优化：正如 PyTorch 用户定义网络结构（计算图）而把权重交给优化器，DSPy 用户定义 LM 调用的「文本转换图」而把提示/示例/权重交给编译器。

核心观点

观点 1：LM 流水线是「文本转换图」，应当被声明而非硬编码

DSPy 把任意 LLM 流水线抽象为 text transformation graphs（文本转换图）：节点是带参数的声明式 LM 调用，边是文本（中间结果）流动。程序里不再出现手写提示字符串，只出现签名（这一步把什么输入变成什么输出）与模块（用哪种调用策略）。

观点 2：签名（Signature）——「做什么」而非「怎么做」

签名是对函数的自然语言类型声明（natural-language typed declaration of a function）。最简形式如 question -> answer：字段名承载语义角色，DSPy 会自动将其扩展为对 LM 有意义的指令；复杂签名可附字段描述与类型（如 answer: bool）。签名声明「做什么」，把「怎么向模型说」留给编译器。

观点 3：模块（Module）——参数化、可组合的调用策略

模块是参数化的可调用组件，类似 PyTorch 的层。基础模块 Predict 保存签名、可选 LM 与 demonstrations（示例）列表；ChainOfThought、ReAct、MultiChainComparison 等都通过组合 Predict 实现——例如 ChainOfThought 只是在签名前添加一个带 "Let's think step by step." 前缀的推理输出字段。模块的「参数」（指令文本、few-shot 示例、甚至 LM 权重）不靠人写，靠优化器学。

观点 4：优化器（Optimizer / Teleprompter）——把提示工程变成编译

给定 DSPy 程序 + 少量训练输入 + 指标函数，优化器自动改进程序。论文给出三阶段视角：

  1. 候选生成（Candidate Generation）：递归找出程序里所有 Predict 模块，用「教师程序」在训练输入上模拟运行、追踪多阶段 traces，经指标过滤（拒绝采样）得到候选 demonstrations——BootstrapFewShot 即此策略；
  2. 参数优化（Parameter Optimization）：对候选示例、指令等参数用随机搜索或 Optuna 等超参优化选择最优组合；BootstrapFinetune 则更进一步，把示例用于微调小模型权重；
  3. 高阶优化（Higher-Order Optimization）：修改程序控制流本身，如把程序复制为集成（ensemble）再用多数投票归约预测。

优化器可组合：昂贵程序（大模型 + 复杂流水线）可以作为 teacher 去监督廉价程序（小模型 + 简单流水线）——这为「用 GPT-4 级模型蒸馏出小模型流水线」提供了系统化的路径。

编程模型与编译器：一个完整示例

论文用一个简洁的 RAG 系统展示 DSPy 的表达力（附录另给出多跳检索、代理循环等更复杂程序）：

签名声明（自然语言「类型签名」）：
class GenerateSearchQuery(dspy.Signature):
  """Write a simple search query that will help answer a complex question."""
  context = dspy.InputField(desc="may contain relevant facts")
  question = dspy.InputField()
  query = dspy.OutputField()

程序组装（模块像神经网络层一样组合）：
class RAG(dspy.Module):
  def __init__(self):
    self.retrieve = dspy.Retrieve(k=3)
    self.generate_answer = dspy.ChainOfThought("context, question -> answer")
  def forward(self, question):
    context = self.retrieve(question).passages
    return self.generate_answer(context=context, question=question)

之后只需 teleprompter.compile(RAG(), trainset=...)，优化器就会为每个模块自举示例、调好指令——全程没有手写提示字符串。把 ChainOfThought 换回 Predict、或把签名改成 "context, question -> search_query"，都只是一行改动（体现模块化）。

与 LangChain / LlamaIndex 等库相比（论文附录 B 专门讨论）：这些库聚焦「把 LM 调用与外部组件接起来」的集成胶水，提示仍由人手写；DSPy 关注的是把这些调用组织成可优化的程序——两者定位不同，DSPy 程序中完全可以调用检索器等组件。

实验结果与结论

案例研究覆盖四类任务：数学应用题推理（GSM8K）、多跳检索问答（HotPotQA）、带引用的复杂问答、代理循环（ReAct 式）。核心数字：

任务 / 模型基线（zero-shot 或手写 few-shot）DSPy 编译后
GSM8K · GPT-3.524.0%（zero-shot）；论文口径整体 33%bootstrap CoT 72.9% → reflection+bootstrap 76.0%（论文口径整体 82%）
GSM8K · Llama2-13b-chat7.0%（zero-shot）；论文口径整体 9%reflection+bootstrap 46.9%（论文口径整体 47%）
HotPotQA 多跳 · GPT-3.5手写 few-shot 31.5%multihop+bootstrap 39.6% → +集成 45.6%
HotPotQA 多跳 · Llama2-13b-chat手写 few-shot 21.8%multihop+bootstrap 36.4% → +集成 41.0%
HotPotQA · T5-Large（770M 参数，微调）—dev EM 39.3% / 段落准确率 46.0%，仅用 200 条标注 + 800 条无标注问题

摘要层面的总结论：编译后流水线相对标准 few-shot 提示，GPT-3.5 与 Llama2-13b-chat 通常分别提升 25% 与 65% 以上；相对专家手工构造示例的流水线，提升可达 5–46% 与 16–40%；编译到 770M T5 或 Llama2-13b-chat 的 DSPy 程序，可与依赖专家提示链的专有 GPT-3.5 方案竞争。

结论：把提示工程从「手工艺」变为「编译问题」是可行且高收益的——简洁的声明式程序足以表达复杂流水线，而自动优化系统性地超过人工调参。

影响与课程关联

  • 与第五讲的关系：CS329Z Lecture 5「Frameworks & Agent Design」以 DSPy 为必读，正对应其主题「框架抽象了什么 vs. 你从零构建了什么、如何选择抽象层级」——DSPy 代表「声明式 + 编译器」这一抽象路线，与 LangChain/LangGraph（编排胶水）、LlamaIndex（数据框架）形成对照。
  • 作者脉络：一作 Omar Khattab 也是 ColBERT（本专栏 第三讲扩展阅读精讲）的一作，通讯/资深作者包括 Matei Zaharia（Spark 之父、复合 AI 系统一文主笔）与 Christopher Potts——DSPy 可视为「复合 AI 系统」理念在编程模型层面的落地。
  • 领域影响：DSPy 开创了「LM 程序编译」范式，后续 prompt 优化研究（MIPROv2、GEPA 等，均为 CS329Z 第九讲 Optimization 的阅读材料）多以 DSPy 为宿主框架；其内建的 ReAct 模块也把第六讲必读的 ReAct 模式变成了可组合组件。
  • 工程启示：当你发现自己在反复手调提示、且提示换个模型就失效时，DSPy 的路径是：写出签名与模块结构 → 定义指标 → 准备少量训练输入 → 让优化器自举示例与指令；对小模型场景还可用 BootstrapFinetune 把优化结果固化进权重。
