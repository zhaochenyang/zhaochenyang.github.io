Model Context Protocol Specification

一句话总结：MCP（Model Context Protocol，模型上下文协议）是一个开放协议，为 LLM 应用连接外部数据源与工具提供标准化方式——官方入门文档把它比作「AI 应用的 USB-C 接口」。协议基于 JSON-RPC 2.0，定义了 host–client–server 三层架构、服务器端原语（tools / resources / prompts）与客户端原语（sampling / roots / elicitation），通过能力协商与有状态会话实现「一次构建、处处集成」（build once and integrate everywhere）。

背景与要解决的问题

在 MCP 出现之前，每个 AI 应用要接入每个外部系统（文件、数据库、日历、搜索引擎、企业内部 API……）都需要写一套定制集成：M 个应用 × N 个数据源/工具 = M×N 条互不兼容的胶水代码。这与当年编辑器为每种编程语言单独写补全/跳转支持的困境如出一辙——微软用 LSP（Language Server Protocol）把「编辑器 × 语言」的 M×N 问题变成「编辑器实现一次 LSP 客户端 + 每种语言实现一个 language server」的 M+N 问题。MCP 规范开宗明义地承认了这一灵感来源：

"MCP takes some inspiration from the Language Server Protocol, which standardizes how to add support for programming languages across a whole ecosystem of development tools. In a similar way, MCP standardizes how to integrate additional context and tools into the ecosystem of AI applications." MCP 从语言服务器协议（LSP）中获得了一些灵感：LSP 标准化了在整个开发工具生态中添加编程语言支持的方式；类似地，MCP 标准化了向 AI 应用生态集成额外上下文与工具的方式。
"Think of MCP like a USB-C port for AI applications. Just as USB-C provides a standardized way to connect electronic devices, MCP provides a standardized way to connect AI applications to external systems." 把 MCP 想象成 AI 应用的 USB-C 接口：正如 USB-C 为电子设备提供了标准化的连接方式，MCP 为 AI 应用连接外部系统提供了标准化的方式。（官方入门文档）

按照官方文档，MCP 让 AI 应用（如 Claude、ChatGPT）能够连接数据源（本地文件、数据库）、工具（搜索引擎、计算器）与工作流（专用提示模板），典型场景包括：智能体访问你的 Google Calendar 和 Notion 成为个性化助理、Claude Code 依据 Figma 设计稿生成整个 Web 应用、企业聊天机器人连接组织内多个数据库等。

核心概念：协议定位与三类角色

概念 1：MCP 是什么、管什么

MCP 提供标准化的方式让应用：与语言模型共享上下文信息、向 AI 系统暴露工具与能力、构建可组合的集成与工作流。协议使用 JSON-RPC 2.0 消息在三类角色之间建立通信：

"Hosts: LLM applications that initiate connections. Clients: Connectors within the host application. Servers: Services that provide context and capabilities." Host（宿主）：发起连接的 LLM 应用；Client（客户端）：宿主应用内部的连接器；Server（服务器）：提供上下文与能力的服务。

基础协议的三个关键特征：JSON-RPC 消息格式、有状态连接（stateful connections）、服务器与客户端能力协商（capability negotiation）。

概念 2：设计原则——服务器极简、可组合、彼此隔离

规范列出四条设计原则：① 服务器应当极易构建（复杂编排责任由宿主应用承担，服务器只专注定义良好的单一能力）；② 服务器应当高度可组合（多个服务器可无缝组合，共享协议保证互操作）；③ 隔离性；④ 特性可以渐进式添加（核心协议只提供最小必需功能，其余能力按需协商）。

"Servers should not be able to read the whole conversation, nor 'see into' other servers." 服务器不应当能读到整个对话，也不应当能「窥视」其他服务器。（完整对话历史留在宿主侧；每个服务器连接保持隔离；跨服务器交互由宿主控制——这是协议层面的安全边界。）

概念 3：一次构建、处处集成

官方入门页强调生态支持：Claude、ChatGPT 等 AI 助手，Visual Studio Code、Cursor 等开发工具都已支持 MCP。对三类角色的收益分别是：开发者——降低构建/集成 AI 应用的时间与复杂度；AI 应用/智能体——获得整个数据源与工具生态，能力与用户体验提升；终端用户——AI 应用能在必要时访问用户数据、代用户采取行动。

架构与功能原语

Client–Host–Server 架构

MCP 采用 client–host–server 架构：一个宿主进程内可以运行多个客户端实例，每个客户端与一个特定服务器保持 1:1 的有状态会话。规范中的架构图（mermaid 绘制）如下：

架构图解读（对应规范 Architecture 页的示意图）：最外层是应用宿主进程（Application Host Process），内含 Host 与 Client 1/2/3；本地机器上有 Server 1（文件与 Git）和 Server 2（数据库），分别连接本地资源 A/B；互联网上有 Server 3（外部 API），连接远程资源 C。每条 Client→Server 连线是一条独立的协议会话。
角色职责（规范原文归纳）
Host 宿主容器与协调者：创建并管理多个客户端实例；控制客户端连接权限与生命周期；执行安全策略与用户同意（consent）要求；处理用户授权决策；协调 AI/LLM 集成与 sampling；跨客户端聚合上下文
Client 客户端由宿主创建，与每个服务器维持一条隔离的有状态会话；负责协议协商与能力交换；双向路由协议消息；管理订阅与通知；维护服务器之间的安全边界
Server 服务器提供专门的上下文与能力：通过 MCP 原语暴露 resources/tools/prompts；职责单一、独立运行；可通过客户端接口请求 sampling；必须遵守安全约束；可以是本地进程或远程服务

功能原语（Feature Primitives）

服务器向客户端提供三种原语，客户端向服务器提供三种原语，另有若干通用工具类机制：

方向原语作用
服务器 → 客户端Resources 资源供用户或 AI 模型使用的上下文与数据（如文件内容、数据库记录），由应用控制
Prompts 提示模板面向用户的模板化消息与工作流，由用户选择触发
Tools 工具供 AI 模型执行的函数（模型控制调用）；2025-06-18 版起支持结构化输出与在工具结果中返回 resource links
客户端 → 服务器Sampling 采样服务器发起的 LLM 补全请求，支撑「服务器发起的智能体行为与递归 LLM 交互」；用户必须显式批准
Roots 根目录服务器查询自己应在哪些 URI / 文件系统边界内操作
Elicitation 征询服务器在交互过程中向用户请求补充信息（2025-06-18 版新增）
双向工具类机制配置、进度跟踪（progress）、取消（cancellation）、错误报告、日志（logging）、参数自动补全（completions）、分页

能力协商（Capability Negotiation）

客户端与服务器在初始化时显式声明各自支持的特性，能力决定会话期间哪些协议功能可用：服务器声明如资源订阅（resources.subscribe）、工具支持、提示模板等能力；客户端声明如 sampling、roots、elicitation 支持。双方在整个会话期间必须遵守已声明的能力——例如工具调用要求服务器声明了 tool capabilities，发送资源变更通知要求声明了订阅支持。能力对象还可描述子能力：listChanged（prompts/resources/tools 列表变更通知）与 subscribe（订阅单个资源项变更）。

生命周期与传输层

生命周期三阶段

  1. 初始化（Initialization）：必须是客户端与服务器之间的第一个交互。客户端发送 initialize 请求（携带其支持的协议版本、客户端能力、实现信息）；服务器响应自身版本、能力与实现信息；随后客户端必须发送 initialized 通知表示可以开始正常操作。在服务器响应 initialize 之前，客户端除 ping 外不应发送其他请求。
  2. 操作（Operation）：按协商好的能力交换消息；双方必须尊重协商出的协议版本、只使用协商成功的能力。
  3. 关闭（Shutdown）：无专门关闭消息，由底层传输机制示意连接终止。stdio 传输下客户端应：先关闭服务器子进程的输入流 → 等待退出或发 SIGTERM → 仍未退出则 SIGKILL；HTTP 传输下关闭相应 HTTP 连接即可。

版本协商：客户端在 initialize 中发送其支持（最好是最新）的协议版本；服务器若支持则必须原样返回，否则返回自己支持的最新版本；客户端不支持服务器返回的版本时应当断开。超时与错误：实现应为所有请求设置超时，超时后发送取消通知；需准备处理协议版本不匹配、能力协商失败、请求超时等错误。

两种标准传输层

JSON-RPC 消息必须以 UTF-8 编码。协议定义两种标准传输机制（客户端应尽可能支持 stdio），也允许自定义传输（须保留 JSON-RPC 消息格式与生命周期要求）：

传输要点
stdio客户端把 MCP 服务器作为子进程启动；服务器从 stdin 读 JSON-RPC 消息、向 stdout 写消息；消息按换行分隔且不得内嵌换行；stderr 可用于日志。stdout/stdin 上不得出现任何非 MCP 消息内容
Streamable HTTP取代 2024-11-05 版的 HTTP+SSE 传输。服务器提供单一 MCP endpoint（如 https://example.com/mcp）同时支持 POST 与 GET：客户端每条消息用 POST 发送（服务器可返回单个 JSON 或升级为 SSE 流）；GET 用于打开 SSE 流接收服务器主动消息。支持会话管理（Mcp-Session-Id 头，初始化时由服务器分配，客户端后续请求必须携带，客户端退出时可 DELETE 显式终止）与断线续传（SSE 事件 id + Last-Event-ID 头重放）。所有后续请求必须带 MCP-Protocol-Version 头
Streamable HTTP 的安全警告（规范原文要求）：服务器必须校验所有入站连接的 Origin 头以防 DNS rebinding 攻击；本地运行时应当只绑定 127.0.0.1 而非 0.0.0.0；应当为所有连接实现适当的认证。缺少这些防护时，攻击者可借 DNS rebinding 从远程网站与本地 MCP 服务器交互。

版本演进（2025-06-18 主要变化）与安全要求

相对 2025-03-26 版的九大变化

  1. 移除 JSON-RPC batching（批量消息）支持；
  2. 新增结构化工具输出（structured tool output）；
  3. 把 MCP 服务器归类为 OAuth Resource Server，增加受保护资源元数据以发现对应授权服务器；
  4. 要求客户端实现 RFC 8707 Resource Indicators，防止恶意服务器窃取访问令牌；
  5. 澄清授权规范中的安全考虑，并新增安全最佳实践页；
  6. 新增 elicitation：服务器可在交互中向用户请求补充信息；
  7. 工具调用结果支持 resource links；
  8. HTTP 传输下所有后续请求必须携带 MCP-Protocol-Version 头；
  9. 生命周期操作中一处 SHOULD 升级为 MUST。

其他 schema 变化：更多接口类型增加 _meta 字段；CompletionRequest 增加 context 字段；新增 title 字段用于人类友好显示名（name 保留为程序化标识符）。

安全与信任（Security and Trust & Safety）四原则

规范强调 MCP 通过任意数据访问与代码执行路径带来强大能力，随之而来的安全责任必须由实现者承担：

  1. 用户同意与控制：用户必须显式同意并理解所有数据访问与操作，保留对「共享什么数据、采取什么行动」的控制权；实现者应提供清晰的审查与授权 UI。
  2. 数据隐私：宿主在向服务器暴露用户数据前必须获得显式同意；未经同意不得把资源数据传往他处；用户数据应有适当访问控制。
  3. 工具安全：
    "Tools represent arbitrary code execution and must be treated with appropriate caution. … descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server."工具意味着任意代码执行，必须以相应的谨慎对待；工具行为的描述（如 annotations）除非来自可信服务器，否则应视为不可信。宿主在调用任何工具前必须获得用户显式同意。
  4. LLM Sampling 控制：任何 sampling 请求必须经用户显式批准；用户应能控制是否发生 sampling、实际发送的提示内容、以及服务器能看到什么结果——协议有意限制了服务器对提示词的可见性。

规范同时承认：MCP 协议本身无法在协议层强制执行这些安全原则，因此实现者应当（SHOULD）：在应用中构建健壮的同意与授权流程、清晰记录安全影响、实现适当的访问控制与数据保护、遵循集成安全最佳实践、在特性设计中考虑隐私影响。

影响与课程关联

  • 与第四讲的关系：CS329Z Lecture 4「Tool Use & Function Calling」覆盖 REPL、function-calling API、MCP、工具设计、代码执行沙箱与错误处理。function calling 解决的是「模型如何表达要调用哪个工具」（模型层 API，各家格式不一），MCP 解决的是「工具/数据如何被任何应用发现、连接与调用」（协议层标准）——两者互补：模型经 function calling 决策，宿主经 MCP 执行。本篇即该讲唯一必读材料。
  • 与第一讲的关系：Lecture 1 把 MCP 放在「复合 AI 系统：RAG、工具使用与 MCP」章节中介绍（见 复合 AI 系统精讲），MCP 正是复合系统「工具组件」的标准化接口。
  • 生态影响：协议由 Anthropic 于 2024 年末发起并开源，此后被主流 AI 应用广泛采纳（官方文档列举 Claude、ChatGPT、VS Code、Cursor 等），课程页将规范治理方标注为 The Linux Foundation。「服务器易构建 + 高度可组合 + 相互隔离」的设计使工具生态可以像 npm 包一样被复用，成为智能体工程事实上的连接标准。
  • 工程启示：规范中「宿主负责编排与安全策略、服务器职责单一」「能力协商 + 渐进增强」「工具描述不可信、调用需用户同意」等条款，直接对应构建生产级智能体时的权限模型与信任边界设计（与 Lecture 14 Agent Safety 的主题呼应）。
