Building Effective Agents

构建有效的智能体
作者：Erik Schluntz & Barry Zhang　|　出处：Anthropic Engineering Blog（2024-12-19）

TL;DR 背景 核心观点 五种工作流模式 自主智能体 框架使用 实践建议 影响与关联 术语对照
一句话总结（TL;DR）：最成功的 LLM 智能体实现并不依赖复杂框架，而是使用 简单、可组合的模式（simple, composable patterns）——先从「增强型 LLM」这一基础构建块出发， 按需在五种工作流模式（提示链、路由、并行化、编排者—工作者、评估者—优化者）与自主智能体之间选择， 只有当复杂度确实换来更好的结果时才增加它。

一、背景与要解决的问题

本文是 Anthropic 工程团队基于与数十个行业团队合作构建 LLM 智能体的经验写成的实践指南，发布于 2024 年 12 月， 已成为智能体工程领域被引用最多的入门文献之一（也是 CS329Z 第二讲的必读材料）。

它要回答的核心问题是：怎样才算「构建好了」一个 LLM 智能体系统？ 当时业界充斥着各种智能体框架和「全自动 agent」宣传，而作者观察到：真正在生产环境中稳定运行的系统， 大多是由少量清晰、可测试的模式组合而成，而不是把一切都交给模型「自主发挥」。

"Consistently, the most successful implementations use simple, composable patterns rather than complex frameworks." 一贯而言，最成功的实现使用的是简单、可组合的模式，而非复杂的框架。

注：原文页面顶部提示，自 2024 年 12 月发布以来工具生态已有演进，Anthropic 当前的相关实践可另参考其「Managed Agents」等新内容；但本文的模式划分至今仍是行业通用语汇。

二、核心观点

观点 1：一切从「增强型 LLM」这个构建块开始

智能体系统的基本构建块是 增强型 LLM（augmented LLM）： 在语言模型之上加入检索（retrieval）、工具（tools）与记忆（memory）三类能力。 这些增强应贴合具体用例，并为模型提供易用、文档清晰的接口（文中提到可通过 Model Context Protocol 接入第三方工具）。

观点 2：「agentic systems」内部分两类——工作流 vs 智能体

作者把各种 LLM 驱动的系统统称为 agentic systems（智能体系统），并在其中做出关键区分：

工作流 Workflows智能体 Agents
控制方式LLM 与工具按预定义代码路径（predefined code paths）编排LLM 动态决定自己的流程与工具使用（dynamically direct their own processes and tool usage）
可预测性高：路径固定、易测试低：步骤数与路径不确定
成本/延迟较低较高，且错误可能累积
适用子任务可预先枚举的固定流程开放式问题、无法硬编码路径的任务
"They are typically just LLMs using tools based on environmental feedback in a loop." （所谓智能体）通常不过是 LLM 在循环中基于环境反馈使用工具而已。

观点 3：何时（以及何时不）使用智能体

  • 不要过早构建复杂智能体：许多应用只需单次模型调用 + 检索 + 上下文示例（in-context examples）优化即可达到很好效果。
  • 智能体系统本质上是用更高的延迟与成本换取更好的任务表现——只有当任务价值配得上这个代价时才值得。
  • 需要稳定一致的固定任务更适合工作流；步骤无法预测的开放问题才适合自主智能体。
  • 智能体应在沙箱环境中充分测试，并加防护（guardrails），因为其错误会随步骤累积。

观点 4：框架可以用，但先直接用 API

文中点名了 LangGraph、Amazon Bedrock 的 Strands Agents、Rivet、Vellum 等框架（以及 Anthropic 自家的 SDK）。框架的价值：

  • 简化入门：开箱即得的循环、工具调用、可视化调试。

框架的风险：

  • 额外的抽象层会把提示词与响应藏起来，让调试更难；
  • 容易诱使你在并不需要时就给系统加复杂度。

作者建议：先直接使用 LLM API（很多模式几行代码即可实现）；如果用框架，务必理解其底层代码——对底层机制的错误假设是常见的 bug 来源。

三、方法与框架：五种工作流模式

这是全文最常被引用的部分——五种可组合的 workflow 模式，每种都给出机制、适用场景与示例。

模式 1：提示链 Prompt Chaining

机制：把任务分解为一系列步骤，每一步的 LLM 调用处理上一步的输出；步骤之间可以插入程序化检查（gate）， 对中间结果做验证，保证方向正确。

适用：任务可以清晰拆成固定的子任务序列；愿意用更多延迟换取更高的准确性与可控性。

原文示例：

  • 先写营销文案 → 再把文案翻译成目标语言；
  • 先产出文档大纲 → 程序检查大纲是否达标（gate） → 再依据大纲写正文。

模式 2：路由 Routing

机制：先对输入进行分类，再把它导向专门化的后续流程——实现关注点分离（separation of concerns）， 让每类输入都能拿到针对性的提示词与工具，避免「一个巨型提示包打天下」。

适用：复杂任务中存在明显可区分的类别，且分类可由模型（或传统分类器）准确完成。

原文示例：客户服务系统把「普通咨询 / 退款请求 / 技术支持」路由到不同的后续提示、工具与流程； 简单常见问题交给便宜的小模型，困难或罕见问题交给更强（更贵）的模型——同时优化成本与质量。

模式 3：并行化 Parallelization

机制：多个 LLM 同时处理任务，结果由程序汇总。包含两种变体：

  • 分节（Sectioning）：把任务拆成互相独立的子任务并行跑；
  • 投票（Voting）：同一任务跑多次（不同提示或不同视角），以多数/综合结果提高置信度。

适用：子任务可并行以压低延迟；或需要多视角、多次尝试来提升可靠性。

原文示例：一个模型回答用户请求、另一个模型并行审查不当内容；自动评测（grader）中每个模型评估代码的不同方面； 用多个不同提示审查代码漏洞；多个提示/阈值投票判断内容是否违规。

模式 4：编排者—工作者 Orchestrator-Workers

机制：一个中心 LLM 动态地拆解任务，把子任务分派给多个工作者 LLM，最后综合它们的输出。 与并行化的区别在于：子任务不是预先知道的，而是由编排者根据具体输入临场决定。

适用：复杂任务的子任务无法事先枚举、需要按输入灵活拆解的场景。

原文示例：编码产品需要同时修改多个文件（改哪些文件事先不知道）； 搜索任务需要从多个来源收集并分析可能相关的信息。

模式 5：评估者—优化者 Evaluator-Optimizer

机制：一个 LLM 生成响应，另一个 LLM 在循环中评估该响应并给出反馈，生成者据反馈迭代改进—— 相当于把「人类评审—修改」循环自动化。

适用：我们有清晰的评估标准，且迭代确实能带来可衡量的价值； 当人类反馈能明显改善输出时，LLM 评审反馈往往也能起到类似作用。

原文示例：文学翻译——评估模型指出初译没有捕捉到的细微之处（nuances），翻译模型据此修改； 复杂搜索——评估模型判断当前的检索与分析是否足以回答问题、要不要继续深挖。

四、自主智能体（Agents）

定义与运行机制

当任务无法用固定流程解决、需要模型自己决定步骤时，才使用自主智能体。其运行是一个循环：

  1. 启动：智能体从人类用户的命令或交互式讨论中开始工作；
  2. 规划与行动：模型基于任务与当前状态，自己决定下一步动作（通常是调用工具）；
  3. 环境反馈：智能体依据工具调用结果、代码执行输出等来自环境的反馈（ground truth）判断进展、修正计划；
  4. 检查点 / 人类介入：可在检查点或遇到阻碍时暂停，向人类请求反馈、补充信息或判断；
  5. 停止：任务完成时终止，或触发停止条件（如最大迭代次数）以保持控制。
"Agents begin their work with either a command from, or interactive discussion with, the human user." 智能体的工作始于人类用户的一条命令，或与人类用户的交互式讨论。
"Agents can then pause for human feedback at checkpoints or when encountering blockers." 智能体随后可以在检查点或遇到阻碍时暂停，等待人类反馈。

什么时候值得用

  • 开放式问题：所需步骤难以预测、无法硬编码固定路径；
  • 可以在可信环境中让模型多轮执行、且能拿到真实反馈（测试、编译器、页面渲染结果等）；
  • 任务价值足以覆盖更高的成本、延迟与错误累积风险。

反过来，如果单次调用 + 检索 + 示例已经够用，就不要引入智能体。

原文给出的两个实例

  • 编码智能体：解决 SWE-bench 类任务——仅凭 issue / 拉取请求描述，自主编辑多个文件； 自动测试可以验证功能是否正确，但作者强调人工审查仍然重要。
  • 计算机使用（computer use）参考实现：Claude 直接操作计算机（截图→点击→输入循环）完成任务。

五、结论与实践建议

组合与定制

作者强调：这些模式不是固定处方，而是可以按场景改造、组合的词汇表。 正确做法是：从最简方案开始 → 度量性能 → 只在复杂度确实改善结果时才引入更复杂的模式。

"Success in the LLM space isn't about building the most sophisticated system." 在 LLM 领域，成功并不在于构建最精巧复杂的系统（而在于构建合适的系统）。

总结中的三条原则

  1. 简洁（simplicity）：能单调用解决的不上工作流，能工作流解决的不上自主智能体；
  2. 透明（transparency）：明确展示智能体的规划步骤，便于调试与信任；
  3. 精心打磨智能体—计算机接口（ACI）：通过充分的工具文档与测试，建立可靠的接口—— 像设计 UI 一样设计工具的提示、参数与输出格式。

附录要点

  • 附录 1（智能体实战）：客户支持（customer support）与编码智能体（coding agents）是两类被验证特别有价值的应用方向。
  • 附录 2（给你的工具做提示工程）：工具的名称、参数、描述与输出格式都应像提示词一样认真设计与测试， 目标是最大限度降低模型误用工具的概率——例如给参数起无歧义的名字、写清楚什么时候该用/不该用、 返回省 token 且信息完整的输出（如相对路径而非整个文件内容）。

六、影响与后续

  • 本文的「workflow vs agent」二分法与五种模式命名已成为行业通用语汇，被 OpenAI《A Practical Guide to Building Agents》、 Google 的 agent 白皮书等大量后续文献沿用。
  • 「增强型 LLM」「ACI（agent-computer interface）」等概念直接对应 CS329Z 第一、二讲中的智能体架构内容 （LLM 核心 + 规划 + 记忆 + 工具 + 环境）；本文是第二讲「面向智能体的 LLM」部分的必读材料。
  • Anthropic 后续推出的 Claude Agent SDK、MCP（Model Context Protocol）生态，可以视为本文理念的产品化。
  • 同专栏延伸阅读：《Effective Context Engineering for AI Agents》（第二讲扩展阅读）。
